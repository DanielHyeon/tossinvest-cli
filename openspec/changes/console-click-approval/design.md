# Design: console-click-approval

## A1. 승인의 성립 요건 — 무엇이 사라지고 무엇이 남는가

현행 콘솔 승인은 네 겹이었다.

| 겹 | 무엇을 막는가 | 이 change 이후 |
|---|---|---|
| 루프백 전용 바인딩 | 원격 접근 | 유지 |
| 세션 토큰(프로세스 수명, URL→쿠키 1회 교환) | 이 머신의 다른 사용자·프로세스 | 유지 |
| CSRF 토큰 | 타 사이트가 유도한 POST | 유지 |
| 화면 표시 nonce 타이핑 | "실수로 눌렀다" | **제거** |
| 승인 창 TTL 5분 | 묵은 가격에 대한 승인 | 유지 |
| 계획 목록 표시 + `Plan.Authorises` | 목록 밖 요청 | 유지 |

제거되는 것은 오직 "실수 클릭 방지" 한 겹이고, 그 자리는 **계획 목록을 띄운 전용 화면의
명시적 버튼**이 대신한다. 대시보드나 목록 화면에는 승인 버튼이 없다 — 승인은 그 계획을
보여주는 화면에서만 가능하다.

근거: 이 콘솔은 단일 사용자가 자기 머신의 루프백에서만 여는 도구다. 타이핑은 세션 탈취
공격자에게는 비용이 아니고(화면에 nonce가 그대로 보인다) 정당한 사용자에게만 비용이다.
2026-07-27 실측이 그 비용을 보여줬다 — 장중 창 하나가 측정 0건으로 소모됐다.

## A2. 왜 "클릭조차 없는 자동 승인"은 아닌가

사용자 요청은 "웹에서 자동화"다. 자동화의 범위를 다음 선에서 끊는다.

- 실행 진행(단계 순회·재시도·백오프·기록)은 이미 전부 자동이다.
- 계획 수립과 표시도 자동이다.
- **실계좌에 첫 요청이 나가기 직전의 사람 행위 하나**는 남긴다.

§0.1은 "사람 승인 없는 LIVE 주문 side effect"를 금지한다. 클릭은 사람의 행위이고 타이핑도
사람의 행위지만, 스케줄러가 장 개장에 맞춰 스스로 승인하는 것은 사람의 행위가 아니다.
전자 둘 사이의 선택은 UX 결정(사용자 소관)이고, 후자로 넘어가는 것은 안전 불변식의 변경
이다. 이 change는 UX 결정만 반영한다.

## A3. Prompt/Summary 분리

`Batch.Prompt()`는 지금 세 가지를 한 문자열에 담는다: ① 계획 목록, ② 확인 문자열과 만료,
③ "입력하라" 지시. 콘솔은 이 전체를 `<pre>`에 렌더해 왔다(pages.go 주석: 계획을 HTML로
다시 그리면 두 번째 요약이 생기고, 배치 모델은 요약의 완전성에 걸려 있다).

클릭 승인에서 ②③을 그대로 보여주면 화면이 거짓말을 한다. 그렇다고 HTML로 재렌더하면
요약이 둘이 된다. 그래서 **문자열을 쪼갠다**:

```
Summary()  = ① 계획 목록 (콘솔이 렌더, TTY도 이걸 먼저 출력)
Prompt()   = Summary() + ② 확인 문자열/만료 + ③ 타이핑 지시   (TTY 전용)
```

요약의 원천은 여전히 하나(`Plan.WriteLines`)이고, 콘솔과 터미널이 보는 목록은 byte 단위로
같다. `Prompt()`의 기존 출력은 Summary 부분이 앞에 그대로 오도록 유지한다 — CLI 사용자가
보는 화면은 변하지 않는다.

## A4. 증거 기록의 채널 표기

`approval.model` 관측의 detail이 지금 "one typed expiring string for the whole run"이다.
콘솔 클릭 승인 run에서 이 문장은 거짓이 된다. 증거 기록은 나중에 "사람이 무엇을 보고
무엇을 했는가"를 증명하는 물건이므로 거짓 문장을 남길 수 없다.

`Options.ApprovalChannel`(문자열, zero value = TTY 타이핑)로 호출자가 채널을 말하고,
`recordApproval`이 그 값을 detail에 쓴다. 콘솔 배선(`cmd/tossctl/console.go`)만 클릭
채널을 넘긴다. zero value가 기존 의미이므로 다른 호출자·테스트는 무변경이다(§0.2).

## A5. 무동작 기본값 제거

시작 화면의 두 동작:

| 동작 | 대상 | 지금 |
|---|---|---|
| 이어하기(`mode=resume`) | 판정이 없는(비terminal) 단계 | 대상 0이어도 활성 — 눌리면 즉시 0단계 종료 |
| 재측정(`mode=redo`) | 판정이 `fail`·`skipped`인 단계 | 아래 별도 섹션 |

`Pending`(비terminal 단계)이 비었으면 이어하기는 정의상 아무것도 하지 않는다. 그때는
비활성화하고 이유를 쓴다 — 그리고 재측정 대상이 있으면 그쪽이 기본 동작으로 앞에 온다.
판단 근거는 전부 이미 화면이 들고 있는 값(`Snap.Verify.Pending`, `Snap.Verify.Redo`)이고
새 상태를 만들지 않는다. 대상 계산은 계속 **기록**에서 하며 폼에서 받지 않는다.

## A6. 대안과 기각 사유

- **원클릭(시작 = 승인)**: 계획이 만들어지기 전에 승인하게 되어 "본 목록만 승인된다"는
  배치 모델의 근거가 사라진다. 기각.
- **타이핑 대신 체크박스**: 마찰의 형태만 바꾼 것으로 사용자 지시의 취지에 어긋난다. 기각.
- **콘솔 재시작 후 자동 이어하기**: 다음 창의 클릭 수를 줄이지만 재기동 경로에 자동 실행
  상태를 새로 만든다. 이 change의 범위 밖으로 둔다(필요하면 별도 change).
