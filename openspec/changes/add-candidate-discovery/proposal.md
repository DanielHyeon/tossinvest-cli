# Change: add-candidate-discovery

## Why

발굴 **데이터**는 다 있다. 발굴 **판정**이 없다.

현재 소스에는 공식 Open API 랭킹(`MARKET_TRADING_AMOUNT`, `MARKET_TRADING_VOLUME`,
`TOP_GAINERS`, `TOP_LOSERS` — [market_reads.go:333](../../../internal/official/market_reads.go)),
투자자 매매, 지표 캔들, 그리고 WTS의 인기 순위·투자자 순위·테마·AI 시그널·스크리너
([wts_operations.go](../../../internal/ops/wts_operations.go))가 모두 구현돼 있고 CLI에서
호출된다. 그런데 이것들은 **한 번 호출해서 지금 상태를 출력**한다.

한 번의 조회는 조기 발굴이 아니다. `TOP_GAINERS`는 정의상 **이미 오른 종목**의 목록이고,
그것을 그대로 후보로 쓰면 StockOS에서 문제였던 추격매수가 그대로 재현된다. 조기 발굴과
뒤늦은 발굴을 가르는 것은 데이터 원천이 아니라 **시간축**이다:

| 필요한 것 | 지금 |
|---|---|
| 같은 심볼을 시간에 걸쳐 다시 관측 | 없음 — 매 호출이 독립 |
| 처음 임계를 통과한 **시각** | 없음 |
| 거래대금·거래량의 **가속도** | 없음 — 수준만 있고 변화율이 없다 |
| 우리가 늦게 본 것을 늦었다고 표시 | 없음 |
| 원천이 줄어든 사실의 기록 | 없음 |

비테스트 소스에서 `CandidateEvidence`, `anti-chase`, `seen_late`, `pullback`,
`entry_quality`는 **0건**이다. `internal/candidate`는 존재하지 않는다.

### 영속이 부가 기능이 아니라 정의의 일부인 이유

"처음 본 시각"이 프로세스 메모리에만 있으면, 재시작할 때마다 **모든 종목이 방금 발견한
것이 된다.** 그러면 추격 판정은 항상 "방금 발견했으니 늦지 않았다"고 답하고, 조기 발굴
시스템이 구조적으로 **늦은 발굴 시스템**이 된다. 관측 이력의 영속은 성능이나 편의가 아니라
이 기능이 주장하는 바로 그것의 전제다.

### 왜 지금, 2c와 병행인가

발굴은 **읽기 전용**이다. 주문 경로에 닿지 않으므로 `ProtectionReady` 인터록과 무관하게
진행할 수 있고, 실계좌 주문 검증의 완료를 기다릴 기술적 이유가 없다.

로드맵은 이것을 Phase 3 `add-strategy-engine`의 T3.1로 두고 착수 조건을 T1.14·T2.8 완료로
걸어 뒀다([ROADMAP.md](../../../docs/ROADMAP.md)). 그 순서에는 안전상의 이유가 있지만,
그 이유는 **주문을 내는 부분**에만 해당한다. 후보를 기록하고 화면에 보여주는 부분까지
막을 이유는 없고, 막아 두면 2c가 열리는 날 관측 이력이 **0일치**인 채로 시작하게 된다.
반대로 지금 세워 두면 2c가 열릴 때 며칠치 실데이터가 이미 쌓여 있고, "그때 이 후보를
샀으면 어땠나"를 [counterfactual.go](../../../internal/measure/counterfactual.go)의 기존
반사실 측정으로 답할 수 있다.

따라서 이 change는 T3.1을 `add-strategy-engine`에서 **떼어내 선행**시키고, 로드맵 Phase 3의
착수 조건을 그에 맞게 고친다.

## What Changes

**새 capability: `candidate-discovery`** (`internal/candidate`)

- **관측 누적** — `(market, symbol)`마다 시각이 붙은 관측을 반복 기록한다. 순위, 거래대금,
  거래량, 가격, 어느 원천이 올렸는가.
- **최초 통과 시각** — 그 심볼이 처음 임계를 넘은 시각을 잡고, 재시작을 넘어 유지한다.
- **시간축 지표** — 거래대금·거래량 가속도, 최초 발견가 대비 확장률, 일중 range position.
- **추격 위험 veto** — `seen_late`(처음 봤을 때 이미 크게 초과), `extended`(발견가 대비
  확장), `near_high`(일중 고점 근접). 점수가 아니라 **거부권**이다.
- **원천 강등의 기록** — WTS가 만료·실패해도 공식 랭킹만으로 후보를 계속 낸다. 단
  `sources`와 `degraded`를 후보에 남겨, 원천이 줄어든 것을 모르고 판단하는 일이 없게 한다.
- **영속** — 엔진 원장과 **분리된** 자체 저장소. 발굴이 원장 락을 다투지 않는다.
- **사람이 보는 표면** — `tossctl candidate scan`(1회), `tossctl candidate watch`(반복),
  콘솔 후보 화면.

## Non-Goals

이 change에 **없는 것**을 명시한다. 있다고 오해되면 안전 판단이 틀어진다.

- **진입 판정·주문·사이징이 없다.** 후보는 어떤 경로로도 주문이 되지 않는다.
- **Guardian 입력 배선이 없다.** `internal/risk`·`internal/execgw`에 연결하지 않는다.
- **전략 레인(T3.2)·장 시간 스케줄러(T3.3)·레인별 성과(T3.4)가 없다.** `watch`는 사람이
  띄우는 반복 스캔이지 장 시간 인지 루프가 아니다.
- **자동 실행이 없다.** 엔진이 이 패키지를 부르지 않는다.
- **매수 임계의 최적화가 없다.** 임계는 설정 가능한 보수적 기본값으로 두고, 무엇이 좋은
  임계인지는 이 change가 쌓는 데이터로 나중에 답한다.

## Impact

- **새 패키지**: `internal/candidate`
- **새 명령**: `tossctl candidate scan`, `tossctl candidate watch` (둘 다 `mutating: false`)
- **새 콘솔 화면**: `/candidates`
- **읽는 것**: `internal/official`(랭킹·캔들·투자자), `internal/ops`(WTS 조회) — 기존 계약
  그대로, 수정 없음
- **손대지 않는 것**: 주문·손절·사이징·Guardian·원장·대사·인증·체결 경로. `ProtectionReady`,
  automation gate, 엔진 기동 순서 전부 무변경
- **rate 예산**: 같은 계좌를 엔진·검증과 공유한다. 스캔 간격 하한과 원천별 호출 상한이
  필요하다(아래 spec) — 읽기 전용이라도 429는 엔진의 체결 감지를 늦출 수 있다

## Risks

| 위험 | 완화 |
|---|---|
| 발굴 폴링이 rate 예산을 먹어 엔진의 체결 감지를 늦춘다 | 스캔 간격 하한 + 원천별 호출 상한을 spec에 고정. 검증 runlock이 살아 있으면 `watch`는 시작하지 않는다 |
| 이 패키지가 나중에 주문 경로에 몰래 배선된다 | 의존성 격리 테스트 — `internal/candidate`가 주문 인터페이스를 **타입으로도** 볼 수 없게 고정(엔진 패키지가 WTS 쓰기 경로를 못 보게 한 것과 같은 방식) |
| 검증되지 않은 수익성 결론이 기록·기억에 남는다 | 후보 저장소는 **관측만** 담는다. "좋은 후보"라는 판정은 저장하지 않고, 화면은 지표와 veto 사유를 그대로 보여준다 |
| 임계를 잘못 잡아 후보가 0건 또는 수백 건 | 기본값은 보수적으로, 스캔 결과에 **임계별 통과 수**를 같이 출력해 사람이 조정할 수 있게 한다 |
