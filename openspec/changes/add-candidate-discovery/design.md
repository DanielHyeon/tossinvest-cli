# Design: add-candidate-discovery

## D1. 후보의 정체성과 수명

**정체성은 `(market, symbol)`이다.** 원천이 아니다 — 같은 종목이 공식 거래대금 순위와 WTS
인기 순위에 동시에 올라오면 그것은 후보 하나이고, 두 원천이 그 하나를 지지한 것이다.

**수명은 세션이 아니라 연속이다.** 임계 아래로 내려간 후보를 즉시 지우면 안 된다:

```
활성(active)    임계 통과 중
냉각(cooled)    임계 아래로 내려갔으나 아직 만료 전
만료(expired)   냉각 TTL 경과 — 다음 통과는 새 후보
```

**재진입 규칙**: 만료 전에 다시 임계를 넘으면 **원래 `first_seen_at`을 유지**한다. 새로
잡지 않는다. 잠깐 순위 밖으로 나갔다 돌아온 것을 "새로 발견"으로 치면 추격 판정이
무력화된다 — 이미 두 배 오른 종목도 한 번 순위에서 빠졌다 들어오면 "방금 발견"이 된다.
이 규칙 하나가 D3의 veto가 우회되는 유일한 경로를 막는다.

## D2. 저장은 원장이 아니다

후보 저장소는 **엔진 journal과 별개 파일이고 별개 락**이다.

| | journal | candidate store |
|---|---|---|
| 권위 | 주문·체결·포지션의 정본 | 파생 관측 |
| writer | 계좌당 1개, flock 배타 | 스캔 프로세스 |
| 손실 시 | 복구 절차 필요 | 이력이 짧아질 뿐 |
| 쓰기 빈도 | 이벤트 발생 시 | 스캔마다 수십~수백 행 |

**같은 락을 쓰면 안 되는 이유**: 발굴 스캔이 원장 락을 잡으면 그동안 엔진이 기동하지
못한다. 관측 기능이 실행 기능을 막는 것은 방향이 거꾸로다.

**SQLite를 쓴다**(JSONL이 아니라). 이 change의 질의는 전부 시계열이다 — "이 심볼이 처음
임계를 넘은 시각", "최근 N분의 거래대금 차분", "관측 간격". JSONL이면 매 스캔마다 전량을
읽어 재생해야 하고, 그 비용이 스캔 간격을 결정하게 된다.

위치는 XDG data dir(원장과 같은 디렉터리, 다른 파일). ext4 강제·fuseblk 거부 규칙은 원장의
것을 그대로 따른다 — 같은 이유(부분 쓰기)가 여기에도 있다.

**"그대로 따른다"는 import가 아니라 복사다** (2026-07-28 리뷰에서 명시). `internal/journal`을
import하면 원장의 API 전체가 이 패키지의 타입 공간에 들어오고, 그것이 정확히 D7·spec
Requirement 6이 막는 것이다. 그래서 `internal/candidate/fsguard.go`는 원장 파일의 복사이고,
대가는 다음 두 가지로 지불한다.

- `fsguard_drift_test.go`가 `internal/journal/fsguard.go`를 **소스로 읽어**(import가 아니다)
  허용 집합의 **멤버십**을 양방향으로 대조한다. 상수 대조만으로는 부족하다 — 원장이 어떤
  파일시스템을 거부 목록으로 옮겨도 상수는 그대로이기 때문이다.
- 저장소 전역 안전 테스트 `internal/testenv` `TestFixedFSProberIsTestOnly`의 허용 파일이
  1개에서 2개가 된다. 대신 그 테스트를 **파일 단위 면제에서 선언 단위 면제로** 좁힌다 —
  정의 파일 안에서의 *호출*도 잡는다. `CheckFilesystem`의 nil-prober 분기를 고정 prober로
  "고치는" 것이 가장 자연스러운 실수이고, 그러면 durability guard가 모든 호출자에게서 꺼진다.

전역 안전 불변식을 건드리는 변경이므로 diff에만 남기지 않고 여기에 적는다.

## D3. 추격 위험은 veto이고 점수가 아니다

점수에 섞으면 다른 축이 상쇄한다. "거래대금 가속도가 대단하니 고점 근처인 건 감수"라는
합산은 정확히 추격매수의 논리다. 그래서 별도 불리언 + **사유 코드**로 둔다.

| 코드 | 의미 | 왜 이것이 위험인가 |
|---|---|---|
| `seen_late` | **처음 관측했을 때 이미** 임계를 크게 초과 | 우리가 늦게 도착했다. 이 종목의 조기 구간은 우리가 못 봤다 |
| `extended` | 최초 발견가 대비 확장률이 상한 초과 | 우리가 일찍 봤더라도 지금 진입은 늦다 |
| `near_high` | **일중 고가까지의 거리가 하한 미만** | 되돌림 여지가 없는 자리 |

### `near_high`의 부호 (2026-07-28 §3 구현 중 발견)

이 표는 원래 "일중 range position이 **상한 초과**"였고, 그것은 계약값과 **정반대**였다.

`near_high_threshold_pct: 2.0`의 경계 고정은 `1.99 true / 2.00 false`다. 즉 저장하는 수는
**고가까지의 거리**이고 비교는 `<`다 — 거리가 작을수록 위험하다. "상한 초과"를 그대로 구현하면
`>`가 되고, **고점에서 먼 후보에 veto가 걸리고 고점에 붙은 후보가 통과한다.** D3이 거부권이라
부른 판정이 정확히 반대로 돈다.

이름도 흔들렸다 — D8의 예시는 `고점 거리 4.1%`로 거리를 쓰는데 이 표와 spec은 `근접도`를 썼다.
근접도는 "가까울수록 큰 값"으로도 읽히므로, 같은 문서 안에서 두 단위가 섞여 있었다.

**결정**: 용어를 **고가까지의 거리**로 통일하고 비교를 명시한다.

```
distance_pct = (day_high - price) / day_high * 100
near_high    = distance_pct < near_high_threshold_pct     # 2.0
```

`day_high`가 없으면 이 식은 계산되지 않는다 — `false`가 아니라 `unmeasured`다(D10).

**`seen_late`와 `extended`는 다른 실패다.** 전자는 관측 시스템의 한계(늦게 봤다), 후자는
타이밍(봤지만 지금은 아니다). 하나로 합치면 어느 쪽을 고쳐야 하는지 알 수 없게 된다 —
전자가 많으면 스캔 간격이나 원천을 고쳐야 하고, 후자가 많으면 임계를 고쳐야 한다.

veto가 걸린 후보도 **저장하고 화면에 보여준다.** 지우면 "우리가 늦게 본 종목이 얼마나
되는가"를 나중에 셀 수 없고, 그 수가 이 시스템이 실제로 조기인지 아닌지의 유일한 증거다.

## D4. 원천 강등은 조용히 하지 않는다

WTS는 세션 만료·계약 변경으로 언제든 끊길 수 있다(로드맵 원칙 5). 그때 후보 산출이 멈추면
안 되지만, **원천이 줄어든 줄 모르고 판단하는 것은 더 나쁘다.**

- 후보마다 `sources`(그 후보를 올린 원천 목록)와 `completeness`(응답한 원천 / 시도한 원천).
- 스캔 결과에 `degraded` 표시와 어떤 원천이 왜 빠졌는지.
- **공식 Open API만으로도 후보가 나오는 구성**이 기본이고 WTS는 가산이다. 반대로 만들면
  WTS가 끊긴 날 발굴이 통째로 멈춘다.

## D5. 시각은 주입한다

이 change의 본질이 시간축이므로, 실제 시계에 의존하면 테스트가 시간축을 만들 수 없다.
`internal/clock`의 주입 가능한 clock을 쓴다(T1.13). 테스트는 "10분 뒤 두 번째 스캔"을
10분 기다리지 않고 만든다.

**관측 간격은 불규칙하다고 가정한다.** 스캔이 매번 같은 간격으로 돌지 않는다(429 백오프,
사람이 띄웠다 껐다). 그래서 가속도는 "관측당 차분"이 아니라 **경과 시간으로 정규화한
차분**이어야 한다. 이것을 안 하면 스캔이 촘촘한 구간에서 가속도가 작아 보인다.

## D6. 파생값은 파생이라고 표시한다

원천이 준 값과 우리가 계산한 값을 구분해 저장한다. 나중에 원천의 의미가 바뀌거나 우리
계산이 틀렸을 때, 어느 쪽을 고쳐야 하는지 기록만 보고 알 수 있어야 한다. 로드맵의
"모든 정책 수치는 출처·적용 시장·검증 상태를 기록한다"와 같은 규칙이다.

## D7. 격리는 테스트로 강제한다

`internal/candidate`가 주문 인터페이스를 **타입으로도 볼 수 없게** 의존성 테스트로 고정한다.
`internal/app/engine`이 WTS 쓰기 경로를 못 보게 한 것과 같은 장치다
([exitloop.go](../../../internal/app/engine/exitloop.go)의 의존성 주석 참조).

주석이나 리뷰 합의가 아니라 테스트여야 하는 이유: 이 패키지는 앞으로 전략 레인이 붙을
자리이고, 그때 "후보에서 바로 주문 한 줄"이 가장 자연스러운 실수다. 그 한 줄이 컴파일되지
않아야 한다.

### 이 보증의 실제 경계 (2026-07-28 §3 리뷰, 변이로 확인)

구현된 격리 테스트가 **잡는 것**: 직접 금지 import, 금지 패키지에 **간접**으로 닿는 import
(체인을 출력한다), `_test.go`의 import, **컴파일되지 않는 build tag 뒤의** import,
외부 `package candidate_test`, 새 하위 패키지.

**잡지 못하는 것 — 여기 적어 두지 않으면 이 보증이 실제보다 넓게 읽힌다.**

1. **모듈 내부 import가 필요 없는 주문 경로.** 확인됨: `internal/candidate`의 프로덕션 파일에
   `http.Post("https://api.tossinvest.com/api/v1/orders", …)` 한 줄을 넣으면 **네 테스트가 전부
   통과한다.** import 걷기는 모듈 접두사가 없는 경로를 버리므로 표준 라이브러리와 서드파티가
   보이지 않는다.
2. `//go:linkname`·`unsafe`·리플렉션·`os/exec`로 `tossctl`을 부르는 것 — import 간선이 없으므로
   걸을 간선도 없다.
3. **배선 방향.** `internal/candidatesrc`는 `candidate → candidatesrc`를 막으려고 목록에 있을
   뿐이다. candidatesrc·`cmd/`·미래의 레인 패키지가 `candidate.Candidate`를 읽고 `execgw`를
   부르는 것은 이 테스트가 제약하지 않는다.
4. 목록의 항목이 낡아도 아무것도 실패하지 않는다 — 디렉터리를 개명하면 그 항목은 무력해진다.

그러므로 spec 문장 "후보에서 주문으로 가는 코드가 컴파일되지 않아야 한다"는 **`internal/candidate`
안에서** 참이고, 그 밖에서는 참이 아니다. 레인이 붙을 때 이 경계를 다시 읽어야 한다.

**실제로 보증을 지탱하는 것은 금지 목록이 아니다.** `internal/candidate`의 모듈 내부 의존
폐포가 정확히 `{internal/clock}`임을 고정하는 테스트다 — 목록에 있든 없든 **새 간선이 생기면
실패한다.** 금지 목록은 실패 메시지를 사람이 읽을 수 있게 만드는 장치이고, 폐포 테스트가
자물쇠다. 항목이 낡는 위험이 대체로 이론에 머무는 이유도 그것이다.

## D8. 순위는 승격선이 아니라 상세조회 예산 배분기다

**결정(2026-07-28)**: 전 시장·전 레인 공통의 순위 하드 컷을 두지 않는다. 원천이 돌려준 행은
전부 관측하고, `상위 100위`·`상위 50위`는 **hot hint** — 상세조회 큐의 우선순위를 올리는
값이지 후보 자격선이 아니다.

이유는 D3와 같다. 절대 순위를 자격선으로 쓰면 "순위가 높다 = 살 만하다"가 되고, 그것이
정확히 이 change가 끊으려는 결합이다. 판단해야 할 것은 순위 자체가 아니라 **순위 변화 +
가속도 + 발견 시점 + 고점 거리**다.

```
현재 137위 · 30초 전 198위 · 가속도 2.4배 · 고점 거리 4.1%  → 관측·hot queue 대상
현재 3위   ·                  가속도 3.0배 · 고점 거리 0.4%  → 관측은 계속, 승격은 veto
```

### 순위 변화는 백분위로 정규화한다

원천마다 리스트 길이가 다르므로(KR 150행, US 100행) "30계단 상승"은 원천마다 다른 뜻이다.
기준은 `rank_percentile_gain_30s >= 20%p`다.

#### 그런데 "30초"가 아무것도 제한하지 않았다 (2026-07-28 §3 리뷰)

구현의 `window` 인자는 **최대 최신성**이지 최대 나이가 아니었다. 30초·30분·9시간·40시간
간격이 전부 같은 값에 사유도 없이 돌아왔다. 손잡이 이름이 `percentile_gain_30s_pct`인데
40시간짜리 상승이 그 기준을 통과한다.

**결정 1**: `RankMove`가 **경과 초를 함께 기록한다**. D9가 `Window`에 두 창의 실제 초를
넣은 것과 같은 이유이고 같은 문장이다 — 읽는 사람이 타임스탬프에서 다시 유도하게 두지 않는다.

**결정 2**: 직전 관측의 나이 상한은 **10분**이고, 유도는 `DefaultStalenessTTL`과 **같다** —
계획된 최장 백오프(300초)의 두 배. `window`의 배수로 두지 않는다: 배수는 누가 창을 조정하면
같이 움직이는데, 직전 관측을 낡게 만드는 것은 창 길이가 아니라 **백오프 사다리**다.
30→60→120→300초는 이 설계가 일어난다고 보장한 일이므로, 두 번째 단계에서 거부하는 상한은
**설계가 예정한 후퇴 동안 순위 속도를 미측정으로 만든다.**

**상한은 보호가 아니라 백스톱이다.** 보호는 경과 초다 — 그것을 읽지 않고 `20%p`와 비교하는
소비자는 상한이 어디 있든 틀렸다. 10분을 넘는 간격은 사다리로 설명되지 않는다. 장 마감이거나
프로세스가 죽었거나 세션 경계이고, 그것은 다른 사실이라 거부할 값이 있다.

### 신규 진입은 순위 속도가 아니라 별도 사실이다 (교정 1)

**문제**: 처음 리스트에 등장한 종목은 직전 백분위가 없다. 이것을 "직전 = 최하위"로 채우면
**모든 신규 진입이 자동으로 순위 속도 통과**가 된다. 리스트 경계(150행 중 140~150위)는
매 스캔 들락거리므로, 그 자리의 잡음이 전부 급상승으로 기록된다.

**결정**: 신규 진입은 `newly_listed`라는 **별개의 사실**로 남기고 `rank_percentile_gain`에
합성하지 않는다. 값을 지어내지 않고 없음을 없음으로 남긴다(D6).

이 구분은 그 자체로 `seen_late` 회계에 필요하다 — **12위로 진입한 종목과 148위로 진입한
종목은 다른 사건**이고, 전자가 많다면 우리 스캔이 늦다는 뜻이다.

## D9. 가속도는 합이 아니라 비율의 비율이다 (교정 2)

초안의 정의는 이렇다.

```
acceleration_ratio = 최근 30초 거래대금 ÷ 직전 30초 거래대금
```

**문제**: 이것은 **원합의 비**다. 그런데 같은 문서가 원천별 backoff를 30→60→120→300초로
규정한다. backoff가 걸리는 순간 "최근 30초"가 실제로는 90초 창이 되고, 원합은 창 길이에
비례하므로 **비율이 조용히 3배로 부풀어 오른다.** 1.8배 임계는 시장이 아니라 우리 폴링
사고에 반응하게 된다. 그리고 backoff는 예외가 아니라 이 설계가 일어난다고 보장한 일이다.

**결정**: 경과 시간으로 정규화한 **초당 거래대금의 비**로 정의한다. spec Requirement
"시간축 지표는 경과 시간으로 정규화되어야 한다"가 이미 요구하는 바와 같다.

```
recent_rate = 최근 창 거래대금 ÷ 최근 창 실제 초
prior_rate  = 직전 창 거래대금 ÷ 직전 창 실제 초
acceleration_ratio = recent_rate ÷ prior_rate
```

두 창의 **실제 길이를 함께 기록한다.** 30/30초에서 나온 1.8배와 30/90초에서 나온 1.8배를
읽는 사람이 구분할 수 있어야 한다.

`WARMING_UP`은 초안대로다 — 첫 관측에는 분모가 없고, 없는 분모로 만든 무한 가속도가 정확히
D3이 막으려는 가짜 조기 신호다. 다만 warming-up 중에도 순위 급상승은 상세조회 큐에 선등록
한다. "가속도 확인 전에는 아무것도 안 한다"로 만들면 늦은 발굴로 되돌아간다.

### 분모가 없는 경우는 하나가 아니다 (2026-07-28 리뷰)

`WARMING_UP`은 "직전 구간이 **없다**"만 가리킨다. 직전 구간이 **있는데 분모가 못 쓰는 값**인
경우가 셋 더 있고, 셋 다 결과가 `+Inf`·음수·NaN이며 셋 다 임계를 통과한다. 산출하지 않는
것이 통과가 아닌 것처럼, **못 쓰는 분모로 만든 값도 통과가 아니다.**

| 상황 | 왜 생기나 | 처리 |
|---|---|---|
| `prior_rate == 0` | 직전 30초에 체결이 없다(거래 정지, 저유동성) | 미산출 |
| 직전 구간 실제 초 == 0 | 한 스캔에서 여러 원천이 같은 순간을 보고했다 | 미산출 |
| 델타가 음수 | 거래대금은 **일중 누적**이므로 세션 경계·원천 재기동에서 뒤로 간다 | 미산출 |

미산출 사유는 `WARMING_UP`과 **구분해서 기록한다.** 전자가 많으면 원천 구성 문제이고 후자가
많으면 그냥 방금 시작한 것이라, 고쳐야 할 대상이 다르다 — D3이 `seen_late`와 `extended`를
가른 것과 같은 이유다.

### 시계열은 원천마다 따로다

`TradingValue`는 원천마다 **다른 누적**이다(단위도, 집계 창도, 우회 여부도). 두 원천의 값을
차분하면 나오는 것은 시장의 가속도가 아니라 원천 간 차이다. 그러므로 rate·가속도의 계열은
`(market, symbol, source)`이고, 저장소는 원천으로 필터링해 읽을 수 있어야 한다.

이것을 적어 두지 않으면 자연스러운 구현이 틀린 쪽이다 — `Observations(market, symbol)`이
모든 원천의 행을 시각순으로 섞어 돌려주므로, 그대로 차분하면 컴파일도 되고 그럴듯한 숫자도
나온다.

## D10. 측정하지 않은 것은 통과가 아니다 (교정 3 — 가장 중요)

`near_high`는 `day_high`를 필요로 하고, 순위 리스트는 `day_high`를 주지 않는다. 즉 이 veto는
**상세조회를 한 후보에 대해서만 계산된다.** 그런데 상세조회는 hot hint로 예산이 배분된다
(D8). 따라서 hot queue 밖의 후보는 `near_high`가 영영 계산되지 않는다.

**함정**: 그 후보들의 `near_high`가 `false`로 저장되면, **veto가 조용히 대부분의 후보에서
꺼진다.** 화면과 기록은 "추격 위험 없음"이라고 말하는데 실제로는 "확인한 적 없음"이다.
이것은 D3의 거부권을 우회하는 두 번째 경로이고, D1의 재진입 규칙이 막은 첫 번째 경로보다
찾기 어렵다 — 아무것도 실패하지 않기 때문이다.

**결정**: 세 veto는 전부 3-상태다.

```
true        측정했고 위험하다
false       측정했고 위험하지 않다
unmeasured  측정하지 못했다 — 입력이 없다
```

`unmeasured`는 **어떤 경우에도 `false`로 취급하지 않는다.** "veto를 통과했다"는 세 값이
전부 `false`일 때만 참이다. 이것은 D4의 `completeness`, D6의 파생값 표시와 같은 규칙이 veto에
적용된 것이다.

## D11. 원 관측은 무한히 쌓지 않는다 (교정 4)

`retain_all_returned_rows: true`의 부피를 계산해 둔다. KR 15초 = 장중 약 5,760 스캔/일,
원천 5개 × 100~150행이면 **일 300만 행 규모**이고 US가 더해진다. 한 달이면 1억 행이다.
15초마다 시계열 질의를 하는 로컬 SQLite에는 맞지 않는다.

**결정**: 보존을 두 층으로 나눈다.

| 층 | 내용 | 보존 |
|---|---|---|
| 원 관측 | 스캔마다의 모든 행 | 최근 N 거래일(기본 2) |
| 후보 요약 | `first_seen_at`, 임계 통과 시각, 극값, veto 이력, 원천·완전성 | 후보 만료까지 |

spec Requirement "후보 관측은 누적되고 재시작을 넘어 유지되어야 한다"와 충돌하지 않는다 —
그 요구는 **덮어쓰지 않을 것과 재시작을 넘을 것**이지 원 행을 영원히 둘 것이 아니다.
다만 이것을 명시해 두지 않으면, 나중에 누가 저장소를 "정리"하면서 `first_seen_at`을 함께
지운다. **강등 대상은 원 관측뿐이고 후보 요약은 아니다.**

### D17. 그 극값 칼럼이 실제로는 없다 (2026-07-28 §3 구현 중 발견)

위 표는 후보 요약이 **극값**을 후보 만료까지 보존한다고 적었다. `candidates` 스키마에는
그런 칼럼이 없다 — 타임스탬프·원천·카운터·`degraded`뿐이다. 그래서 `extended`의 기준선인
**최초 발견가는 오직 prunable한 `observations`에만 있다**(`DefaultRawRetention` 48시간).

결과는 D10 모양의 실패다. 48시간을 넘겨 살아 있는 후보는 `first_seen_at`을 유지한 채
**기준선만 잃는다.** 하필 **가장 오래 달린 후보 — `extended`가 가장 걸릴 만한 후보 — 에서만**
그렇게 된다. 아무것도 실패하지 않으면서.

**정정(§3 리뷰): 실제 동작은 이 문단이 예측한 것보다 나쁘다.** 여기서는 "확장률이 `false`가
아니라 미측정이 된다"고 썼는데, 구현은 **미측정이라고 말하지 않는다.** 기준선을 남아 있는
가장 이른 행으로 조용히 옮기고 `Measured: true`, `Why: ""`로 답한다.

```
prune 전: measured=true  first="10000"  gain=200.0%
prune 후: measured=true  first="20000"  gain=50.0%   ← why=""
```

3배 오른 후보가 50% 확장으로 보고된다. **틀린 숫자는 없는 숫자보다 나쁘다** — 미측정은
`extended`를 통과로 만들지 않지만(D10), 50%는 통과로 만든다.

그리고 이것은 prune을 기다리지 않는다. `SourceObservations`의 doc 주석이 권하는 `since` 창
읽기("최근 2분치만 요청")가 그대로 기준선을 옮긴다. **doc이 권하는 사용법이 결함을 만든다.**

**결정**: 최초 발견가를 후보 요약에 **칼럼으로** 둔다. `first_seen_at`과 같은 등급의 사실이고
같은 규칙을 따른다 — 재진입에 유지되고, 만료에 초기화된다(D1).

```
first_price          TEXT     -- 원천이 준 문자열 그대로. NULL은 "가격을 준 관측이 아직 없다"
first_price_at       TEXT     -- 그 관측의 시각
first_price_source   TEXT     -- 어느 원천이 줬는지
```

**기준선의 나이를 함께 남기는 것이 요점이다.** 기준선이 20분 전인 2배와 3일 전인 2배는
다른 사건이고, 값만 남기면 읽는 사람이 구분할 수 없다 — D9가 두 창의 실제 초를 함께
저장하는 것과 같은 이유다. 세션 경계로 기준선을 리셋하지는 않는다: 사흘에 걸친 3배도
추격이며, 후보 수명(무응답 40분이면 만료)이 이미 "계속 순위에 있었다"를 요구한다.

`first_price`가 NULL인 것과 0인 것은 다르다. 다른 모든 decimal과 같은 규칙이다.

#### 마이그레이션 백필은 **너무 늦은 기준선을 저장할 수 있다** (구현자 제기, Manager 판정)

기존 DB를 v2로 올릴 때 `first_price`를 살아남은 가장 이른 원 관측에서 채운다. 그 행보다 앞선
행이 이미 prune됐다면 **저장하는 값이 진짜 최초 발견가보다 늦다.** 이것은 이 문단이 막으려는
바로 그 결함을 마이그레이션 안으로 옮긴 것이다.

NULL로 두는 대안은 더 나쁘다 — 다음 스캔이 **더 늦은** 값을 기준선으로 박고, 그때는 늦었다는
표시조차 없다. 그러므로 **백필은 유지한다.**

**판정**: 늦었을 가능성을 소비자가 기억해서 유도해야 하는 것으로 두지 않는다. `first_price_at`과
`first_seen_at`이 둘 다 저장되므로 그 차이가 곧 "이 기준선은 최초 발견가가 아니다"이고,
그 차이를 **`Expansion`이 이름 붙은 값으로 나른다.**

그리고 §4가 그것을 써야 한다. **너무 늦은 기준선은 확장률을 과소평가하고, 과소평가는
`extended`를 `false` 쪽으로 민다** — veto를 끄는 방향이다. D10이 금지하는 방향 그대로다.

**결정**: 기준선이 최초 발견보다 `DefaultStalenessTTL`(10분)을 넘겨 늦으면 `extended`는
`false`가 아니라 **`unmeasured`**다. 10분 안이면 사실상 최초가로 취급한다 — 그 창은 스캔
간격과 계획된 백오프로 설명되는 범위다.

## D12. rate 예산에서 발굴이 마지막이다 (교정 5)

spec Requirement 7은 실계좌 검증에만 양보를 규정한다. 그런데 같은 계좌 예산을 쓰는 소비자는
셋이다 — **엔진(체결 감지·대사), 실계좌 검증, 발굴.** 발굴만 빠져 있으면 우선순위가 정해지지
않은 것이다.

**결정**: 순위는 엔진 > 검증 > 발굴이다. 발굴은 읽기 전용이므로 늦어도 **돈이 걸리지 않는
유일한 소비자**다. 체결 감지가 느려지는 것은 손절의 즉시성 문제이므로 안전 불변식 4에 닿는다.

위상 분산은 초안의 5초가 아니라 주기의 절반으로 둔다. KR 스캔이 5초 안에 안 끝나면 5초
오프셋은 겹침을 막지 못하고, 원천 5개를 도는 스캔이 5초 안에 끝난다는 근거가 없다.

```
KR: 00, 15, 30, 45초
US: 07, 22, 37, 52초
```

## D13. 간격은 시장이 아니라 원천에 붙는다 (교정 6, 2026-07-28)

초안은 간격을 시장으로 갈랐다(KR 15초·US 30초). 그런데 실제 제약은 시장이 아니라 **원천**에
있고, 원천 간 차이가 자릿수 단위다.

| 원천 | 한도 | 근거 |
|---|---|---|
| WTS 랭킹·투자자·테마·스크리너 | **사실상 없음** | [open-api.md:50](../../../docs/migration/open-api.md) |
| 공식 `GET /api/v1/rankings` | **미상** — `RANKING` 그룹이 공식 한도표에 없다 | 표는 10그룹, spec의 endpoint는 14개 그룹명을 쓴다 |
| 공식 `GET /api/v1/prices` | 초당 10회 × **호출당 200종목** | `MARKET_DATA` |
| 공식 `GET /api/v1/candles` | 초당 5회, **종목당 1회** | `MARKET_DATA_CHART` |

**결정 1 — 간격을 원천별로 나눈다.** WTS는 기본 5초(하한 3초), 공식 랭킹은 측정 전까지
15초를 유지한다. 시장별 간격은 없앤다. US가 KR보다 느려야 할 이유는 원천 구성이 다르다는
것뿐이고, 그것은 원천별 간격이 이미 표현한다.

**결정 2 — 공식 한도는 추측하지 않고 측정한다.** 응답은 `X-RateLimit-Limit`·`Remaining`·
`Reset`으로 현재 예산을 매번 알려주는데, 지금 코드는 이 헤더를 **어디서도 읽지 않는다**
(`Retry-After`만 429에서 처리한다). 즉 예산을 429가 터질 때에야 알게 된다 — 정확히 늦은
시점이다. 이 change는 첫날부터 이 세 헤더를 스캔 결과에 기록한다. 그러면 `RANKING`의 실제
한도는 다음 결정 때 **추정이 아니라 관측**이 된다. 레인 임계·D8과 같은 처리다.

**결정 3 — 간격을 줄여도 조기성의 병목은 랭킹이 아니다.** 일중 고가는 `prices`에 없고
(`lastPrice`뿐) 종목당 1회인 `candles`에서만 나온다. 초당 5회면 15초 주기에 최대 75종목이다.
후보가 수백이면 **대다수가 `near_high` 미측정**이라는 뜻이고, 이것이 D10을 이론이 아니라
평시 동작으로 만든다. 랭킹 폴링을 3배 빠르게 해도 이 병목은 그대로다.

**하지 않는 것 — 1초로 내리지 않는다.** "사실상 없음"은 대화형 CLI 사용에서 나온 관찰이지,
장중 6.5시간 지속 폴링에 대한 측정이 아니다. 5초 × 6.5시간 × 원천 5개면 하루 2만 건 규모로
트래픽 성격이 다르다. WTS 세션은 tossctl 나머지가 함께 쓰므로 **세션을 잃는 비용이 몇 초의
조기성보다 크다.** 조여 오는 신호가 보이면 즉시 물러난다.

**주의 — 빠른 폴링이 가속도를 빨리 만들지는 않는다.** `minimum_history_seconds: 60`은
그대로다. 30초 창 두 개를 채우는 데 필요한 것은 표본 수가 아니라 **벽시계 시간**이다.
5초 폴링이 주는 것은 더 이른 가속도가 아니라 **창 경계의 정확도**(±15초 → ±5초)와
`first_seen_at`의 해상도다. 후자가 이 change의 본체다.

## D14. 자동 우회는 성공이 아니라 강등이다 — 단, 랭킹에는 우회가 없다 (교정 7, 2026-07-28 정정)

**최초 서술이 틀렸다.** 이 절은 원래 "공식이 429면 hybrid가 자동으로 WTS로 우회하므로 발굴이
조용히 강등된다"고 썼다. [hybrid/client.go:75](../../../internal/hybrid/client.go)의
`route()`만 보고 쓴 것이고, **어느 메서드가 그 경로를 지나는지 확인하지 않았다.**

실제로는 이렇다([hybrid/client.go:185-220](../../../internal/hybrid/client.go)).

| 메서드 | 우회 | 코드의 말 |
|---|---|---|
| `Rankings` | **없음** | "official-only: no WTS fallback (WTS 인기 순위는 다른 데이터셋)" |
| `MarketIndicatorPrices`·`MarketIndicatorCandles`·`MarketInvestorTrading` | **없음** | "official-only (see Rankings)" |
| `Prices`·`Accounts` 계열 | 있음 | `route()`를 지난다 |

즉 발굴의 **주 원천인 랭킹·캔들에는 우회가 아예 없다.** 키가 없으면 `ErrOfficialKeyRequired`,
429면 그대로 실패다.

**그래서 위험이 사라진 것이 아니라 뒤집힌다.**

- 원래 걱정: 우회 때문에 *아무것도 실패하지 않아서* 과도 폴링을 모른다 → `official_prices`
  에만 해당한다.
- 실제 걱정: 랭킹은 429 한 번에 **원천이 통째로 사라진다.** 그런데 spec Requirement 5는
  "공식 Open API 원천만으로도 후보가 산출되는 구성"을 요구한다. **혼자서도 충분해야 하는
  바로 그 원천이 이중화가 없는 원천이다.** WTS 인기 순위는 대체재가 아니다 — hybrid 자신의
  주석이 다른 데이터셋이라고 말한다.

**결정 1**: `ViaFallback` 기록은 유지하되 적용 범위를 `official_prices`로 한정한다. 랭킹·캔들
관측에 이 값이 참으로 찍히면 그것은 우회가 아니라 **버그**이므로, 그렇게 읽어야 한다.

**결정 2**: 랭킹의 429는 강등이 아니라 **결손**으로 기록한다. D4의 `completeness`가 이미
그 자리다 — 시도 5, 응답 4, 빠진 원천 이름. 우회율이 아니라 **결손율**이 `RANKING` 한도를
역산하는 재료가 된다.

**결정 3**: 그래서 D13 결정 2(rate 헤더 기록)의 중요도가 올라간다. 우회라는 완충재가 없으므로
429는 곧 원천 상실이고, 예산 잔량을 미리 못 보면 그 상실을 **사후에만** 알게 된다.

**남는 교훈은 그대로다.** D10과 같은 실패 모양 — 시스템이 계속 동작하면서 자기가 하는 일을
조용히 바꾸는 것 — 은 `official_prices`에 여전히 존재하고, 답도 그대로 D4다. 바뀐 것은
그 답이 적용되는 원천의 목록이다.

## D15. rate 헤더를 읽으려면 누군가는 손대야 한다 (2026-07-28 리뷰)

D13 결정 2는 `X-RateLimit-Limit`·`Remaining`·`Reset`을 첫날부터 기록하겠다고 했고,
proposal의 Impact는 "`internal/official` … 기존 계약 그대로, **수정 없음**"이라고 했다.
**둘 다 참일 수 없다.**

- 저장소 전체에서 `X-RateLimit` 문자열은 **0건**이다.
- `internal/official`은 429를 sentinel error로 바꾸면서 **응답 헤더를 버린다**
  ([execgw/retry.go:183](../../../internal/execgw/retry.go)가 자기 존재 이유로 그렇게 적어 뒀다).
- 헤더가 살아남는 유일한 자리는 RoundTripper이고, 지금 있는 것은 `execgw.RetryAfterTransport`인데
  `internal/execgw`는 주문 경로라 D7·spec Requirement 6이 import를 금지한다.

**결정**: `internal/official`에 **읽기 전용 헤더 노출을 추가**한다. 세 선택지 중 유일하게
새 중복을 만들지 않는 쪽이다.

| 선택지 | 비용 |
|---|---|
| **`internal/official`에 헤더 노출 추가** ← 채택 | Impact 문구 수정. 기존 호출자 무영향(추가만) |
| RoundTripper를 발굴에 심는다 | `internal/execgw` import — spec Requirement 6 위반 |
| transport를 `internal/candidate`에 복사 | fsguard에 이은 **두 번째** 복사. 표류 감시 대상이 하나 더 |

추가는 **순수 가산**이다 — 응답의 마지막 rate 헤더를 클라이언트에 보관하고 읽는 접근자 하나.
기존 메서드의 시그니처·동작·에러는 바뀌지 않으므로 엔진·검증 경로에 영향이 없다. proposal의
Impact 줄을 "`internal/official`: 헤더 노출 **추가**(가산, 기존 계약 무변경)"로 고친다.

같은 결정이 task 5.4의 429 백오프에도 적용된다 — `Retry-After` 역시 같은 자리에서 버려진다.

## D16. 발굴이 원장을 굶길 수 있다 (2026-07-28 리뷰)

D2는 **락**의 방향을 옳게 잡았다 — 발굴이 원장 락을 잡으면 안 된다. **바이트**에 대해서는
같은 질문을 하지 않았다.

D11이 부피를 계산해 뒀다: 일 300만 행, 13개 컬럼 + 인덱스 2개면 **하루 1GB 규모**다. 그리고
저장소는 `journal.db`와 **같은 디렉터리**, 따라서 **같은 파일시스템**에 있다(원장의 데이터
디렉터리 규칙을 그대로 따르므로 의도된 배치다).

그 파일시스템이 차면 **원장의 쓰기가 ENOSPC로 실패한다.** 원장은 주문·체결·대사의 기록이고
`.claude/CLAUDE.md`가 High-risk로 지정한 경로다. 관측 기능이 실행 기록을 굶기는 것은 D2가
락에서 지적한 "방향이 거꾸로"와 같은 일이며, 이번에는 안전 불변식에 닿는다.

세 가지가 계산보다 상황을 나쁘게 만든다.

1. **아무도 정리를 부르지 않는다.** `PruneObservations`·`PruneStale`은 존재하는 API일 뿐
   돌아가는 정책이 아니다. 지금 기본 동작은 **무한 증가**다.
2. **WAL은 오래 열린 독자가 있으면 체크포인트되지 않는다.** 콘솔 `/signals` 화면이 정확히
   그런 독자다. 테이블 위에 `-wal`이 따로 자란다.
3. `raw_observation_retention_days: 2`는 YAML의 숫자일 뿐 강제하는 Requirement가 없었다.

**결정**:

- 보존은 **스캔이 스스로 집행한다.** 정리는 옵션이 아니라 스캔 주기의 일부다.
- 여유 공간 하한을 둔다. 그 아래로 내려가면 **발굴이 먼저 쓰기를 멈추고 말한다.** 실패해야
  하는 쪽은 언제나 발굴이고, 절대 원장이 아니다.
- WAL 체크포인트를 정리와 함께 돌린다.

### 레인별 임계는 이 change가 쓰지 않는다

초안의 레인 표(Opening fast 1.8배, Breakout 1.5배·2% veto 면제, Pullback/Retest 1.3배 …)는
**T3.2의 입력으로 보존**하고 여기서 구현하지 않는다. 이 change의 Non-Goals가 전략 레인을
명시적으로 뺐고, 레인 승격은 곧 진입 판정이기 때문이다.

빼는 것이 손해가 아닌 이유: 초안 스스로 이 숫자들을 추정값이라고 말한다("실제 판단은 정책값
하나만, 나머지는 비교 분석용"). 그런데 이 change가 **5개 임계 통과 여부와 순위 백분위 변화,
고점 거리, veto 3-상태를 전부 기록**하면, T3.2가 착수할 때 레인 임계는 지금 **단언**하는
대신 쌓인 실데이터에서 **도출**할 수 있다. Breakout 레인이 2% veto를 면제받아야 한다는
판단도 그때 기록으로 확인된다.
