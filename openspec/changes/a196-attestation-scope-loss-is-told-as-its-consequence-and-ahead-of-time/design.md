# a196 Design

## 1. 결정

| # | 결정 | 근거 |
|---|---|---|
| D1 | 감독 증거의 기한 = `ProofAt + (ExpiresAt − IssuedAt)`. `ProofAt` 은 기존 `binding` 의 값(endpoint 별 최신 증거 중 가장 이른 것). `ProofAt` 이 0(증거 없음)이거나 `ExpiresAt ≤ IssuedAt` 이면 감독 증거의 기한은 없다 — 만료만 센다 | 파일 안의 값만 쓴다. 엔진이 `internal/soak` 를 import 하지 않고, 30 일이라는 숫자를 복사하지도 않는다 |
| D2 | 「수용 기간 = attestation 유효 기간」이라는 전제는 시험이 고정한다: 발급 함수(`soak.BuildAttestation` 계열)에 유효 기간 직전·직후의 감독 증거를 넣어 직전은 실리고 직후는 빠짐을 보고, 실린 파일로 계산한 기한이 「그 증거가 빠지기 시작하는 시각」과 같음을 단언한다. 시험이 놓일 패키지는 import 순환이 없는 쪽(tasks 1.4 에서 확인) | 「우연이 지키는 안전」을 못 박는다 — 발급자가 두 값을 갈라 쓰기 시작하면 이 시험이 먼저 깨진다 |
| D3 | 날수의 기준 = `min(만료, 감독 증거의 기한)` 까지 남은 시간의 하루 단위 올림(기존 `daysLeftCeil`). 남은 시간이 0 이하(기한은 지났는데 아직 갱신 전이라 파일은 통과)면 임박 단계(critical)다 | 갱신이 성공하면 그 구간은 최대 6 시간이고 다음 갱신이 범위 상실로 바꾼다. AST: 갱신이 실패하면 파일을 쓰지 않으므로(runSoakAttest — BuildAttestation 오류에서 return, `attest.Save` 미도달) 그 구간은 그 파일의 만료까지 이어질 수 있다(`Verify` 는 감독 증거 나이를 보지 않음) — 1.6 리뷰 정정. 그 구간의 날수·키 처리는 Manager 결정 대기(review.md Q4) |
| D4 | 날수 단계의 신원 = **기한의 시각**(파일의 발급·만료 시각이 아님). 만료가 기한이면 종전과 같은 동작이다(갱신이 만료를 바꾸므로 새로 센다). 감독 증거가 기한이면 갱신을 넘겨 같은 단계가 유지된다 | 감독 증거의 기한은 갱신으로 바뀌지 않는다 — 파일 신원으로 세면 6 시간마다 같은 통지가 다시 나간다 |
| D5 | 거절 단계의 신원 = 단계 + (범위 상실이면 정렬된 누락 endpoint 집합) + KST 날짜. 발급 신원을 뺀다. outbox key 도 같은 신원으로 만든다 | 정본의 의도 「하루 한 번」. 2026-11-18~23 의 21 건이 5~6 건이 된다 |
| D6 | 타입은 `broker.credential_expiring` 그대로. 제목·본문만 고친다 | 새 타입은 `internal/obs` 열거·등급표·정본 문구·a102/a134 유일성 시험을 건드린다(조사 인용). 운영자가 먼저 읽는 것은 제목이다 |
| D7 | 문장(확정 문구는 구현에서, 뜻은 고정): 범위 상실 제목 「지금 엔진을 재시작하면 기동이 거부된다 — 주문·취소 검증이 attestation 에 없다」. 본문: 빠진 endpoint 이름 / 재시작이 거부되면 자동 손절·익절이 돌지 않는다 / 지금 도는 엔진은 계속 돈다 / 할 일: 터미널에서 `tossctl verify run` 으로 감독하 실주문 검증을 다시 하고 갱신(다음 타이머 또는 `tossctl soak attest`)을 기다린다. 날수 통지: 「감독하 실주문 검증이 N 일 뒤(<시각>) 만료된다. 그 뒤 첫 갱신부터 엔진 재시작이 거부된다」 + 같은 할 일 | 2026-11-23 사고에서 빠져 있던 세 가지(결과의 단정·원인·할 일) |
| D8 | 계좌 정보·파일 경로·원문 오류 금지, 알림 꺼진 엔진의 일반 등급 강등, 판정 결함 회수·알림기 패닉 비회수 — 전부 기존 규칙 그대로 | 정본 그대로 |

## 2. 편집 자리

- `judgeAttestation`: Verify 통과 뒤 `DaysLeft` 계산의 기준 시각을 새 함수(`restartDeadline(verdict) (time.Time, kind)`)의 값으로 바꾸고, verdict 에 기한의 종류·시각을 싣는다.
- `stageKey` / `prepare`: 신원 계산(D4·D5).
- `eventFor`: 제목·본문·key.
- 새 함수(기한 계산, 문장 조립)는 같은 파일의 새 함수 또는 새 파일. 기존 함수 수정 수를 tasks 1.4 에서 세고 번들을 만든다.

## 3. 침묵·거절하는 정상 입력

- 감독 증거가 실리지 않은 attestation(게이트가 조회만 요구하는 구성이 있다면): 감독 증거의 기한 없음 → 종전 동작.
- 게이트가 꺼진 엔진: attestation 을 읽지 않는다(정본 그대로).

## 4. 운영 절차 (코드 밖, 사람 승인)

1. 엔진 생존 감시 타이머 설치: `deploy/systemd/tossos-heartbeat.{service,timer}` 를 사용자 systemd 에 설치·활성(`systemctl --user enable --now tossos-heartbeat.timer`). 엔진이 죽으면 엔진과 무관하게 1 분 안에 알림이 간다. 2026-11-23 미설치 확인.
2. 감독하 실주문 검증의 재실행과 엔진 재기동(2026-11-23 사고 복구) — 이 change 와 독립.

## 5. 시험 전략 (RED 먼저)

새 시험 파일 `internal/app/engine/a196_attestation_deadline_internal_test.go`(a135 시험의 하네스·가짜 시계 재사용):

1. 만료 30 일 뒤·감독 증거 기한 7 일 뒤 → 일반 등급 1, 본문에 감독 증거 기한과 `verify run`. 8 일 뒤(7 일 1 초) → 0.
2. 같은 날 같은 감독 증거를 실은 새 발급 파일로 바뀌어도 추가 알림 0. 다음 날(D-6) 1.
3. 감독 증거 기한 2 일·1 일 → critical 각 1. 기한이 지났고 파일은 아직 통과 → critical(임박).
4. 새 감독 증거로 기한이 30 일 뒤 → 0, 그 뒤 새 기한으로 다시 셈.
5. 감독 증거 없음 → 만료만 센다(a135 시험과 같은 결과).
6. 범위 상실: 첫 판정 critical 1, 같은 날 같은 누락으로 재발급 2 회 → 0, 다음 날 → 1. 누락 집합이 바뀌면(하나 더 빠짐) 같은 날 1.
7. 범위 상실 제목에 「재시작」「거부」가 있고 조건 접속(「…하면 …할 수 있다」류) 없이 단정이며, 본문에 빠진 endpoint·손절·`tossctl verify run`.
8. 제목·본문·필드·key 에 계좌 원문·숫자열·마스크 꼴 0(기존 누출 시험 형식).
9. 알림 꺼진 엔진 → 일반 등급 기록만.
10. D2 의 전제 고정 시험(발급 함수 경유).
11. 기존 a135 시험 전부 통과 — 깨지는 단언은 「파일이 바뀌면 새로 센다」를 거절 단계에 대해 단언하는 것뿐이어야 하고, 그 시험 함수는 번들과 함께 고친다(몇 개인지 tasks 1.4).

변이(전부 CAUGHT): 기한을 만료로만 계산 · `min` 을 `max` 로 · 날수 신원에 발급 시각 되돌리기 · 거절 key 에 발급 신원 되돌리기 · 누락 집합을 key 에서 빼기 · D-2 경계 한 칸 밀기.

선택 시험: `./internal/app/engine -run 'A196|A135|Attestation'`, D2 시험이 놓인 패키지의 해당 시험.

## 6. 잔여

- 타입 태그 `broker.credential_expiring` 은 남는다(D6). 운영자가 태그로 걸러 읽는다면 여전히 「자격 만료」로 보인다.
- 엔진이 꺼져 있으면 이 감시도 돌지 않는다 — §4-1 의 타이머가 그 구간을 맡는다.
