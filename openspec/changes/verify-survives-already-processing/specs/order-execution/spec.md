# order-execution Specification (delta)

## MODIFIED Requirements

### Requirement: 취소의 일시적 거절 처리

브로커가 **취소 또는 정정**을 일시적 사유로 거절하면 그 요청은 유한 재시도해야 한다(SHALL).
일시적 거절의 실측 형태는 HTTP 409 `already-processing` + `data.retryAfterSeconds`이며
취소(M16)와 정정(M24) 양쪽에서 관측됐다.
대기는 브로커가 제시한 `retryAfterSeconds`를 따르되 상한을 둔다(SHALL — 현행 5초). 재시도
횟수에는 상한이 있어야 한다(SHALL — 현행 추가 2회). 재시도가 모두 실패하면 실패로 기록하고
잔여 객체를 보고한다(SHALL — 조용히 성공으로 만들지 않는다).

이 재시도는 **취소와 정정에만** 적용된다(SHALL NOT — 주문 접수·조건주문 생성의 자동 재시도는
계속 금지된다). 근거: 취소는 노출을 줄이고, 정정은 이 도구에서 체결 불가 지정가를 시장에서
한 호가 더 멀리 옮기는 것이며, 둘 다 **생성 연산이 아니다** — 반복해도 두 번째 주문이 생길 수
없다. 접수와 조건주문 생성은 반복하면 생길 수 있으므로 금지가 유지된다. 재시도 사실과 횟수는
관측 기록에 남겨야 한다(SHALL — 재시도로 성공한 요청을 첫 시도 성공으로 표시해서는 안 된다
(SHALL NOT)).

재시도 판정은 HTTP 상태와 **본문의 오류 코드가 모두 일치할 때만** 참이어야 한다(SHALL) —
다른 사유의 409를 재시도 루프로 만들지 않는다.

#### Scenario: 일시적 거절 후 성공

- **WHEN** 취소 또는 정정이 `already-processing`으로 거절되고 재시도가 성공하면
- **THEN** 요청은 처리되고, 기록에는 재시도가 있었다는 사실과 횟수가 남는다

#### Scenario: 재시도 상한 소진

- **WHEN** 상한까지 재시도해도 계속 거절되면
- **THEN** 실패로 기록되고 그 객체가 살아 있다는 사실이 보고된다

#### Scenario: 접수·조건주문 생성은 재시도하지 않는다

- **WHEN** 주문 접수나 조건주문 생성이 실패하면
- **THEN** 자동 재시도는 일어나지 않는다

## ADDED Requirements

### Requirement: 실패한 단계도 자기 산출물을 정리한다

검증 단계가 오류로 끝나더라도 그 단계가 만든 미취소 주문은 같은 실행 안에서 취소해야 한다(SHALL).
성공 경로에서만 정리하고 실패 경로에서 빠져나가서는 안 된다(SHALL NOT) — 그렇게 하면 실패할
때마다 잔여물이 하나씩 쌓이고, 그것이 노출 상한을 채워 뒤따르는 단계를 연쇄로 막는다
(measurements.md M24 실측).

정리는 다른 모든 라이브 요청과 같은 게이트를 지나야 한다(SHALL) — 승인된 계획에 그 단계의
취소 줄이 없으면 전송되지 않는다(SHALL NOT). 계획 밖 요청으로 실행이 멈춘 경우와 컨텍스트가
취소된 경우에는 정리를 시도하지 않는다(SHALL NOT) — 그때는 아무것도 보내지 않는 것이 규칙이다.

#### Scenario: 정정이 실패해도 그 단계의 주문은 남지 않는다

- **WHEN** 정정이 상한까지 재시도해도 거절되면
- **THEN** 그 단계가 접수한 주문은 취소되고, 뒤따르는 단계는 노출 상한에 걸리지 않는다

#### Scenario: 계획 밖 요청으로 멈춘 실행은 정리도 보내지 않는다

- **WHEN** 단계가 승인된 계획에 없는 요청을 보내려다 실행이 멈추면
- **THEN** 정리 취소도 전송되지 않고 그 객체는 잔여물로 보고된다
