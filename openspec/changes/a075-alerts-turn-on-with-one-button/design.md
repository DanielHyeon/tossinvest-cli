# a075 · Design

## D1 — 채널 주소는 운영자가 고르지 않는다

ntfy.sh에서 topic 이름은 유일한 접근 제어다. 운영자에게 입력란을 주면 대부분
`tossos`, `myaccount`, 계좌 별명 같은 것을 쓴다. 그것은 계좌 이벤트를 공개하는
것과 같다.

그래서 **입력란이 없다.** 버튼을 누르면 `crypto/rand`가 16바이트를 뽑고,
base32(소문자·padding 없음)로 접두어와 함께 조립한다.

```
tossos-<26자 base32>          128비트
```

접두어를 붙이는 이유는 하나다: 운영자가 ntfy 앱의 구독 목록에서 이것이 무엇인지
알아볼 수 있어야 한다. 접두어는 엔트로피가 아니고 엔트로피인 척하지도 않는다.

**나쁜 topic을 고르는 경로를 없애는 것**이 이 설계 결정의 전부다. 검증으로
막을 수도 있었지만, 검증은 "이 이름은 왜 거부되나"를 설명해야 하고 그 설명은
결국 "충분히 무작위여야 한다"이며, 그렇다면 처음부터 기계가 뽑는 것이 맞다.

## D2 — 토큰은 화면에 나타나지 않는다

a074는 `config.Notifications`에 토큰 필드를 만들지 않았다. 이유는 구조적이었다 —
"설정 파일에 토큰을 써도 착지할 자리가 없다."

같은 논리를 화면에 적용한다. 입력란이 없으면 붙여넣을 수 없다. self-hosted ntfy를
쓰는 운영자의 경로(`TOSSCTL_NTFY_TOKEN` 환경변수)는 a074 그대로 살아 있고, 화면은
그 사실을 **읽는 문장으로** 안내한다. 화면이 그 값을 받지는 않는다.

카드는 토큰이 설정되었는지 **여부도** 표시하지 않는다. 콘솔 프로세스의 환경과 엔진
프로세스의 환경은 다를 수 있고(컨테이너·systemd unit이 다르다), 콘솔이 자기 환경을
보고 "토큰 있음"이라고 말하면 그것은 엔진에 대한 거짓이 된다. 콘솔은 자기가 아는
것만 말한다: 파일에 무엇이 쓰였는가.

## D3 — 저장은 기존 splice 경로를 그대로 쓴다

`internal/config`에는 이미 확립된 규율이 있다 (limits_io.go가 세우고 operating_io.go가
이어받은 것): **한 저장은 자기 대상 키의 바이트만 다시 쓴다.** 블록 전체를 re-emit하면
flock 밖의 read가 stale일 때 다른 키를 되돌린다.

알림 저장도 닫힌 멤버 목록을 갖는다.

```
notificationMembersOf   enabled, base_url, topic      (a075)
```

세 키. `rejected`는 없다 — 그것은 파서가 붙이는 진단이지 운영자가 쓰는 설정이
아니며, 저장이 그것을 emit하면 다음 로드가 자기 자신의 진단을 설정으로 읽는다.

끄기(`Disable`)는 `enabled` **한 키만** 다시 쓴다. topic을 지우지 않는 것은
의도적이다 — 지우면 다시 켤 때 새 주소가 생기고 운영자의 폰 구독이 죽는다.
a074의 `resolveNotificationPublisher`는 `enabled=false`이면 topic이 남아 있어도
publisher를 만들지 않으므로("설정 파일에 남은 topic이 알림을 다시 켜지 않는다"),
남겨 두는 것이 안전하다.

## D4 — 테스트 발송은 콘솔이 직접 한다. outbox를 거치지 않는다

콘솔은 엔진과 **다른 프로세스**다. 설정을 저장해도 가동 중인 엔진은 기동 시점
설정으로 계속 동작한다 (`effectNotice`가 모든 카드에 쓰는 문장). 그러면 운영자는
"켰는데 도착하나?"를 엔진 재시작 전까지 알 수 없다.

테스트 발송이 그 간극을 메운다. 콘솔이 `obs.Ntfy`를 하나 만들어 한 통 publish한다.

이것이 건드리지 않는 것:

- **outbox** — `EnqueueAlert`을 호출하지 않는다. 테스트 메시지는 critical 이벤트가
  아니고, outbox 행이 되면 `event_key` 중복 억제와 entry gate latch의 대상이 된다.
- **entry gate** — 발송 실패는 latch하지 않는다. 화면에 실패 사유를 그대로 쓴다.
- **operating mode** — 승격도 강등도 없다.

테스트가 증명하는 것은 정확히 하나다: **이 주소로 지금 이 기계에서 메시지가
나간다.** 엔진이 같은 것을 할 수 있는지는 엔진의 환경(네트워크·토큰)에 달렸고,
화면은 그 구분을 문장으로 밝힌다.

## D5 — 채널 주소는 notice에 실리지 않는다

`redirectSettings`는 결과 문장을 **URL 쿼리 파라미터**로 되돌린다.

```go
c.redirectSettings(w, r, "알림 켜짐 — …")   // → /settings/tools?notice=…&form=notifications
```

URL은 브라우저 히스토리에 남고, 프록시·리버스프록시 로그에 남을 수 있다. 그래서
notice 문장에 채널 주소를 넣지 않는다. 주소는 카드 본문이 `Load()`의 결과에서
렌더한다 — 서버가 응답 본문에 직접 쓰는 것이지 URL을 경유하지 않는다.

이것은 a074가 audit에 대해 내린 결정과 같은 규칙의 다른 적용면이다.

## D6 — 카드는 어느 탭에 있는가: 도구

a055의 분류는 **가역성과 빈도**다.

| 탭 | 뜻 | 알림이 여기인가 |
|---|---|---|
| 상시 | 비가역 · 주 1회 미만 · 사람이 승인 | 아니다 — 알림은 가역이다 |
| 당일 | 가역 · 일 단위 조절 | 아니다 — 매일 만지는 것이 아니다 |
| 도구 | 진단과 유지보수 · 드물게 · 열면 상태부터 읽는다 | **그렇다** |

한 번 켜고 다시 열지 않는 설정이며, 열었을 때 가장 먼저 읽어야 하는 것이 상태
("지금 켜져 있나, 어디로 가나")다. 도구 탭의 계약이 그대로 맞는다.

## D7 — seam은 넷이고, 그 넷이 콘솔이 가진 능력의 전부다

```go
type NotificationSettings interface {
	Load() (config.Notifications, error)  // 파일이 쓴 대로
	Enable() (config.Notifications, error) // 없으면 채널 생성 + 저장 + audit
	Disable() error                        // enabled 한 키
	Test(context.Context) error            // 한 통 발송
}
```

`Enable`이 값을 받지 않는 것이 핵심이다. 콘솔은 **무엇을 쓸지 결정하지 않는다** —
누를 수 있을 뿐이고, 무엇이 쓰이는지는 seam의 구현(`cmd/tossctl`)이 안다. 그래서
`internal/console`은 `crypto/rand`도, `config.Service`도, `obs.Ntfy`도, `audit.Log`도
이름조차 부르지 않는다. 기존 정적 검사
(`TestTheConsoleNeverNamesTheConfigService`, `TestTheConsoleWritesNothingButThe…`)가
그것을 이미 강제하고 있고, a075는 그 규율 안에 들어간다.

`Enable`이 자기가 쓴 것을 **반환하는** 이유는 화면이 구독 주소를 즉시 보여줘야
하기 때문이다. 저장 후 다시 `Load()`하면 될 것 같지만, 그 사이의 실패는 "저장은
됐는데 주소를 모르겠다"가 되어 운영자가 손댈 수 없는 상태가 된다.

## D8 — 실패 방향

| 실패 | 결과 |
|---|---|
| seam 미배선 | 카드가 사유를 렌더하고 버튼을 렌더하지 않는다 (기존 `cardGuard` 규율) |
| 설정 파일 읽기 실패 | 카드가 사유를 렌더하고 버튼을 렌더하지 않는다 |
| 저장 실패 | 아무것도 바뀌지 않는다. notice가 사유를 그대로 쓴다 |
| audit 기록 실패 | 저장은 유지된다 (기존 `recordGateFlip`·`recordLimitSave`의 best-effort 규율과 동일) |
| 테스트 발송 실패 | **설정은 그대로 켜진 채로 남는다.** 발송 실패는 설정 실패가 아니다 — 네트워크가 잠깐 끊긴 것일 수 있고, 되돌리면 운영자가 방금 만든 주소를 잃는다. 화면이 실패 사유를 쓰고 [테스트 한 통 더] 버튼이 남는다 |

마지막 줄이 이 change에서 가장 미묘한 판단이다. "테스트가 실패하면 켜지 않는다"가
더 안전해 보이지만, 그러면 알림 설정의 성공 여부가 **그 순간의 네트워크**에 달리게
된다. 알림이 꺼진 상태가 지금의 결함이고, 일시적 실패로 그 상태에 머무는 것이
더 나쁘다. a074의 A7과 같은 논거다.
