# a082 · Issues

작업 중 확인한 사실 중 이 change가 고치지 않는 것, 또는 다른 곳에 남는 것.

## I1 — `send()`는 401에만 재시도하고 403에는 안 한다

```go
// internal/official/client.go:329
if code == http.StatusUnauthorized {
	tok, err = c.tm.refresh(ctx)
```

그런데 `classifyStatus`는 **401과 403을 같이** 인증 거부로 친다. 브로커가 낡은
토큰에 403을 준다면 재시도가 아예 없고, 이 change의 채택 갈래에 **닿지도 않는다**.

지금 고치지 않는 이유는 브로커가 실제로 무엇을 주는지 모르기 때문이다. 재시도
의미를 근거 없이 넓히는 것은 안전 방향이 아니다 — 403은 "이 자격증명으로는 안
된다"일 수도 있고, 그때 재시도는 무의미한 호출을 늘린다.

**이 change의 상태 코드 수정이 그 근거를 만든다.** 배포 뒤 로그에 401만 나오면
현재 설계로 충분하고, 403이 나오면 후속 change에서 403 재시도를 논증해야 한다.
task 6.7의 실측이 이 질문에 답한다.

**배포 후 추가 (2026-08-05): 답이 안 나왔다.** 상태 코드는 오류가 로그까지
올라와야 보이는데, `send()`의 재시도가 성공해서 올라오지 않는다. 배포 후 900초
동안 거부는 최소 18번 있었지만(교환 18회) `authentication failed`는 한 줄도 더
안 나왔다. 즉 **재시도가 삼키는 거부는 관측 불가**다. 이 질문에 답하려면 재시도가
구해낸 거부도 남기는 후속 작업이 필요하다 — I12와 같은 곳을 가리킨다.

## I2 — 세 프로세스가 config 디렉터리 하나를 공유하는 구조 자체

```
tossos-tossos-1   PID 7   console
tossos-tossos-1   PID 16  engine run
tossos-httpapi-1  PID 7   httpapi
```

셋 다 `/var/lib/tossos/config`를 본다. 토큰 캐시는 그중 하나일 뿐이다. 같은
디렉터리에 `openapi-credentials.json`, `engine.lock`, `engine-run.json`,
`config.json`, `performance.db`가 있다.

이 change는 토큰 파일만 고친다. **다른 공유 파일에 같은 형태의 가정이 있는지는
확인하지 않았다.** `config.json`은 `adoption_flock_unix.go`가 flock으로 직렬화하고
`engine.lock`은 `enginelock`이 쓰므로 그 둘은 의식적으로 다뤄져 있다. 나머지는
별도로 볼 일이다.

## I3 — 브로커가 토큰 하나만 살려 둔다는 것은 추론이다

직접 문서로 확인한 사실이 아니다. 근거는 관측의 유일한 정합적 설명이라는 것이다 —
옛 토큰이 계속 유효하면 401이 없고, 401이 없으면 `refresh()`가 안 불리고, 그러면
`saveCache`의 유일한 호출자인 `exchange()`가 안 돌고, 24시간 토큰의 캐시 파일이
1분에 7번 다시 쓰일 수 없다.

이 change의 수정은 그 추론이 틀려도 해롭지 않다. 토큰이 서로를 안 죽인다면 401이
안 나고 채택 갈래는 그냥 안 돌 뿐이다. 다만 **왜 고쳤는지에 대한 설명**은 그때
틀린 것이 되므로, 배포 실측(6.7)에서 교환 횟수가 안 떨어지면 이 항목을 먼저 다시
읽어야 한다.

**배포 후 추가 (2026-08-05): 떨어졌다.** 1분 6.3회 → 1.2회. 채택 갈래가 실제로
돌았다는 뜻이고, 따라서 "토큰이 서로를 죽인다"는 추론은 실측으로 지지된다. 다만
0회가 아니므로 그 추론이 **전부**를 설명하지는 못한다 — I12.

## I4 — `saveCache`는 best-effort이고 아무도 실패를 보고하지 않는다

```go
_ = m.saveCache(ct) // best-effort; do not fail the call if disk write fails
```

쓰기가 실패하면 이 보유자는 브로커가 아는 토큰을 메모리에만 갖고, 파일에는 옛
토큰이 남는다. 다른 보유자들은 그 옛 토큰을 계속 쓰다가 거부당하고, 채택하려고
파일을 봐도 거기엔 죽은 토큰뿐이라 각자 교환한다 — 수렴이 느려진다.

**초안의 이 항목은 틀렸었다.** 리뷰어가 지적했다: 철회된 mtime 확인이 있었을 때
`stampCacheFile()`이 살아남은 옛 파일의 mtime을 찍으므로 새 토큰이 오히려
유지됐다. 지금은 그 메커니즘 자체가 없으므로 위 문단이 실제 동작이다.

이 change는 best-effort 계약을 바꾸지 않는다. 쓰기 실패를 **아무도 보고하지
않는다**는 것이 원래 성질이고, 그것이 관측되지 않는 한 이 결함군은 다시 조용히
자란다. 후속 대상이다.

## I5 — 기존 테스트 1건을 고쳤다

`orders_raw_test.go:TestRawReadsClassifyErrorsLikeEveryOtherRead`가 판정을
`err == ErrAuth`로 하고 있었다. 이 change가 sentinel을 감싸면서 깨졌다.

`errors.Is`로 바꿨다. 근거는 **그것이 production의 계약**이라는 것이다 — 그 오류를
읽는 다섯 곳(`execgw/retry.go:60`, `classify.go:111`, `failclosed.go:210`,
`cmd/tossctl/soak.go:613`, `openapi.go:56`) 전부 `errors.Is`/`errors.As`를 쓰고,
그 테스트의 주석 자신이 "the retry matrix classifies by those sentinels"라고
적어 두었다. `==`는 계약보다 엄격해서 production이 받아들이는 오류를 거부했다.

같은 표의 429·500 행도 함께 바꿨다. 감싸지 않은 sentinel에 대해
`errors.Is(x, x)`는 `x == x`와 같으므로 판정력은 그대로이고, 한 표 안에 두 판정
방식이 섞이는 것이 읽는 사람에게 더 나쁘다.

약화가 아니라는 증거는 `TestNothingDecidesAnAuthRefusalByReadingItsMessage`가
따로 고정한다 — 같은 문구를 가진 무관한 오류는 `errors.Is`를 만족하지 않는다.

## I6 — 변이가 두 번 통과했고 두 번 다 코드를 지웠다

이 change에서 변이 검증이 두 번 "통과"했다. 두 번 다 테스트를 느슨하게 두는 대신
**코드를 없앴다.**

1. 초안에서 채택 갈래를 지웠는데 헤드라인 테스트가 통과했다 — 당시엔 mtime 확인이
   그 시나리오를 흡수하고 있었다. 채택이 사는 창(건네준 뒤 답하기 전의 회전)을
   전용 테스트로 세워 RED를 확인했다. 그 mtime 확인은 나중에 리뷰가 철회시켰고,
   지금은 채택이 유일한 메커니즘이라 M1이 4건을 깬다.
2. 리뷰 P1-5 반영으로 형제 goroutine 전용 갈래를 넣었는데, 지워도 아무 테스트가
   안 깨졌다 — `exchange`가 반환 전에 파일을 쓰므로 파일 갈래가 이미 잡는다.
   **삭제했다.**

교훈은 하나다: 변이가 통과하면 테스트를 고칠지 코드를 지울지 매번 물어야 하고,
기본값은 지우는 쪽이다.

## I7 — 기존 테스트 하나를 더 고쳤다 (개정 후)

`token_test.go:TestTokenRefresh`가 `m.refresh(ctx)`를 부른다. `refused` 인자와
`adopted` 반환이 생기면서 컴파일되지 않는다.

**판정은 바꾸지 않았다.** 넘기는 `refused`는 방금 얻은 토큰이고 디스크에도 같은
것뿐이라 채택 후보가 없다 → 교환한다 → `hits == 2`가 그대로 성립한다. 단언을
하나 **더했다**: 이 시나리오에서 `adopted`는 false여야 한다. 늘어난 반환값을
버리면 그것이 무엇이든 통과하기 때문이다.

이 테스트가 손대지 않은 채로 M4(채택 조건 확대)를 잡는다는 점은 그대로다.

## I8 — D2 철회로 사라진 것과 남은 것

초안의 mtime 확인을 철회했으므로(design D2), **회전마다 보유자당 401을 한 번씩
먹는다.** `send()`의 재시도가 흡수하고 토큰 수명이 24시간이므로 하루 3회다.

그 401은 로그에 남지 않는다 — `send()`가 재시도로 삼켜서 호출자에게 오류가 가지
않는다. 즉 **배포 후 실측에서 "401이 사라졌는지"로는 이 change를 검증할 수 없다.**
검증 대상은 토큰 파일의 mtime 변경 횟수다(task 6.7).

## I9 — 리뷰어 worktree가 저장소 안에 만들어진다

`.claude/worktrees/agent-*/`는 저장소 트리 안이다. 저장소를 걸어다니는 정적
가드(`internal/candidate/bandscale_test.go:462` 등)가 그 안의 파일을 저장소 파일로
세어 **리뷰어가 도는 동안 `make test`가 실패한다**. 실제로 이 change 작업 중에
7건이 그렇게 실패했고 원인 추적에 시간을 썼다.

이 change가 고치지 않는다. 다음에 격리 리뷰를 돌릴 때는 worktree를 저장소 밖에
두거나, 정적 가드가 `.claude/worktrees/`를 제외해야 한다. a081 issues I6이
"리뷰어에게 각자 worktree를 줘라"고 적었고 이것이 그 대가다.

## I10 — `make test`는 부하에 따라 `internal/journal`에서 붉어진다

독립 리뷰어가 두 번 다 `internal/journal`이 **600.024s** — Go 기본 패키지
타임아웃 — 로 실패하는 것을 봤다. `t.Parallel()`에 goroutine이 묶인 상태였다.
단독으로 돌리면 `ok … 318.925s`로 통과한다.

이 change와 무관한 기존 취약성이고 여유가 2배쯤이다. 다만 **"`make test` 0 failed"는
부하 조건에 달린 주장**이라는 뜻이므로, 병행 작업(리뷰어 worktree 포함)이 도는
동안의 통과·실패를 그대로 믿으면 안 된다. I9와 같은 계열이다.

## I12 — 배포 실측: 증폭은 사라졌고 방아쇠는 남았다

task 6.7의 실측이 이 change의 예측을 반증했다. 예측은 "관측 창 안에 0회"였고
실측은 **1분 1.2회**다.

| | mtime 변경 | 환산 |
|---|---|---|
| 배포 전 (180초) | 19회 | 1분 6.3회 |
| 배포 후 (900초, 간섭 없음) | 18회 | 1분 1.2회 |

**이 change가 겨눈 증상은 사라졌다.** `reconcile.mismatch`(23)와
`authentication failed`(11)는 배포 후 한 건도 늘지 않았다. 그 둘은 같은 사건의
두 이름이었다 — 배포 전 로그에서 확인했다:

```
"msg":"reconcile.mismatch" … "error":"reconcile: snapshot discarded after a
partial read: walking the open-order list: official: authentication failed"
```

**남은 것은 다른 결함이다.** 채택은 연쇄를 끊었지만 연쇄를 시작시키는 것은 그대로다.
관측된 성질:

- 주기가 **61.5초**로 시계처럼 규칙적이다. 앞 11분은 사이클당 정확히 1회.
- reconcile이 아니다. `DefaultReconcilePeriod = 60초` + 작업 2.5초로 주기는
  맞지만, 쓰기가 사이클 종료 **20초 후**·다음 사이클 시작 **40초 전**에 떨어진다.
  두 60초 시계가 어긋나며 돈다 (간격이 23→22→21→20초로 줄었다).
- 매번 진짜 새 토큰이다 — `expires_at` = mtime + 24시간.
- 마지막 3분에는 사이클당 2회로 늘었다. 채택 후 또 거부당해 교환하는 갈래
  (task 3.7)이거나 보유자 둘이 각각 교환하는 것인데, 밖에서는 구분이 안 된다.

**왜 밖에서 더 못 캐는가.** 교환은 401을 받아야 일어나고, `send()`의 재시도가
성공하면 그 401은 아무 데도 안 남는다. 900초에 최소 18번의 거부가 있었는데 로그에
한 줄도 없다. I1의 401/403 질문도 같은 이유로 답이 없다.

**후속에 필요한 것.** 재시도가 구해낸 거부도 남기는 관측(상태 코드 포함).
그것 없이는 이 1분 1.2회의 원인을 지목할 수 없고, 지목 없이 코드를 고치는 것은
이 change가 이미 한 번 한 실수다 (D2 철회).
