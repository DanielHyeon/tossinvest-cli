# a082 · Design

## D1 — 채택-우선이 핑퐁을 끊는 지점

핑퐁의 엔진은 `refresh()`의 무조건 교환이다.

```go
// base f1aae509, token.go:89-93
func (m *tokenManager) refresh(ctx context.Context) (string, error) {
	m.mu.Lock()
	defer m.mu.Unlock()
	return m.exchange(ctx)
}
```

401이 말하는 것은 **"내가 들고 있는 토큰이 낡았다"**이지 **"새 토큰을 발급받아야
한다"**가 아니다. 둘을 같게 취급한 것이 결함이다. 다른 프로세스가 이미 새 토큰을
받아 디스크에 써 뒀다면, 그것을 받아 쓰는 것이 맞고 그때 새로 교환하면 그 프로세스의
토큰을 죽인다.

수정 후 `refresh()`는 이 순서다.

1. 디스크를 읽는다.
2. 디스크 토큰이 유효하고 **`m.cache`의 토큰과 다르면** 채택하고 반환한다.
3. 아니면 교환한다.

비교 대상이 `m.cache.AccessToken`인 근거: `send()`는 `c.tm.token(ctx)`가 준 토큰으로
요청하고 401이면 곧바로 `c.tm.refresh(ctx)`를 부른다. `token()`의 세 갈래 전부
반환 직전에 `m.cache`를 그 값으로 맞춰 두므로(step 1은 이미 그것, step 2는
`m.cache = ct`, step 3의 `exchange`는 `m.cache = ct`), **`m.cache.AccessToken`은
방금 실패한 토큰과 같다.** 같은 프로세스의 다른 goroutine이 그 사이에 `m.cache`를
바꿨다면 그것은 이미 새 토큰이라는 뜻이고, 그때도 "디스크와 다르면 채택"은 옳게
동작한다.

### 수렴 증명

A가 T1(디스크 현재값)을 쥐고 B·C가 낡은 T0을 쥔 상태.

| | 사건 | 교환 | 디스크 |
|---|---|---|---|
| 1 | B 요청 → 401 → refresh → 디스크 T1 ≠ T0 → 채택 | **0** | T1 |
| 2 | B 재시도 성공 | 0 | T1 |
| 3 | C도 같은 경로 | **0** | T1 |
| 4 | 셋이 T1로 수렴, 24시간 조용 | 0 | T1 |
| 5 | T1 만료 → 먼저 알아챈 하나가 교환 → T2 | 1 | T2 |
| 6 | 나머지 둘은 401 한 번 후 T2 채택 | 0 | T2 |

교환이 **토큰 수명당 1회**로 떨어진다.

## D2 — 디스크가 바뀌었으면 메모리를 믿지 않는다

D1만으로도 수렴하지만 5→6 회전마다 프로세스당 401을 한 번 먹는다. 그 401은
`send()`의 재시도가 흡수하므로 오류가 되지는 않지만, 낭비이고 **재시도 창을 한 번
더 여는 것**이라 이 change가 없애려는 바로 그 경주를 다시 만든다.

`token()`이 메모리 캐시를 믿기 전에 캐시 파일의 mtime을 본다. 마지막으로 우리가
읽거나 쓴 시각보다 새로우면 디스크를 다시 읽는다.

```
if isStillValid(m.cache, now) && !m.diskChanged() {
	return m.cache.AccessToken, nil
}
```

`stat` 한 번은 로컬 파일시스템 호출이고 요청당 마이크로초 단위다. 브로커 호출을
한 번 아끼는 값과 비교할 수준이 아니다.

**mtime을 쓰는 이유**: 토큰 값 자체를 비교하려면 파일을 매번 읽어야 하고 그건
`stat`보다 비싸다. mtime이 뒤로 가는 경우(시계 조정)는 "바뀌었다"로 읽혀 디스크를
한 번 더 읽을 뿐 안전 방향이다.

## D3 — 파일 락을 쓰지 않는다

이 저장소에는 `internal/config/adoption_flock_unix.go`와 `internal/enginelock`이라는
flock 선례가 둘 있다. 여기서는 쓰지 않는다.

- D1이 이미 수렴한다. 락이 막는 것은 만료 시점에 두 프로세스가 **동시에** 교환하는
  경우뿐이고, 그때도 각자 유효한 토큰을 받는다 — 하나가 다른 하나를 죽이지만 그쪽은
  다음 401에서 채택한다. 오류가 아니라 낭비 1회다.
- 락은 새 실패 모드를 들여온다. 토큰 획득은 **엔진의 모든 읽기가 지나는 경로**이고
  손절 판정도 그 위에 있다. 여기에 블로킹 락을 놓으면 락을 쥔 채 느려진 프로세스가
  나머지의 손절 판정을 지연시킬 수 있다. 안전 불변식 3이 금지하는 방향이다.
- 논블로킹 락이면 그 지연은 없지만, 락 실패 시 무엇을 할지가 다시 D1과 같은 질문이
  된다. 그러면 D1만 있으면 된다.

락이 필요해지는 경우가 있다면 브로커가 **동시 교환 자체를 거부**할 때다. 관측된
바 없고, D4의 상태 코드가 그것을 드러낼 것이다.

## D4 — 상태 코드를 버리지 않는다

```go
// base f1aae509, errors.go:41-45
case code == 401 || code == 403:
	if reIPWord.Match(bytes.ToLower(body)) {
		return ErrIPNotAllowed
	}
	return ErrAuth
```

401과 403이 같은 맨 sentinel이 된다. 이 결함이 사흘 동안 `authentication failed`
한 줄로만 보인 이유다.

`fmt.Errorf("%w (HTTP %d)", ErrAuth, code)`로 감싼다. 판정 규칙은 한 글자도 바꾸지
않는다 — 401/403 구분도, `ip` 낱말 검사도, 반환하는 sentinel도 그대로다. 바뀌는 것은
**메시지에 코드가 실린다**는 것뿐이다.

`errors.Is(err, ErrAuth)`가 계속 참이어야 한다. 이 저장소에서 그 판정에 기대는 곳은
`execgw/retry.go:60`, `execgw/classify.go:111`, `execgw/failclosed.go:210`,
`cmd/tossctl/soak.go:613`, `cmd/tossctl/openapi.go:56`이고 전부 `errors.Is`/
`errors.As`를 쓴다. 문자열 비교로 판정하는 곳은 없다 — 그것을 테스트로 고정한다.

**본문은 싣지 않는다.** 응답 본문에 계좌 식별자나 시크릿 파생값이 들어올 수 있고,
이 에러는 로그로 나간다. 코드만으로 401·403 구분이라는 목적이 달성된다.

## D5 — 기존 테스트가 왜 그대로 통과해야 하는가

`TestTokenRefresh`는 `refresh()`가 교환하는 것을 `hits == 2`로 고정한다. 그 테스트는
manager 하나가 자기가 쓴 토큰을 다시 읽는 상황이므로 **디스크 토큰 == `m.cache`
토큰**이고, D1의 조건("다르면 채택")이 성립하지 않아 교환한다. 그대로 통과한다.

이것이 이 설계의 좁음을 보여주는 증거다: 동작이 달라지는 것은 **다른 프로세스가
디스크를 바꿔 놓았을 때뿐**이고, 단일 프로세스 의미론은 글자 그대로 보존된다.

## D6 — 무엇을 관측으로 판정할 것인가

단위 테스트는 두 manager가 한 파일을 공유하는 것으로 프로세스 둘을 흉내낼 수 있다.
그것으로 충분한 이유는 결함이 **프로세스 경계가 아니라 캐시 계층**에 있기 때문이다 —
`tokenManager` 인스턴스 둘이 한 `cacheFile`을 보면 운영과 같은 조건이다.

배포 후 실측은 `openapi-token.json`의 mtime을 세는 것으로 한다. 지금 1분에 7회이고,
수정 후에는 **관측 창 안에 0회**여야 한다(토큰 수명이 24시간이므로).
