> a165 delta — 기존 요구 두 개의 MODIFIED(1.2). proposal 단계의 ADDED 초안을 대체한다.
> 노출 감소 주문(청산·flatten)의 접수 재시도 범위는 design D7 의 권고안 B 로 적었다 — **사람 결정 대기**. 다른 안이 고르면 이 delta 를 고치고
> requirement 변경 리뷰를 다시 한다.

## MODIFIED Requirements

### Requirement: Retry Matrix 산출물
재시도 정책은 endpoint×method×오류 클래스 표로 스펙 산출물화해야 한다(SHALL). 최소 규정: **주문 mutation은 아래 두 예외를 빼고 어떤 오류에도 자동 재시도 금지 — 단, 멱등 재생은 재시도가 아니라 정체 회수다**(같은 키·같은 본문의 재요청은 유효 창 안에서 새 주문을 만들 수 없다 — openapi; IN_DOUBT 해소 요구의 조건·상한·비활성 규칙을 따른다). 이 구분은 재시도 정책 구현부의 문서화된 근거에도 반영한다(SHALL). 조회는 재시도 예산(횟수·총 시간)과 bounded jitter, 429는 Retry-After 상한 준수, 401/403은 즉시 신규 진입 차단 + 알림, 필수 조회의 staleness 임계 초과 시 신규 진입 차단. 표의 수치는 구현 시 확정하고 표 없이 구현하지 않는다(SHALL NOT).

예외 1 — **엔진 게이트웨이의 노출 증가 주문 접수(`POST /api/v1/orders`)의 안전 재시도**(사용자 결정 2026-10-22·10-23). 재시도는 한 attempt 안의 재전송이며(SHALL — 새 attempt·새 결정·새 nonce 를 만들지 않는다), 같은 `clientOrderId` 와 같은 본문 바이트로만 한다(SHALL). 최초 전송 시작부터 8초 창 안에서만 재전송을 시작하고(SHALL), 재전송은 최대 2회다(SHALL). 갈래는 셋이다.

- (a) 브로커가 확실히 접수하지 않은 경우 — HTTP 429, 또는 요청 바이트를 하나도 쓰지 않은 전송 실패 — 는 짧은 대기 뒤 재전송할 수 있다(SHALL).
- (b) 결과 불명 — 5xx, 요청을 쓴 뒤의 전송 실패·타임아웃 — 은 맹목 재전송해서는 안 된다(SHALL NOT). 먼저 미체결·종결 목록을 IN_DOUBT 해소와 같은 지문으로 조회하고, 조회가 성공했고 일치가 없을 때만 재전송할 수 있다(SHALL). 조회 실패·일치 있음·창 초과면 재전송하지 않고 IN_DOUBT 해소 절차로 넘긴다(SHALL NOT — 창 밖 재전송 금지).
- (c) 확정 거절(4xx 검증 오류)과 그 밖의 응답(그 밖의 409 포함)은 재시도하지 않는다(SHALL NOT).

재전송마다 첫 전송 직전과 같은 마지막 경계 검사(결정 재읽기·키 일치·보호·진입 게이트·예약, strategy 면 최종 권한)를 다시 통과해야 하고(SHALL), 하나라도 거절하면 재시도를 멈춘다. 재시도는 최종 분류를 낙관 쪽으로 바꿀 수 없다(SHALL NOT): 브로커에 닿았을 수 있는 전송이 하나라도 있었으면 마지막 전송의 미전송·확정 거절은 결과 불명(IN_DOUBT)으로 기록한다. 토큰 갱신 뒤의 401 재전송(공식 클라이언트 안, 최대 2회, 같은 본문)은 「확실한 미접수」로 보되 그 근거는 시험으로 고정한다(SHALL — 실측 근거는 없다). 노출 감소 주문(청산·flatten)의 접수와 조건주문 생성·정정·취소는 이 예외의 대상이 아니다(SHALL NOT — 재시도 0회).

예외 2 — 취소·정정의 `409 already-processing` 재시도(「취소의 일시적 거절 처리」).

재시도의 사실·전송 횟수·갈래는 attempt 기록에 남아야 한다(SHALL — 재시도로 성공한 요청을 첫 시도 성공으로 기록하지 않는다). 재시도 설정이 없으면(nil) 재시도는 0회이고 기록은 재시도 이전과 같다(SHALL).

#### Scenario: 재생과 재시도의 구분
- **WHEN** 멱등키 없이 전송된 mutation이 모호한 오류로 끝나면
- **THEN** 어떤 자동 재전송도 발생하지 않는다 (재생은 영속된 키·본문이 있는 attempt의 해소 절차에서만)

#### Scenario: 필수 조회 장기 실패
- **WHEN** 잔고 조회가 재시도 예산을 소진하고 staleness 임계를 초과하면
- **THEN** 신규 진입이 차단되고 조회 복구 후 자동 해제된다

#### Scenario: 429 뒤 같은 키 재전송
- **WHEN** 노출 증가 주문 접수가 HTTP 429 로 끝나고 최초 전송부터 8초가 지나지 않았으며 재전송이 2회 미만이면
- **THEN** 같은 `clientOrderId`·같은 본문 바이트로 같은 attempt 안에서 다시 보내고, 기록에는 전송 횟수와 갈래가 남는다

#### Scenario: 결과 불명은 조회 먼저
- **WHEN** 주문 접수가 요청을 쓴 뒤의 타임아웃으로 끝나고 조회가 일치하는 주문을 찾으면
- **THEN** 재전송하지 않고 IN_DOUBT 해소 절차로 넘긴다

#### Scenario: 8초 창 밖의 결과 불명
- **WHEN** 주문 접수 결과가 불명이고 최초 전송부터 8초가 지났으면
- **THEN** 재전송하지 않고 IN_DOUBT 해소 절차로 넘긴다

#### Scenario: 확정 거절은 재시도 없음
- **WHEN** 주문 접수가 4xx 검증 오류로 거절되면
- **THEN** 자동 재시도는 일어나지 않는다

#### Scenario: 재시도 뒤 거절은 원 주문을 증명하지 않는다
- **WHEN** 429 뒤 재전송이 `422 idempotency-key-conflict` 같은 확정 거절로 끝나면
- **THEN** attempt 는 FAILED_CONFIRMED 가 아니라 IN_DOUBT 로 정착한다

#### Scenario: 청산 주문은 재시도하지 않는다
- **WHEN** 청산·flatten 의 매도 접수가 HTTP 429 로 끝나면
- **THEN** 자동 재전송은 일어나지 않는다

### Requirement: 취소의 일시적 거절 처리

브로커가 **취소 또는 정정**을 일시적 사유로 거절하면 그 요청은 유한 재시도해야 한다(SHALL) — 검증 도구와 엔진 게이트웨이 양쪽에서.
일시적 거절의 실측 형태는 HTTP 409 `already-processing` + `data.retryAfterSeconds`이며
취소(M16)와 정정(M24) 양쪽에서 관측됐다.
대기는 브로커가 제시한 `retryAfterSeconds`를 따르되 상한을 둔다(SHALL — 검증 도구는 회당 5초, 엔진 게이트웨이는 **누적 5초**이고
최초 전송부터 8초 창 안에서만 재전송한다). 재시도 횟수에는 상한이 있어야 한다(SHALL — 추가 2회). 재시도가 모두 실패하면 실패로 기록하고
잔여 객체를 보고한다(SHALL — 조용히 성공으로 만들지 않는다; 엔진 게이트웨이에서는 지금처럼 IN_DOUBT 로 정착한다).

이 재시도는 **취소와 정정에만** 적용된다(SHALL NOT — 조건주문 생성의 자동 재시도는 계속 금지되고, 주문 접수의 재시도는 「Retry Matrix 산출물」의
예외 1 만 따른다). 근거: 취소는 노출을 줄이고, 정정은 이 도구에서 체결 불가 지정가를 시장에서
한 호가 더 멀리 옮기는 것이며, 둘 다 **생성 연산이 아니다** — 반복해도 두 번째 주문이 생길 수
없다. 재시도 사실과 횟수는 관측 기록(엔진 게이트웨이는 attempt 기록)에 남겨야 한다(SHALL — 재시도로 성공한 요청을 첫 시도 성공으로 표시해서는 안 된다
(SHALL NOT)).

재시도 판정은 HTTP 상태와 **본문의 오류 코드가 모두 일치할 때만** 참이어야 한다(SHALL) —
다른 사유의 409를 재시도 루프로 만들지 않는다. 본문의 두 code 자리(최상위 `code`·`error.code`)가 서로 다르면 재시도하지 않는다(SHALL NOT).

#### Scenario: 일시적 거절 후 성공

- **WHEN** 취소 또는 정정이 `already-processing`으로 거절되고 재시도가 성공하면
- **THEN** 요청은 처리되고, 기록에는 재시도가 있었다는 사실과 횟수가 남는다

#### Scenario: 재시도 상한 소진

- **WHEN** 상한까지 재시도해도 계속 거절되면
- **THEN** 실패로 기록되고 그 객체가 살아 있다는 사실이 보고된다

#### Scenario: 조건주문 생성은 재시도하지 않는다

- **WHEN** 조건주문 생성이 실패하면
- **THEN** 자동 재시도는 일어나지 않는다

#### Scenario: 다른 사유의 409

- **WHEN** 엔진 경로의 취소가 409 로 거절되고 본문 code 가 `already-processing` 이 아니면
- **THEN** 재시도하지 않는다
