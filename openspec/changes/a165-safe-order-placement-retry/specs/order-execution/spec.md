> a165 delta (3판) — 기존 요구 두 개의 MODIFIED. 사용자 3차 결정(2026-10-23)으로 주문 접수 재전송은 a171 로 옮겼다. 1·2판을 대체한다.

## MODIFIED Requirements

### Requirement: Retry Matrix 산출물
재시도 정책은 endpoint×method×오류 클래스 표로 스펙 산출물화해야 한다(SHALL). 최소 규정: **주문 mutation은 어떤 오류에도 자동 재시도 금지 — 단, 멱등 재생은 재시도가 아니라 정체 회수이고, 취소의 `409 already-processing` 은 「취소의 일시적 거절 처리」를 따른다**(같은 키·같은 본문의 재요청은 유효 창 안에서 새 주문을 만들 수 없다 — openapi; IN_DOUBT 해소 요구의 조건·상한·비활성 규칙을 따른다). 이 구분은 재시도 정책 구현부의 문서화된 근거에도 반영한다(SHALL). 조회는 재시도 예산(횟수·총 시간)과 bounded jitter, 429는 Retry-After 상한 준수, 401/403은 즉시 신규 진입 차단 + 알림, 필수 조회의 staleness 임계 초과 시 신규 진입 차단. 표의 수치는 구현 시 확정하고 표 없이 구현하지 않는다(SHALL NOT).

공식 클라이언트가 401 에 토큰을 갱신해 같은 요청을 다시 보내는 기존 동작(최대 2회, 같은 본문 바이트)은 브로커가 그 요청을 받지 않은 경우로 본다(SHALL — 근거는 시험으로 고정한다; 실측 근거는 없다). 이 재전송은 클라이언트 안의 일이라 attempt 기록 대상이 아니다.

#### Scenario: 재생과 재시도의 구분
- **WHEN** 멱등키 없이 전송된 mutation이 모호한 오류로 끝나면
- **THEN** 어떤 자동 재전송도 발생하지 않는다 (재생은 영속된 키·본문이 있는 attempt의 해소 절차에서만; 취소의 `409 already-processing` 은 모호한 오류가 아니라 「취소의 일시적 거절 처리」가 다루는 확정 거절이다)

#### Scenario: 필수 조회 장기 실패
- **WHEN** 잔고 조회가 재시도 예산을 소진하고 staleness 임계를 초과하면
- **THEN** 신규 진입이 차단되고 조회 복구 후 자동 해제된다

#### Scenario: 401 재전송은 같은 본문이다
- **WHEN** 주문 접수 POST 가 401 을 받고 토큰이 갱신되면
- **THEN** 다시 보내는 요청의 본문은 첫 요청과 바이트 동일하고, 401 이 아닌 오류에는 다시 보내지 않는다

### Requirement: 취소의 일시적 거절 처리

브로커가 **취소 또는 정정**을 일시적 사유로 거절하면 검증 도구는 그 요청을 유한 재시도해야 한다(SHALL).
일시적 거절의 실측 형태는 HTTP 409 `already-processing` + `error.data.retryAfterSeconds`이며
취소(M16)와 정정(M24) 양쪽에서 관측됐다.
대기는 브로커가 제시한 `retryAfterSeconds`를 따르되 상한을 둔다(SHALL — 현행 5초). 재시도
횟수에는 상한이 있어야 한다(SHALL — 현행 추가 2회). 재시도가 모두 실패하면 실패로 기록하고
잔여 객체를 보고한다(SHALL — 조용히 성공으로 만들지 않는다).

엔진 게이트웨이의 **취소**가 `409 already-processing` 으로 거절되면(사용자 결정 2026-10-23):

- 엔진(청산 루프)은 같은 시도 안에서 기다리거나 다시 보내지 않고 그 취소를 실행되지 않은 확정 거절(FAILED_CONFIRMED)로 기록한다(SHALL — 같은 주기의 뒤 포지션 지연 0). 그 주문은 살아 있는 것으로 남고, 청산 루프는 다음 주기에 새 결정으로 다시 취소한다(SHALL). 그 대상 주문이 살아 있는 동안 그 종목의 **새 진입(노출을 늘리는 변경)은 거절된다**(SHALL — 대상 주문의 종결 기록이나 그 주문의 접수 확정된 취소가 원장에 생기면 풀리고, 재시작 뒤에도 유지된다). 취소·청산 매도·flatten·대사·보호 경로는 이 거절을 받지 않는다(SHALL NOT).
- CLI flatten 은 `retryAfterSeconds`(없거나 숫자가 아니거나 0 이하면 1초)를 따라 누적 대기 5초 이내·첫 전송의 마지막 경계 검사가 시작되기 전부터 잰 8초 창 안에서 최대 2회 다시 보낸다(SHALL — 창의 시작을 첫 전송 뒤로 미뤄 창을 늘려서는 안 된다(SHALL NOT)). 재전송은 첫 전송과 같은 마지막 경계 검사·전송 직전 취소 확인을 그대로 거치고, 재시도 창이 끝나거나 취소돼도 그 취소의 결과 기록은 끊기지 않아야 한다(SHALL). 재전송마다 첫 전송 직전과 같은 마지막 경계 검사를 다시 통과해야 한다(SHALL). 브로커가 수락하거나 `already-processing` 이 아닌 답을 주면 그 답으로 기록하고, 소진·중단·재전송의 전송 전 실패이면 그 취소를 결과 불명(IN_DOUBT)으로 남겨 해소 절차와 그 종목의 매도 보류를 그대로 받는다(SHALL — 확정 거절·미전송으로 닫아 「주문이 없다」로 읽히게 해서는 안 된다(SHALL NOT)).
- 게이트웨이의 주문 접수·정정에는 이 처리를 적용하지 않는다(SHALL NOT).

이 재시도는 **취소와 정정에만** 적용된다(SHALL NOT — 주문 접수·조건주문 생성의 자동 재시도는
계속 금지된다). 근거: 취소는 노출을 줄이고, 정정은 이 도구에서 체결 불가 지정가를 시장에서
한 호가 더 멀리 옮기는 것이며, 둘 다 **생성 연산이 아니다** — 반복해도 두 번째 주문이 생길 수
없다. 접수와 조건주문 생성은 반복하면 생길 수 있으므로 금지가 유지된다. 재시도 사실과 횟수, 그리고 게이트웨이의 확정 거절 분류는
관측 기록(게이트웨이는 attempt 기록)에 남겨야 한다(SHALL — 재시도로 성공한 요청을 첫 시도 성공으로 표시해서는 안 된다
(SHALL NOT)). 게이트웨이에 이 처리의 설정이 없으면 기록은 이 처리 이전과 같다(SHALL).

재시도·확정 거절 판정은 HTTP 상태와 **본문의 오류 코드가 모두 일치할 때만** 참이어야 한다(SHALL) —
다른 사유의 409를 재시도 루프로 만들지 않는다. 본문의 두 code 자리(최상위 `code`·`error.code`)가 모두 있고 서로 다르면 참이 아니다(SHALL NOT).

#### Scenario: 일시적 거절 후 성공

- **WHEN** 검증 도구의 취소 또는 정정, 또는 CLI flatten 게이트웨이의 취소가 `already-processing`으로 거절되고 재시도가 성공하면
- **THEN** 요청은 처리되고, 기록에는 재시도가 있었다는 사실과 횟수가 남는다

#### Scenario: 재시도 상한 소진

- **WHEN** 검증 도구가 상한까지 재시도해도 계속 거절되면
- **THEN** 실패로 기록되고 그 객체가 살아 있다는 사실이 보고된다

#### Scenario: 접수·조건주문 생성은 재시도하지 않는다

- **WHEN** 주문 접수나 조건주문 생성이 실패하면
- **THEN** 자동 재시도는 일어나지 않는다

#### Scenario: 엔진 청산 전 취소의 already-processing

- **WHEN** 엔진 청산 루프의 취소가 `409 already-processing` 으로 거절되면
- **THEN** 브로커 호출은 1회이고 대기 없이 FAILED_CONFIRMED 로 기록되며, 같은 주기의 다음 주문 처리가 늦어지지 않고, 다음 주기에 다시 취소된다

#### Scenario: 엔진 취소 확정 미수락 뒤 같은 종목 진입

- **WHEN** 엔진 청산 루프의 취소가 `409 already-processing` 으로 확정 미수락 기록되고 그 대상 주문이 아직 종결되지 않았으면
- **THEN** 같은 종목의 새 진입은 브로커 호출 없이 거절되고, 같은 종목의 재취소·청산 매도·flatten 은 거절되지 않으며, 대상 주문의 종결 기록이나 접수 확정된 취소가 생기면 진입 거절이 풀리고, 엔진을 재시작해도 풀리기 전에는 거절이 유지된다

#### Scenario: CLI flatten 취소의 재시도 소진

- **WHEN** CLI flatten 의 취소가 재시도 상한까지 `already-processing` 으로 거절되면
- **THEN** 그 취소는 IN_DOUBT 로 남아 해소 절차를 거치고, 그 종목의 청산 매도는 취소가 정착할 때까지 보류된다

#### Scenario: 다른 사유의 409

- **WHEN** 게이트웨이의 취소가 409 로 거절되고 본문 code 가 `already-processing` 이 아니거나 두 code 자리가 다르면
- **THEN** 이 처리 이전과 같이 결과 불명으로 기록된다
