> a165 delta (2판) — 기존 요구 세 개의 MODIFIED. 사용자 2차 결정(2026-10-23)을 반영했다. 1판(ADDED·MODIFIED 첫 판)을 대체한다.

## MODIFIED Requirements

### Requirement: Retry Matrix 산출물
재시도 정책은 endpoint×method×오류 클래스 표로 스펙 산출물화해야 한다(SHALL). 최소 규정: **주문 mutation은 아래 예외를 빼고 어떤 오류에도 자동 재시도 금지 — 단, 멱등 재생은 재시도가 아니라 정체 회수다**(같은 키·같은 본문의 재요청은 유효 창 안에서 새 주문을 만들 수 없다 — openapi; IN_DOUBT 해소 요구의 조건·상한·비활성 규칙을 따른다). 이 구분은 재시도 정책 구현부의 문서화된 근거에도 반영한다(SHALL). 조회는 재시도 예산(횟수·총 시간)과 bounded jitter, 429는 Retry-After 상한 준수, 401/403은 즉시 신규 진입 차단 + 알림, 필수 조회의 staleness 임계 초과 시 신규 진입 차단. 표의 수치는 구현 시 확정하고 표 없이 구현하지 않는다(SHALL NOT).

예외 1 — **엔진 게이트웨이의 노출 증가 지정가 접수(`POST /api/v1/orders`)의 결과 불명 재전송**(사용자 결정 2026-10-22·10-23). 결과 불명은 실제로 받은 HTTP 5xx, 또는 요청 바이트를 쓰기 시작한 뒤 응답 첫 바이트를 받기 전에 끊긴 전송뿐이다(SHALL — 응답을 받은 뒤의 해석·읽기 실패와 응답 echo 불일치는 포함하지 않는다). 재전송은 한 attempt 안에서(SHALL — 새 attempt·결정·nonce 없음), 같은 `clientOrderId` 와 같은 본문 바이트로만(SHALL), 최초 전송부터 8초 창 안에서만(SHALL), 최대 2회 한다(SHALL). 재전송 전에는 미체결·종결 목록 각 1페이지를 IN_DOUBT 해소와 같은 지문으로 조회하고, 조회가 성공했고 일치가 없을 때만 재전송한다(SHALL). 조회 실패·일치 있음·창 초과면 재전송하지 않는다(SHALL NOT). 재전송마다 첫 전송 직전과 같은 마지막 경계 검사를 다시 통과해야 하며(SHALL), 하나라도 거절하면 재전송하지 않는다. 재전송이 있었던 attempt 의 마지막 전송이 미전송·확정 거절이면 결과 불명(IN_DOUBT)으로 기록한다(SHALL — 재시도는 낙관 종결을 만들지 않는다). HTTP 429·요청 전송 전 실패·노출 감소 주문(청산·flatten)의 접수·strategy first-leg 접수·조건주문 생성·정정·취소는 이 예외의 대상이 아니다(SHALL NOT — 재전송 0회). 토큰 갱신 뒤의 401 재전송(공식 클라이언트 안, 최대 2회, 같은 본문)은 기존 동작이며 「확실한 미접수」로 보되 근거는 시험으로 고정한다(SHALL — 실측 근거는 없다).

예외 2 — 취소의 `409 already-processing` 처리(「취소의 일시적 거절 처리」).

재전송·재시도의 사실·전송 횟수·갈래는 attempt 기록에 남아야 한다(SHALL — 재시도로 성공한 요청을 첫 시도 성공으로 기록하지 않는다). 재시도 설정이 없으면 예외 1·2 의 게이트웨이 동작은 없고 기록은 이 예외 이전과 같다(SHALL).

#### Scenario: 재생과 재시도의 구분
- **WHEN** 멱등키 없이 전송된 mutation이 모호한 오류로 끝나면
- **THEN** 어떤 자동 재전송도 발생하지 않는다 (재생은 영속된 키·본문이 있는 attempt의 해소 절차에서만; 취소의 `409 already-processing` 은 모호한 오류가 아니라 「취소의 일시적 거절 처리」가 다루는 확정 거절이다)

#### Scenario: 필수 조회 장기 실패
- **WHEN** 잔고 조회가 재시도 예산을 소진하고 staleness 임계를 초과하면
- **THEN** 신규 진입이 차단되고 조회 복구 후 자동 해제된다

#### Scenario: 5xx 뒤 조회 부재면 같은 키 재전송
- **WHEN** 노출 증가 지정가 접수가 HTTP 5xx 로 끝나고, 최초 전송부터 8초가 지나지 않았고, 미체결·종결 1페이지 조회에 일치가 없으면
- **THEN** 같은 `clientOrderId`·같은 본문 바이트로 같은 attempt 안에서 다시 보내고, 기록에는 전송 횟수와 갈래가 남는다

#### Scenario: 결과 불명이지만 조회가 일치를 찾음
- **WHEN** 접수가 응답 전에 끊긴 전송으로 끝나고 조회가 일치하는 주문을 찾으면
- **THEN** 재전송하지 않고 IN_DOUBT 해소 절차로 넘긴다

#### Scenario: 8초 창 밖의 결과 불명
- **WHEN** 접수 결과가 불명이고 최초 전송부터 8초가 지났으면
- **THEN** 재전송하지 않고 IN_DOUBT 해소 절차로 넘긴다

#### Scenario: 확정 거절과 429 는 재전송 없음
- **WHEN** 접수가 4xx 검증 오류 또는 HTTP 429 로 끝나면
- **THEN** 자동 재전송은 일어나지 않는다

#### Scenario: 응답을 받은 뒤의 실패는 재전송 없음
- **WHEN** 접수가 2xx 응답을 받았으나 본문을 읽거나 해석하지 못했거나, 응답 echo 의 `clientOrderId` 가 다르면
- **THEN** 재전송하지 않는다

#### Scenario: 재전송 뒤 거절은 원 주문을 증명하지 않는다
- **WHEN** 재전송이 `422 idempotency-key-conflict` 같은 확정 거절로 끝나면
- **THEN** attempt 는 FAILED_CONFIRMED 가 아니라 IN_DOUBT 로 정착한다

#### Scenario: 청산 주문은 재전송하지 않는다
- **WHEN** 청산·flatten 의 매도 접수가 HTTP 5xx 로 끝나면
- **THEN** 자동 재전송은 일어나지 않는다

#### Scenario: 재시도 설정이 없으면 이전과 같다
- **WHEN** 게이트웨이에 재시도 설정이 없고 접수가 HTTP 5xx 로 끝나면
- **THEN** 전송은 1회이고 attempt 기록은 이 예외 이전과 바이트 동일하다

### Requirement: 취소의 일시적 거절 처리

브로커가 **취소 또는 정정**을 일시적 사유로 거절하면 그 요청은 유한 재시도해야 한다(SHALL — 검증 도구). 엔진 게이트웨이는 아래 규칙을 따른다.
일시적 거절의 실측 형태는 HTTP 409 `already-processing` + `error.data.retryAfterSeconds`이며
취소(M16)와 정정(M24) 양쪽에서 관측됐다.
검증 도구의 대기는 브로커가 제시한 `retryAfterSeconds`를 따르되 상한을 둔다(SHALL — 현행 5초). 재시도
횟수에는 상한이 있어야 한다(SHALL — 현행 추가 2회). 재시도가 모두 실패하면 실패로 기록하고
잔여 객체를 보고한다(SHALL — 조용히 성공으로 만들지 않는다).

엔진 게이트웨이의 **취소**가 `409 already-processing` 으로 거절되면 그 취소는 실행되지 않은 확정 거절(FAILED_CONFIRMED)로 기록한다(SHALL — 결과 불명이 아니다). 엔진 청산 루프는 같은 주기 안에서 재시도하지 않고 다음 주기에 다시 취소한다(SHALL — 뒤 포지션 지연 0, 사용자 결정 2026-10-23). CLI flatten 의 게이트웨이는 `retryAfterSeconds`(없거나 숫자가 아니거나 0 이하면 1초)를 따라 누적 대기 5초·최초 전송부터 8초 창 안에서 최대 2회 재시도하고(SHALL), 소진하면 같은 확정 거절로 기록한다. 게이트웨이의 정정에는 이 처리를 적용하지 않는다(SHALL NOT — 생산 호출자 없음).

이 재시도는 **취소와 정정에만** 적용된다(SHALL NOT — 조건주문 생성의 자동 재시도는 계속 금지되고, 주문 접수의 재전송은 「Retry Matrix 산출물」의
예외 1 만 따른다). 근거: 취소는 노출을 줄이고, 정정은 이 도구에서 체결 불가 지정가를 시장에서
한 호가 더 멀리 옮기는 것이며, 둘 다 **생성 연산이 아니다** — 반복해도 두 번째 주문이 생길 수
없다. 접수와 조건주문 생성은 반복하면 생길 수 있으므로 예외 1 밖에서는 금지가 유지된다. 재시도 사실과 횟수는
관측 기록(게이트웨이는 attempt 기록)에 남겨야 한다(SHALL — 재시도로 성공한 요청을 첫 시도 성공으로 표시해서는 안 된다
(SHALL NOT)).

재시도·확정 거절 판정은 HTTP 상태와 **본문의 오류 코드가 모두 일치할 때만** 참이어야 한다(SHALL) —
다른 사유의 409를 재시도 루프로 만들지 않는다. 게이트웨이에서 본문의 두 code 자리(최상위 `code`·`error.code`)가 서로 다르면 이 처리를 하지 않는다(SHALL NOT).

#### Scenario: 일시적 거절 후 성공

- **WHEN** 취소 또는 정정이 `already-processing`으로 거절되고 재시도가 성공하면
- **THEN** 요청은 처리되고, 기록에는 재시도가 있었다는 사실과 횟수가 남는다

#### Scenario: 재시도 상한 소진

- **WHEN** 상한까지 재시도해도 계속 거절되면
- **THEN** 실패로 기록되고 그 객체가 살아 있다는 사실이 보고된다

#### Scenario: 조건주문 생성은 재시도하지 않는다

- **WHEN** 조건주문 생성이 실패하면
- **THEN** 자동 재시도는 일어나지 않는다

#### Scenario: 엔진 청산 전 취소의 already-processing

- **WHEN** 엔진 청산 루프의 취소가 `409 already-processing` 으로 거절되면
- **THEN** 같은 주기 안 재시도 없이 FAILED_CONFIRMED 로 기록되고, 다음 주기에 다시 취소된다

#### Scenario: 다른 사유의 409

- **WHEN** 게이트웨이의 취소가 409 로 거절되고 본문 code 가 `already-processing` 이 아니면
- **THEN** 재시도·확정 거절 분류 없이 이전과 같이 처리된다

### Requirement: IN_DOUBT 해소
IN_DOUBT 해소의 목적은 **정체 회수**다 — 주문이 접수됐는지, 접수됐다면 어떤 식별자인지 확정하는 것이며, 정체를 모르는 채 다시 주문을 내는 것은 금지된다(SHALL NOT).

공식 API의 주문 생성은 클라이언트 제공 멱등키를 지원한다(openapi `clientOrderId`: "동일 값으로 재요청 시 이전 주문 결과를 그대로 재반환합니다", 유효 10분). 해소 순서(SHALL):

1. **멱등 재생**: RECORDED 단계에 영속된 동일 키·동일 wire body의 재요청 응답에서 식별자를 회수한다. 다음은 **진입점 자신의 의무**다(SHALL — 호출자 전제 금지): 대상 attempt가 IN_DOUBT 상태인지 확인, 능력 attestation 플래그 확인 `[미측정 — 2b 전 비활성]`, **재생 1회마다** `elapsed(전송 시작) < TTL − margin`(margin 기본 60초, 설정 주입 — 경과 근거가 로컬 시계이므로 마진 없는 경계 사용 금지(SHALL NOT)) 재검사, 회수 상한(기본 2회)·최소 간격 준수, 저장된 wire body 외의 본문을 구성·전송할 수 없는 형태(SHALL — 진입점 입력은 attempt 식별자뿐). 재생은 새 attempt를 만들지 않고 nonce를 소비하지 않으며 해소 기록(횟수·시각)으로 남는다(SHALL).

   재생 응답 분류에 dispatch 분류기를 사용해서는 안 된다(SHALL NOT — 재생의 422는 의미가 다르다): 2xx+식별자 → 회수·CONFIRMED; `409 request-in-progress`(openapi) → 원 요청 처리 중, 대기 후 재시도(상한 미소비); `422 idempotency-key-conflict`(openapi) → 원 주문에 대해 아무것도 증명하지 않으므로 FAILED_CONFIRMED 금지(SHALL NOT), 프로그램 오류로 UNRESOLVED + critical 알림; 응답 유실 → 기록 후 상한 도달 시 조회 폴백.
2. **조회 대조 (폴백)**: 창 초과, 미검증, 키 충돌, 멱등키를 받지 않는 mutation(취소·정정)은 journal fingerprint로 미체결·종결 양쪽 목록을 pagination 완주하며 대조한다. `status` 파라미터는 그룹 라벨이고 `PARTIAL_FILLED`는 양쪽 그룹에 모두 속하므로(openapi), 유일성 판정 전에 **orderId 기준 dedup**을 수행해야 한다(SHALL — dedup 없이는 부분 체결 주문이 이중 매칭되어 영구 주차된다). 조회 응답은 멱등키를 싣지 않으므로 키로 매칭할 수 없다(SHALL NOT).
3. **부재 판정**: 최소 관찰 기간에 걸친 연속 N회(기본 3회) 안정화 조회 + 매수가능금액·보유수량 delta 교차 확인 후에만. 관측 창 동안 같은 심볼에 다른 mutation이 전송되었다면 delta 교차 확인은 무효이며 자동 FAILED_CONFIRMED는 금지된다(SHALL NOT — 부재를 증명할 수 없으므로 UNRESOLVED로).
4. **해소 불능**: UNRESOLVED_IN_DOUBT로 해당 심볼 신규 진입 영구 차단, 운영자 해소만 허용.

**접수 직후 재전송은 해소가 아니다(a165).** 엔진 게이트웨이가 노출 증가 지정가 접수의 결과 불명(실제로 받은 5xx, 또는 응답 첫 바이트 전에 끊긴 전송)을 같은 attempt 안에서 최초 전송부터 8초 창 안에 같은 키·같은 본문으로 재전송하는 것은 DISPATCH_STARTED 단계의 전송이며, 위 1 의 재생(능력 attestation 전제)과 별개다(SHALL — 「Retry Matrix 산출물」 예외 1). 그 재전송 전에는 미체결·종결 목록 각 1페이지를 지문으로 조회해 일치가 없어야 하고(SHALL), 재전송이 ACK 를 받으면 정착 전에 같은 조회로 일치가 정확히 하나이고 그 orderId 가 ACK 의 것일 때만 CONFIRMED 로 종결한다(SHALL — 아니면 IN_DOUBT). 창을 넘거나 재전송하지 않은 결과 불명은 이 해소 절차로 온다. 실패 응답 뒤 같은 키 재요청의 멱등 동작은 측정되지 않았다(사용자 수락 잔여 2026-10-23).

재시작 복구가 호출 순서를 소유한다(SHALL): 미종결 attempt 순회 → IN_DOUBT이고 재생 적격이면 Gateway의 해소 전용 재생 진입점 → 부적격·실패 시 조회 폴백. 해소 절차 자체는 mutator를 갖지 않는다(P1 불변식 유지 — 재생 진입점은 Gateway 소속). 조회 대조의 유일 매칭을 위해 심볼당 in-flight mutation 1개 제한은 **모든 safety class에** 유지된다(SHALL — 동시 반대 방향 제출은 브로커도 `422 opposite-pending-order-exists`로 거부한다(openapi)). §0.3은 동시성이 아니라 해소의 우선·유계성(재생이 이를 단축)과 수동 flatten의 순서화된 saga로 달성한다.

#### Scenario: 멱등 재생으로 정체 회수
- **WHEN** 능력 검증 완료 상태에서 제출 응답이 유실되고 TTL−margin 이내에 해소가 시작되면
- **THEN** 저장된 wire body의 재요청 응답에서 orderId를 회수해 CONFIRMED로 종결하며 두 번째 주문은 생성되지 않는다

#### Scenario: 두 번째 재생의 시간 재검사
- **WHEN** 첫 재생 후 재시도 시점에 경과 시간이 TTL−margin을 넘었으면
- **THEN** 두 번째 재생은 수행되지 않고 조회 폴백으로 전환된다

#### Scenario: 재생 중 409
- **WHEN** 재생 요청이 409 request-in-progress를 받으면
- **THEN** 상한을 소비하지 않고 대기 후 재시도하거나 조회 폴백으로 전환한다

#### Scenario: 부분 체결 주문의 양쪽 목록 출현
- **WHEN** 조회 폴백이 같은 orderId를 미체결·종결 목록 양쪽에서 발견하면
- **THEN** dedup 후 단일 매칭으로 CONFIRMED 종결되며 이중 매칭 주차가 발생하지 않는다

- **THEN** delta 교차 확인이 무효화되어 자동 FAILED_CONFIRMED 없이 UNRESOLVED로 처리된다

#### Scenario: 해소 불능
- **WHEN** 관찰 기간 내 존재도 부재도 증명되지 않으면
- **THEN** UNRESOLVED_IN_DOUBT로 표기되어 해당 심볼 신규 진입이 영구 차단되고 운영자 알림이 발송된다

**브로커가 이름을 준 거절은 code가 분류한다.**

브로커 응답이 **요청 자체를 서술하는 code**를 실었으면 그 code로 분류해야 하며, HTTP status로 분류해서는 안 된다(SHALL NOT). code가 확정 거절을 뜻하면 그 attempt는 IN_DOUBT로 가지 않고 종결해야 한다(SHALL).

`opposite-pending-order-exists`는 확정 거절이다(SHALL) — 브로커가 반대 방향 미체결 주문의 존재를 이유로 요청을 거절했고, 그 상태에서 주문은 접수되지 않는다.

이 판정은 응답 본문의 **`code` 필드 값**으로만 성립해야 한다(SHALL). status로 걸어서는 안 되고(SHALL NOT), message 문구로 걸어서도 안 되며(SHALL NOT), **본문 전체에 대한 부분문자열 일치로 걸어서도 안 된다**(SHALL NOT — 다른 필드가 그 문자열을 담을 수 있다). 브로커는 같은 code에 대해 계약과 다른 status와 message를 낼 수 있고, 실제로 냈다.

**code 필드의 자리와 표기는 하나가 아니다.** 실측된 본문은 두 모양을 갖는다 — 최상위 `{"code": "TRADE_AUTH_REQUIRED", …}`와 `{"error": {"code": "opposite-pending-order-exists", …}}`. 따라서 판정은 **최상위 `code`와 `error.code`를 모두 읽어야 하고(SHALL)**, 값 비교는 **대소문자를 무시한 전체 일치**여야 한다(SHALL — 부분문자열 일치는 위에서 금지했다). 어느 자리에서도 code를 얻지 못하거나 본문이 JSON이 아니면 **분류하지 않고 종전 경로로 보내야 한다**(SHALL — 모르는 것을 확정으로 바꾸지 않는다). 최상위 `code`와 `error.code`가 **둘 다 있고 값이 다르면** 그 응답은 **모호로 강제**해야 하며(SHALL), 그 뒤의 어떤 분류(브로커 거절 문구 분류·HTTP status 분류)도 적용해서는 안 된다(SHALL NOT — status가 확정 거절 목록의 422여도 확정 거절로 떨어지지 않는다). 이 분류기의 결과는 확정 거절·모호 강제·판정 없음 셋이며, 판정 없음만 종전 경로로 간다(SHALL).

HTTP status 자체의 확정 거절 목록에 409를 추가해서는 안 된다(SHALL NOT — `409 request-in-progress`는 원 요청이 실행됐을 수 있으므로 확정 거절로 다루면 살아 있는 주문을 은퇴시킨다).

**이 분류를 재생 응답에 적용해서는 안 된다(SHALL NOT).** 재생에서 같은 code는 재생 요청이 거절됐다는 것만 말하고 원 주문에 대해서는 아무것도 증명하지 않는다 — 위 §1의 `422 idempotency-key-conflict` 규칙과 같은 구조다.

**종결된 mutation attempt는 그것이 무장한 보호 발의를 풀어야 한다.**

보호 청산의 발의는 그것을 실행하려던 attempt가 **접수되지 않음이 입증된 종결 상태**에 이르면 해제되어야 한다(SHALL). 대상 상태는 브로커가 확정 거절한 경우(`FAILED_CONFIRMED`)와 전송되지 않은 경우(`NOT_DISPATCHED`)뿐이다.

**판정 불능으로 park된 attempt(`UNRESOLVED_IN_DOUBT`)의 발의를 해제해서는 안 된다**(SHALL NOT — 원 주문의 존재가 미지이고, 발의는 두 번째 매도를 막는 실제 방벽이다. 발의를 비우면 원 매도가 살아 있어도 다음 발의가 무장된다). park는 운영자 해소로만 끝난다. 운영자가 비수용으로 닫으면 **그 자리에서** 위 규칙과 **같은 해제 판정**으로 발의를 해제해야 한다(SHALL — 다음 기동까지 기다리면 무보호 창이 늘어난다). 해제 판정은 한 곳에만 두어야 한다(SHALL).

해제는 **그 attempt의 intent가 현재 무장된 발의의 intent와 같을 때만** 발의를 비워야 한다(SHALL). 다르면 아무것도 바꾸어서는 안 된다(SHALL NOT — 늦게 도착한 해제가 그 사이 무장된 다른 발의를 지운다).

attempt 종결과 발의 해제가 다른 쓰기이므로, **기동 시** 무장된 발의마다 그 intent의 attempt가 **모두** 위 두 종결 상태이거나 그 intent의 attempt가 **하나도 없으면**(전송 전 기록이 없으므로 아무것도 나가지 않았다) 해제해야 한다(SHALL — 두 쓰기 사이의 충돌이 발의를 영구 무장 상태로 남기지 않게 한다). 이 따라잡기는 재시작 복구가 끝난 뒤, 관측 루프가 시작되기 전에 수행해야 한다(SHALL).

**세션 중 제출 결과로 발의를 풀 때도 같은 규칙이다.** 제출 결과가 위 두 종결 상태이거나 attempt가 기록되기 전에 끝난 경우에만 발의를 해제해야 한다(SHALL). attempt가 기록된 뒤 그 결과를 원장에 쓰지 못해 상태가 없는 결과가 돌아오면 발의를 해제해서는 안 된다(SHALL NOT — 주문은 나갔을 수 있다; 재시작 복구와 기동 따라잡기가 그 attempt를 처리한다).

**기동 단계는 엔진을 세워서는 안 된다**(SHALL NOT). 따라잡기의 한 행 실패는 그 행을 바꾸지 않은 채 기록하고 다음 행으로 가야 하며(SHALL), 재시작 복구 전체를 실패시켜서는 안 된다(SHALL NOT — 복구가 실패하면 관측 루프가 하나도 시작되지 않아 모든 포지션의 손절이 사라진다). 그 실패는 포지션 단위 key의 critical 알림으로 보고되어야 한다(SHALL — 흡수는 침묵이 아니다).

**attempt가 CONFIRMED로 종결되면 발의를 해제해서는 안 된다**(SHALL NOT — 그 주문은 실제로 나갔고, 발의를 끝내는 것은 체결 경로의 일이다).

**발의를 attempt 종결 전에 해제해서는 안 된다**(SHALL NOT — 주문이 살아 있을 수 있는 동안 해제하면 다음 관측이 그 위에 두 번째 매도를 얹는다). 이 요구는 그 규칙을 **뒤집지 않고 완성한다**: 종결 전에는 무장을 유지하고, 종결 후에는 반드시 푼다.

**근거**: 오늘 모호한 결과를 받은 발의는 무장된 채 남고, 그 상태에서 청산 정책은 손절 조건이 성립해도 **빈 전이**를 돌려준다. 그 결과 해당 포지션은 손절도 익절도 제안되지 않는 상태로 **영구히** 머문다. 재시작 복구는 attempt만 순회하므로 이 상태를 해소하지 못한다. 실측(2026-08-07): 열린 포지션 다섯 중 둘이 이 상태였고, 그중 하나는 사건 발생 이후 계속 무보호였다.

발의 해제는 **보호 기준을 바꾸어서는 안 된다**(SHALL NOT — 진입가·최초 손절·유효 손절 중 어느 것도 이 경로에서 쓰이지 않는다).

발의 해제는 **멱등이어야 한다**(SHALL — 이미 해제된 발의에 대한 재호출은 아무것도 하지 않는다).

**기동은 ACKED로 남은 발주를 기록된 번호로만 확정하고, 나머지는 명명해 알려야 한다.**

재시작 뒤 접수(ACKED) 상태로 남은 발주 attempt에 기록된 브로커 주문 번호가 있으면, 기동은 그 번호로 주문을 한 번 읽어 응답의 주문 번호가 기록 번호와 **바이트 일치**하고 응답의 종목이 **비어 있지 않으며** 발주 종목과 일치할 때 접수 확정으로 종결해야 한다(SHALL). 이 판정은 발주 직후 확인과 같은 판정 함수로 해야 한다(SHALL — 판정을 둘로 두지 않는다). 그 판정은 응답 종목이 없거나 비어 있으면 확인되지 않은 것으로 다루어야 한다(SHALL — 발주 직후 확인에도 같이 적용된다; 계약상 종목은 필수다). 그 외의 경우(번호·종목 불일치, 읽기 실패, 응답 해석 불가, 기록 번호 없음, 취소·정정 attempt, 확정 전이의 원장 쓰기 실패)에는 attempt 상태를 바꾸어서는 안 되고(SHALL NOT) 그 attempt의 id·종류·종목·intent·사유를 명명한 critical 알림을 그 attempt를 에피소드로 하는 key로 기록해야 한다(SHALL — 그 발의는 재시작마다 무장된 채 남으므로 침묵해서는 안 된다; 같은 attempt에 대한 알림은 재시작 뒤에도 같은 기록이다). 바이트 일치 외의 어떤 추론으로도 ACKED attempt를 종결하거나 모호로 올려서는 안 되며(SHALL NOT), 목록 대조 해소로 보내서는 안 된다(SHALL NOT — 지문이 같은 다른 주문의 번호로 기록된 번호를 덮어쓸 수 있다). 이 경로의 실패는 재시작 복구를 실패시켜서는 안 된다(SHALL NOT — 복구가 실패하면 모든 포지션의 관측 루프가 시작되지 않는다). 그 밖의 ACKED 정산은 해소기가 기록된 주문 번호와의 바이트 일치를 요구하게 된 뒤의 별도 change에서 다룬다.

**판정 불능으로 park된 attempt의 해소는 운영자 명령으로 제공되어야 한다.**

park(`UNRESOLVED_IN_DOUBT`)를 끝내는 운영자 명령이 있어야 한다(SHALL — 그것이 park의 유일한 출구이며, 출구가 없으면 park된 발의의 손절은 영구히 멈춘다). 그 명령은 자동 실행되지 않는 mutating 명령이어야 하고(SHALL), 운영자 신원·승인 참조·확인한 내용(note)·목표 종결 상태(접수 확정이면 브로커 주문 번호)를 요구해야 한다(SHALL). 감사 기록은 원장 전이보다 **먼저** 기록되어야 하며 감사 기록이 실패하면 아무것도 바꾸어서는 안 된다(SHALL NOT). 전이 시점에 그 attempt가 park 상태가 아니면 거절해야 한다(SHALL). 운영자가 비수용으로 닫으면 같은 명령 안에서 위의 해제 판정으로 발의를 해제해야 한다(SHALL). 이 명령은 엔진을 멈추도록 요구해서는 안 되며(SHALL NOT — 엔진 정지는 손절 정지다), 콘솔 버튼으로 노출해서는 안 된다(SHALL NOT).

**세션 중 해소는 이 change의 범위가 아니다.**

미종결 attempt를 엔진이 도는 동안 해소 절차에 넣는 것은 **별도 change로 분리한다**. 그 change는 해소 진입점의 배선, 주기와 동시 실행 상한의 실측, 그리고 park가 계정 전역 진입을 차단한다는 운영 결과의 공시를 **모두** 포함해야 한다(SHALL). 그 셋 없이 세션 중 해소를 도입해서는 안 된다(SHALL NOT).

재시작 복구의 재시작 규칙(RECORDED → NOT_DISPATCHED, DISPATCH_STARTED → IN_DOUBT)을 세션 중에 적용해서는 안 된다(SHALL NOT — 세션 중 그 두 상태는 진행 중인 전송이며, 그것을 재시작 규칙으로 종결시키는 것은 원장 위조다).

#### Scenario: 종결된 attempt가 발의를 푼다
- **WHEN** 보호 발의를 실행하려던 attempt가 접수되지 않음으로 확정되면
- **THEN** 그 발의가 해제되어 다음 관측이 같은 조건에서 다시 제안할 수 있다

#### Scenario: 접수된 주문의 발의는 유지된다
- **WHEN** attempt가 CONFIRMED로 종결되면
- **THEN** 발의는 해제되지 않는다

#### Scenario: 판정 불능으로 park된 attempt
- **WHEN** attempt가 존재도 부재도 증명되지 않아 park되면
- **THEN** 발의는 해제되지 않고 무장된 채 남으며, 운영자가 비수용으로 닫으면 그 자리에서 같은 해제 판정으로 해제된다

#### Scenario: 다른 intent의 발의
- **WHEN** 비수용으로 종결된 attempt의 intent가 현재 무장된 발의의 intent와 다르면
- **THEN** 발의는 바뀌지 않는다

#### Scenario: 종결과 해제 사이의 충돌
- **WHEN** attempt가 비수용으로 종결된 뒤 발의 해제가 기록되기 전에 프로세스가 멈추면
- **THEN** 다음 기동이 준비 신호 전에 그 발의를 해제한다

#### Scenario: 발의 해제는 손절 가격을 바꾸지 않는다
- **WHEN** 발의가 해제된다
- **THEN** 진입가·최초 손절·유효 손절은 종전 값 그대로다

#### Scenario: 이미 해제된 발의
- **WHEN** 이미 해제된 발의에 대해 해제가 다시 요청되면
- **THEN** 아무것도 바뀌지 않고 오류도 발생하지 않는다

#### Scenario: 결과를 쓰지 못한 제출
- **WHEN** attempt가 기록된 뒤 전송 결과를 원장에 쓰지 못해 상태가 없는 결과가 돌아오면
- **THEN** 발의는 해제되지 않는다

#### Scenario: 기동 단계의 한 행이 실패한다
- **WHEN** 따라잡기가 한 행을 처리하다 실패하면
- **THEN** 그 행은 바뀌지 않고 나머지 행이 처리되며 재시작 복구는 실패하지 않고, 그 포지션의 critical 알림이 발송된다

**부재 판정의 증거 모델은 매도에 대해 성립해야 한다.**

부재 판정의 매수가능금액·보유수량 delta 교차 확인은 **매수 예약**을 증거로 삼는다. 접수됐으나 미체결인 매도는 두 값을 모두 움직이지 않으므로, 그 교차 확인만으로 매도의 부재를 확증해서는 안 된다(SHALL NOT — 확증하면 살아 있는 매도를 은퇴시키고 다음 주기가 두 번째 매도를 낸다).

매도 mutation에 대해 사전 계정 기준선을 공급하려면 **매도용 부재 증거 모델이 먼저 정의되어야 한다**(SHALL). 그 모델 없이 기준선만 공급해서는 안 된다(SHALL NOT — 기준선의 부재가 park를 강제하는 현재 동작이 그 경우의 안전측이다).

기준선의 어떤 필드가 미측정인지 표현할 수 없다면 그 필드를 0으로 채워서는 안 된다(SHALL NOT — 0은 "변화 없음"과 구별되지 않아 해당 교차 확인을 침묵으로 통과시킨다).

#### Scenario: 브로커가 계약과 다른 status로 알려진 code를 낸다
- **WHEN** 주문 제출이 `opposite-pending-order-exists` code를 실은 응답으로 거절되고 그 HTTP status가 openapi가 선언한 422가 아니라 409이면
- **THEN** attempt는 code로 확정 거절 분류되어 종결하며, IN_DOUBT로 가지 않고 그 심볼의 다른 mutation을 차단하지 않는다

#### Scenario: 같은 문자열이 code가 아닌 필드에 있다
- **WHEN** 응답 본문의 `message`나 다른 필드에만 그 문자열이 있고 code 필드는 다른 값이면
- **THEN** 확정 거절로 분류되지 않는다

#### Scenario: code가 최상위에 있는 본문과 error 아래에 있는 본문
- **WHEN** 같은 code가 한 응답에서는 최상위 `code`로, 다른 응답에서는 `error.code`로 오면
- **THEN** 둘 다 같은 분류를 받는다

#### Scenario: 본문이 JSON이 아니거나 code가 없다
- **WHEN** 거절 응답의 본문을 JSON으로 읽을 수 없거나 어느 자리에도 code가 없으면
- **THEN** 이 분류는 적용되지 않고 attempt는 종전 경로로 처리된다

#### Scenario: 같은 status의 다른 code는 확정되지 않는다
- **WHEN** 재생 요청이 `409 request-in-progress`를 받으면
- **THEN** 종전대로 상한을 소비하지 않고 대기 후 재시도하거나 조회 폴백으로 전환하며, 확정 거절로 종결되지 않는다

#### Scenario: 매도의 부재는 잔고 delta만으로 확증되지 않는다
- **WHEN** 미체결 매도의 IN_DOUBT 해소에서 보유수량과 매수가능금액이 기준선과 같으면
- **THEN** 부재는 확증되지 않고 UNRESOLVED로 park한다

#### Scenario: 두 자리의 code가 다르고 status가 422다
- **WHEN** 발주 거절 응답의 status가 422이고 본문의 최상위 `code`와 `error.code`가 서로 다른 값이면
- **THEN** attempt는 확정 거절로 종결되지 않고 모호로 간다

#### Scenario: 재시작 뒤 ACKED로 남은 발주
- **WHEN** 브로커가 접수해 주문 번호가 기록된 뒤 결과를 쓰지 못한 채 프로세스가 멈췄다가 재시작하면
- **THEN** 기동은 그 번호로 주문을 한 번 읽어 번호가 바이트 일치하고 종목이 일치하면 접수 확정으로 종결한다

#### Scenario: 재시작 뒤 ACKED 발주의 읽기가 실패한다
- **WHEN** 기동이 ACKED 발주를 기록 번호로 읽다 실패하거나 다른 번호의 주문을 받으면
- **THEN** attempt 상태와 발의는 바뀌지 않고 그 attempt를 명명한 critical 알림이 기록되며, 재시작 복구는 실패하지 않는다

#### Scenario: 운영자가 park된 attempt를 비수용으로 닫는다
- **WHEN** 운영자가 승인 참조와 확인 내용을 붙여 park된 발주 attempt를 확정 거절로 닫으면
- **THEN** 감사 기록이 먼저 남고, attempt가 종결되며, 같은 명령 안에서 그 attempt가 무장한 발의가 해제된다

#### Scenario: park가 아닌 attempt의 운영자 해소
- **WHEN** 운영자 명령 시점에 대상 attempt가 이미 park 상태가 아니면
- **THEN** 명령은 거절되고 아무것도 바뀌지 않는다

#### Scenario: 읽기 응답에 종목이 없다
- **WHEN** 발주 직후 확인이나 기동 확정의 주문 읽기 응답이 기록 번호와 바이트 일치하지만 종목 필드가 없거나 비어 있으면
- **THEN** 확인되지 않은 것으로 다루어져 접수 확정으로 종결되지 않는다

#### Scenario: 재전송 ACK 의 목록 대조 실패
- **WHEN** 결과 불명 뒤 재전송이 ACK 를 받았는데 정착 전 조회에서 일치가 둘이거나 없거나 다른 orderId 이면
- **THEN** attempt 는 CONFIRMED 가 아니라 IN_DOUBT 로 남고 해소 절차가 정한다
