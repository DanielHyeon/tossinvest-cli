맥락: 실제 돈을 다루는 손절 경로. a198 은 길 치우기의 엔진 주문 취소가 처음 실제로 나가게 했고, 구현 리뷰 r2 가 「취소가 미종결(IN_DOUBT·ACKED)로 남으면 대상 주문의 종결 기록이 들어와도 그 종목의 손절이 재시작까지 막힌다 — 이전에는 취소가 안 나가 종결 기록 뒤 손절이 나갔다」 회귀를 실측했다. 보강 2: D10 은 세션 해소 실행자가 IN_DOUBT 취소를 대상 주문의 원장 종결 기록(길 치우기와 같은 술어, 소유 PLACE/AMEND intent 범위, 소유 유일, fail_closed 아님)으로 한 트랜잭션 안에서 닫는다(브로커 호출 없음, 판정 표는 resolveCancel 의 CANCELLED*→CONFIRMED · FILLED/REJECTED*→FAILED_CONFIRMED, REPLACED·비종결은 무변). D9 는 기동이 기록 번호가 있는 ACKED 취소를 그 번호로 CONFIRMED 로 마친다(읽기 없음).

찾을 것(P0/P1/P2, 파일:줄 근거, 사실과 추측 구분):
1. 원장의 종결 기록만으로 취소 attempt 를 닫는 것이 살아 있는 주문 위에 손절(초과 매도·이중 매도)을 내게 하는 경로 — 종결 표현의 반례: 부분 체결 뒤 잔량, 정정(REPLACED·already-modified), 주문 번호 재사용(다른 날·다른 계좌·다른 방향), fail_closed, 소유 모호, legacy 빈 범위 스냅숏, lineage 로 바뀐 현재 번호(target_order_id)와 소유 attempt 의 broker_order_id 의 관계.
2. 기동이 ACKED 취소를 CONFIRMED 로 마치는 것이 틀린 주문 번호를 확정하거나 살아 있는 주문을 치움으로 읽게 하는 경로(a094 가 PLACE 에서 철회한 이유가 CANCEL 에도 해당하는가; D8 의 매수 치움과 결합; CANCEL_REJECTED 레코드).
3. 세션 실행자와 디스패치·체결 감지·길 치우기·flatten 프로세스의 resolveCancel 사이의 경합(같은 attempt 를 두 곳이 종결, 판독과 쓰기 사이의 창, 한 트랜잭션 설계가 실제로 닫는가).
4. flatten(Saga.settleStep·classifyCancel·resolveStep·planLiquidation)과 기동 복구(Recovery.Run·confirmAcked·resolveCancel)·a165 latch·예약 해제에 주는 영향, 비상 청산의 즉시성.
5. 정본 MODIFIED 가 기존 문장(같은 Requirement 의 다른 문단·시나리오, exit-policy)과 모순되는 곳, ADDED 의 Scenario 가 시험 가능한가.
