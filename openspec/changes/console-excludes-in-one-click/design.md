# Design: console-excludes-in-one-click

## D1. 왜 별도 라우트인가 — 전체 폼 저장을 재사용하지 않는다

`/settings/save`는 폼 전체를 읽어 블록을 통째로 다시 쓴다. 거기에 심볼 하나를 더하려면
호출자가 나머지 세 값(enabled · default_stop_pct · include)을 **정확히 되돌려 보내야**
하고, 그 왕복이 바로 `LoadRawEngineAdoption`이 막으려 했던 유실 경로다.

`/settings/exclude`는 `handleSettingsInclude`와 같은 형태다 — 서버가 스스로 Load하고,
한 필드만 바꾸고, Save한다. 클라이언트는 심볼 하나만 보낸다. 폼이 보내지 않은 값은
폼이 잃을 수 없다.

## D2. 제외가 이미 관리 중인 포지션의 손절을 벗기지 않는다 (§0.4)

이것이 이 change에서 확인해야 했던 단 하나의 안전 질문이다. `judgeHoldings`는

```go
if p.ExitEligible() {
        if p.Adopted() { d.checkExternalIncrease(ctx, p) }
        continue          // ← 제외 판정보다 앞이다
}
...
if d.opts.Adoption.Excludes(symbol) { unmanaged = append(...); continue }
```

이미 exit 자격이 있는 포지션은 제외 판정에 **도달하지 못한다**. 따라서 제외 클릭은
살아 있는 손절을 절대 벗기지 못한다. 스펙이 이미 같은 사실을 다른 말로 적어 뒀다 —
"exclude 추가는 이미 편입된 포지션에 무효".

그 무효성의 귀결이 D5다.

## D3. 상호 배제의 방향은 위험 비대칭을 따른다

엔진은 제외를 편입보다 우선한다. 두 목록에 동시에 오른 심볼은 편입되지 않는다.
따라서 동시 등재는 **아무 효과 없는 편입 지정을 화면이 성공으로 보고하는 상태**다.
없애야 하지만, 두 방향의 자동화는 위험이 다르다.

| 전이 | 방향 | 처리 |
|---|---|---|
| 편입된 심볼을 **제외** | 보수(엔진이 덜 한다) | 같은 저장에서 편입 지정을 함께 내린다. 자동. 공지에 명시 |
| 제외된 심볼을 **편입** | 확장(엔진이 더 한다) | 자동으로 제외를 풀지 않는다. 행에서 편입 컨트롤을 감추고 "제외를 먼저 해제"를 안내 |

확장 방향을 자동화하지 않는 이유: `exclude_symbols`는 오래전에 "이건 절대 건드리지
마"라고 적어 둔 목록일 수 있고, 그것을 푸는 것은 편입 지정과 다른 결정이다. 두 번의
클릭(제외 해제 → 편입)은 마찰이 아니라 **서로 다른 두 결정**이다.

## D4. 제외는 손절폭을 발명하지 않는다

`handleSettingsInclude`는 `default_stop_pct`가 없으면 5%를 채워 넣는다. 그래야 하는
이유는 UX가 아니라 검증이다 — `Adoption.validate()`:

```go
if !a.Enabled && len(a.IncludeSymbols) == 0 && a.DefaultStopPct == 0 { return "" }
```

**include 목록**이 비어 있지 않으면 블록이 "의미 있는" 것이 되어 손절폭 검증을 부르고,
채우지 않으면 `SaveEngineAdoption`이 저장을 거부한다. `ExcludeSymbols`는 그 조건에
없다 — 제외만 있는 블록은 검증을 부르지 않는다.

그러므로 제외 경로는 `DefaultStopPct`를 **읽은 그대로 둔다**. 채워 넣으면 운영자가
고르지 않은 손절 숫자가 파일에 남고, 나중에 편입을 켤 때 그 숫자가 이미 거기 있다.
전용 테스트로 못박는다.

## D5. 관리 중인 행에는 제외 컨트롤을 두지 않는다

D2에 따라 그 클릭은 아무 효과가 없다. 효과 없는 버튼은 두 가지로 나쁘다 — 운영자가
보호를 껐다고 믿거나(위험), 껐는데 안 됐다고 믿는다(혼란). 그 행에는 컨트롤을 두지
않고, 여러 심볼을 한 번에 손보는 고급 접힘의 목록 편집은 그대로 열려 있다.

컨트롤이 붙는 행의 조건은 편입 컨트롤과 **정확히 같다**:
`CanDesignate ∧ InBroker ∧ ¬Managed ∧ ¬Unknown`. 조건이 하나면 두 컨트롤이 어긋날 수
없다.

## D6. 화면이 감춘 것은 강제가 아니다

제외된 행에서 편입 체크박스를 렌더하지 않는 것은 UI 결정이지 접근 제어가 아니다.
`/settings/include`로 직접 POST하면 여전히 도달한다. 그 경로에서 지정을 거부하지는
않는다(거부는 마찰이고, 기록 자체는 무해하다 — 엔진이 편입하지 않는다). 대신
**공지가 사실을 말한다**: "제외가 우선하므로 편입되지 않는다". 오늘의 공지는
"편입 예약됨 — 상시 규칙이다"이고, 그것은 제외된 심볼에 대해 거짓이다.

## D7. 라벨 세 번째 상태

`Label()`에 "관리 제외"를 더한다. 이유는 장식이 아니다 — 한 번의 클릭이 무엇을 바꿨는지
행이 말하지 않으면 운영자는 클릭이 먹었는지 알 수 없고, 엔진의 미관리 알림은 이미
"지정되지 않아서"와 "의도적으로 뺐으므로 보호하지 않는다"를 다른 문장으로 구별한다.
화면이 그 구별을 지우면 알림과 화면이 서로 다른 말을 한다.

판정 순서는 엔진과 같게 **제외 먼저**다.

## D8. 감사 기록은 이미 있다

`consoleAdoptionSettings.Save` → `recordAdoptionSave`가 네 설정을 기록하고 그중
`console.adoption.exclude_symbols`가 이미 있다. 새 감사 코드는 없다. 엔진 기동 시의
`interlock.go` 기록이 두 번째 흔적으로 남는 구조도 그대로다.
