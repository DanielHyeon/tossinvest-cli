## 응답
References `design`, `delta`, and `tasks` refer to files under the reviewed change directory.

1. **MAJOR — Binding creation loses disputes accumulated while insertion was pending.**  
   D2 accumulates identities and taint only for symbols **already having bindings** (`design.md:204–213`). Counterexample: missing order A creates a pending block; insertion fails; a later comparison reports missing B or a quantity dispute, but insertion fails again; a clean comparison finally retries successfully. The retained block still carries A because `Observe` preserves the first block on key collision (`internal/reconcile/mismatch.go:719–724`), and retries pending blocks even on clean comparisons (`:760–767`). The new binding contains A alone, without the earlier disqualification. Two subsequent clean comparisons can release it. This reopens first-round #2’s pending-retry case.  
   **Change:** Retain pending identities/taint separately from release-authorizing bindings, then transfer them only after proven insertion; alternatively, permanently exclude retried pending blocks from this release path. Add both counterexamples to `tasks.md:29–34`.

2. **MAJOR — External-position taint can disappear through the clean branch’s authority-error return.**  
   D2 updates history at the **blocking** branch entrance and after persistence (`design.md:210–213`). External positions do not make `BlocksEntry()` true (`internal/reconcile/mismatch.go:574–581`). An eligible binding plus a pending permanent proposal can therefore observe an external position, enter the clean branch, and return on authority failure before either update (`:637–647`). Once that observation disappears, later clean comparisons can release the binding despite the mandatory lifetime disqualification (`delta:7–8`; `design.md:200,256`). C9 protects only the current comparison.  
   **Change:** Accumulate existing-binding history before **either** branch can return. Extend the authority-error test (`design.md:406`) to external-position-only comparisons, not just blocking quantity disputes.

3. **MAJOR — Reusing a Tracker across `Restore` preserves release authority.**  
   D6 explicitly leaves `Restore` unchanged (`design.md:303–306`), but existing `Restore` resets streaks and credits, not the proposed bindings or arms (`internal/reconcile/mismatch.go:954–966`). Bind → arm → `Restore` on the same object → later clean comparison can release the restored row because its ID and digest still match. The planned restart test uses a **new** Tracker and misses this (`design.md:397`). This contradicts the stated exclusion of restored blocks (`design.md:129–131,188–190`; `delta:36–38`).  
   **Change:** Explicitly clear bindings and arms under the Restore lock; update D8/D11, proposal impact, and tasks to include that edit. Test same-object Restore. Separately clarify that ordinary `Refresh` preserves an existing proven binding for the same row; it merely cannot **create** one. Otherwise the blanket “Refresh blocks excluded” wording contradicts D6 and the production refresh-before-observe sequence (`internal/app/engine/reconcileloop.go:447–453`).

4. **MINOR — The normative release scenario omits the accepted conservative watermark interval.**  
   Design C12 rejects fills committed between watermark acquisition and insertion (`design.md:265,271–273`), and explicitly tests this (`:404`). The delta describes only fills **after insertion**, while its two-comparison scenario unconditionally requires release (`delta:7–12,26–28`). A legitimate fill in that interval therefore satisfies the written scenario but must remain blocked under the design.  
   **Change:** Define eligibility against the pre-insert watermark in the delta and qualify the release scenario with all retention conditions.
