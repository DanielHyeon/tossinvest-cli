`PrecheckQFinalCampaignFirstLeg` compares sealed strategy terms to risk entry/stop/target and owner/campaign and produces a canonical `RiskIntent` with Guardian q_final. Atomic `RecordQFinalCampaignFirstLeg` creates decision, Guardian and bucket reservations, immutable strategy lineage and campaign/leg binding in one transaction. Existing q_final/min caps and monetary FX provenance must be reused. `RiskIntent.PolicyVersion` is Guardian identity, not exit policy. Immutable v2/v3 strategyflow risk binding identity includes strict canonical JSON, so reinterpreting it or silently changing its serialization breaks replay.

`ExitObserver.openState` reads durable RiskIntent entry/stop but currently chooses the first exit policy from current `opts.CommonPolicy`. `OpenExitState` validates `PolicyIdentity` against pinned policy meaning, writes the initial stop baseline, and existing exit state thereafter supplies persisted policy. Position adoption branches before lookup. Exit wiring's sellable cap comes from existing authoritative path. Existing campaign `entry_blocked` and RECONCILE state are durable and checked by dispatch; `latchCampaignLinkConflict` is transaction-local and specific to order-link conflicts, not a general recovery API. Existing exit snapshot quarantine prevents all judgement including stop; never use it to suppress a valid admitted snapshot.

## Minimum candidate design for Manager approval

1. Snapshot the existing configured exit policy's kind, pinned ID/version/digest at the production authority boundary; pass it into first-leg precheck and include it in the first-leg idempotency binding. No config/default change. Check validity before issue; missing or mismatch refuses new admission without submitting an order.
2. Use a new v4 strategyflow journal-binding payload containing the exit policy snapshot; maintain separate exact v2/v3 decoding and byte-identical historical hashes. Its immutable lineage and existing first-leg atomic transaction bind it to decision, campaign, Guardian quantity and reservations without rewriting rows. Include snapshot in replay identity; atomic rollback on failure. v4 is a durable marker distinguishing new campaigns from legacy ones; schema change may be unnecessary if existing payload suffices, but confirm reader and strict-JSON compatibility before committing to this design.
3. At pre-dispatch issuance/claim, independently re-read and verify exact v4 binding, not caller DTO or current configuration; new v4 missing/mismatch refuses dispatch. Preserve legacy v2/v3 in-flight handling explicitly rather than pretending old rows have a snapshot.
4. For an engine-entered v4 position, resolve exact entry decision/campaign/position generation, validate admitted v4 snapshot, seed existing `OpenExitState` with its policy identity and RiskIntent stop, and continue the existing exit/sellable path. Changed current config alone is not a mismatch; the admitted policy wins. Adopted and legacy existing campaigns continue their old behavior and are never backfilled. Existing exit states remain untouched.
5. Actual post-fill binding mismatch with a valid admitted snapshot needs a durable, idempotent, transactionally scoped campaign entry latch and reconciliation/operator event while normal protection still evaluates the admitted stop. Existing campaign order-conflict latch cannot be used unmodified. Ensure a crash between latch and initialization cannot allow additional exposure; do not create flatten behavior. If admitted snapshot cannot be recovered or authenticated, do not invent it: block exposure and explicitly report unprotected/unknown; preserve any already-existing protection. Exact event, alert and transaction boundaries require Manager approval and tests.
6. Bound only a148 RR diagnostic's own numerical inputs with a 64-character signed-decimal grammar before existing shared parser. Empty fields retain unknown; nonempty invalid inputs produce invalid. Cover both planned and filled paths, signed PnL, exponent/radix and oversized values; leave lane.go and sealed v1 untouched.

## Mandatory test design

RED/GREEN tests: policy configuration changes between admission and first exit; exact replay and altered snapshot; pre-submit missing/mismatched snapshot; rollback and restart; legacy v2/v3/adopted compatibility; partial fills, duplicate events and blocked later exposure; valid admitted stop still evaluated after mismatch, authoritative sellable limits respected, protection failures visible; no wider stop or invented fill rejection; quantity caps/FX/zero behavior retained. Supplement with decimal input resource-bound adversarial tests. Existing runtime tests and full gate required; no live order, measurement, config or restart.

## Feasibility and unresolved no-send race

`ClaimStrategyDispatchLease`, `Attempt.beginStrategyDispatchTx` and `BeginStrategyDispatchSubmitting` serialize journal writes and call `validateStrategyDispatchClaimAuthority`, which already checks campaign `entry_blocked=0`. They refuse an unstarted lease when a campaign latch committed first. The Gateway then calls `RequireCurrentStrategyDispatchTransportAuthority` before broker `plan.call`; that method checks owner, lease and expiry, but not the campaign latch, and its transaction ends before the call. A latch can commit between the final check and broker transport. Even adding a DB recheck cannot eliminate that interval.

`Gateway.withStrategyEntryGateAuthority` holds `EntryGate.mu` during the final check and broker call. Coordinating mismatch handling with that same gate may serialize a process-local latch with transport, but requires deliberate wiring/lock-order analysis, fail-closed persistence-failure handling, and evaluation across other processes; a journal transaction alone cannot prove this ordering. A send that already crossed the fence cannot be retroactively blocked or called refused. It needs existing in-doubt/reconciliation treatment. Therefore a complete strict no-new-send guarantee is **not yet proven** and cannot be claimed from the current primitives.

A positive new-contract marker independent of the optional snapshot (for example additive first-leg column, written atomically) can distinguish new missing/corrupt data from pre-existing v2/v3 rows. A genuinely non-strategy historical position has no first-leg binding, but missing rows alone are not proof of legacy origin. Confirm a reliable origin discriminator before designing the fallback. Also decide how failed latch persistence is fenced across restart without disabling a still-valid protective exit.


## Approved implementation resolution

The design now uses an immutable v4 decision marker and a separately persisted admitted policy, with legacy markers preserved. Final authority reads the durable latch and binding in a consistent journal transaction; an authorization already past that read remains possibly in flight. No network lock or retroactive refusal is claimed. Foreign-generation binding is rejected. A wider same-generation existing stop is raised through the normal monotone snapshot path using a floor-specific CAS; the first orderable observation is explicitly suppressed without clearing pending orders, and a later actual observation performs normal order evaluation. A stale or unselectable candidate preserves the existing snapshot. These changes address the historical discovery concerns above; reviews and final gate remain separate.
