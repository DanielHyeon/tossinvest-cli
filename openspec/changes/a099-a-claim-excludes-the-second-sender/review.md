## 1.1 ⛔⛔ 가장 무거운 발견 — a099는 crash 경로를 **오늘보다 나쁘게** 만든다 (B-P1)

내가 직접 확인했다.

```go
// notifier.go:194
sent, owed, err := n.claimAndDeliver(ctx, record, e)
...
// notifier.go:217
if owed && !sent { n.escalate(ctx, e) }
```

`claimAndDeliver`의 `!owed` 분기(B4 `:266` → 이탈 `:274`)는 `false, false, nil`을 돌려주고
**게이트를 안 잠근다.** 게이트를 잠그는 것은 **오류 분기 B3 `:261-263`뿐이다.**

| 단계 | a099 설계대로면 |
|---|---|
| 1 | 발송자 A가 claim한다 |
| 2 | A가 publish 전에 죽는다 |
| 3 | 행은 PENDING이고 임차는 살아 있다 |
| 4 | 재시작한 B가 같은 조건을 관측한다 → **`owed=false`** |
| 5 | `claimAndDeliver`가 조용히 반환 — **래치 없음** |
| 6 | `owed && !sent`가 거짓 — **escalate 없음** |
| 7 | **미전달 critical 알림이 있는데 신규 진입이 열린다** |

**오늘은 이렇게 안 된다.** 임차가 없으므로 4단계에서 `owed=true`가 나오고 그냥 보낸다.

`!owed`의 오늘 의미는 *"운영자가 이미 받았다"*이고(`:267-268`의 주석), a099는 거기에
*"다른 발송자가 들고 있다"*를 **같은 값으로** 밀어 넣는다. **두 사실은 안전 성질이 반대다.**

> **이것이 설계 결함이지 문서 결함이 아니다.** 구현 전에 잡혔다는 것이 게이트가 한 일이다.

## 1.2 A-P1·A-P2 — 4단계 순서의 전제가 두 군데 틀렸다

**A-P1**: *"a098이 배제 없는 두 번째 발송자를 만든다"*는 **a098의 현재 형태에서는 거짓이다.**
확인했다 — `&obs.Notifier{}` 생성처는 `exitwiring.go:73` 하나뿐이고
(`gateway.go:280`이 유일한 호출), `internal/enginelock`의 flock이 두 번째 엔진 프로세스를
거부한다. a098의 루프가 `Notifier.Flush`를 부르면 **같은 `n.mu`가 가른다.**

**A-P2**: 그런데 그 형태는 **정지를 지연시킨다.** `Flush`는 `PendingAlerts(ctx, 0)`으로
전부를 받아 `n.mu`를 쥔 채 행마다 publish한다. a092가 이미 그 지연을
`N × publish timeout`으로 유도했고 **N에 상한이 없다.**

**그래서 a098에는 두 형태가 있고 둘 다 오늘 안전하지 않다.**

| a098의 형태 | 배제 | 정지 지연 |
|---|---|---|
| (i) `Notifier.Flush`를 부른다 | `n.mu`가 한다 | **`N × publish timeout`** — 불변식 4 위반 |
| (ii) `n.mu` 밖에서 보낸다 | **아무것도 안 한다** | 없음 |

**a099가 없애는 것은 (ii)의 위험이다.** 즉 a099는 「a098이 발송자를 만드니까」가 아니라
**「a098이 (ii) 형태여야 하고, (ii)는 원장 배제를 요구하니까」** 필요하다.
proposal의 서술을 그렇게 고쳐야 하고, **a098의 proposal §범위 1이 명시적으로
`Notifier.Flush`를 부른다고 적고 있으므로 그것도 고쳐야 한다.**

### 3.2 ⛔⛔ B-P2 — spec Requirement 1이 이 설계로 **달성 불가능**하다

만료 임차와 fencing token은 **원격 publish를 fence하지 못한다.**

```text
A가 claim → SIGSTOP / 긴 GC / VM 정지
54초 뒤 B가 만료 임차를 탈취 → publish (전화기에 1회)
A가 재개 → 자기 publish 실행       (전화기에 2회)
그 뒤에야 A의 정산이 token 불일치로 거부된다
```

**a099가 「정산 CAS는 publish 뒤에 도니까 이중 발송을 못 막는다」로 기존 CAS를 반증했는데,
그 논리가 자기 token CAS에 그대로 걸린다.** 토큰은 원장 쓰기를 fence하지 네트워크
전송을 fence하지 않는다.

spec `:12-29`는 *"정확히 하나만 발송 권한을 얻는다"*를 무조건으로 적는다. **거짓이다.**

선택은 둘뿐이다.

| 안 | 무엇 | 비용 |
|---|---|---|
| (a) sink idempotency | 전송 수단이 중복 요청을 삼키게 한다 | ntfy에 그런 키가 없다 — 전송 수단 계약을 바꿔야 한다 |
| (b) **요구를 낮춘다** | *"유계 실행·유효 임차 아래에서 한 발송자. crash·시계 도약에서는 at-least-once"* | 규범이 약해지지만 **참이 된다** |

**이것은 a099가 무엇을 약속하는지를 바꾼다 — 사용자 결정이다.**

### 3.3 ⛔⛔ A-P1 — D10이 정상 경합에서도 게이트를 영구 잠근다

내가 리뷰와 **독립적으로 같은 것을 찾았고** A가 코드로 확정했다.

`EntryGate.Block`(`retry.go:498-505`)은 reason별 **단일 메모리 래치**이고 자동 해제가 없다.
해제는 운영자 `Acknowledge` → `Gate.Clear`뿐이다(`notifier.go:506`).

| 원장이 보는 것 | 실제 | D10의 처리 |
|---|---|---|
| 「유효한 임차를 남이 보유」 | A가 **정상 발송 중** | 게이트 잠금 ← **틀렸다** |
| 「유효한 임차를 남이 보유」 | A가 **죽었다** | 게이트 잠금 ← 맞다 |

**둘은 경합자 입장에서 구분되지 않는다.** 그래서 a098 루프가 정상 발송 중일 때 동기
관측이 스치기만 해도 진입이 잠기고, **A가 성공적으로 정산해도 그 래치를 푸는 경로가 없다.**

**정상 동작이 신규 진입 정지와 수동 개입을 만든다.** 1라운드 B-P1을 고치면서 반대쪽
실패를 만들었다.

기존 `TestConcurrentObservationsOfOneConditionSendOnce`
(`a096_one_send_per_condition_test.go:249`)는 **발송 수만 보고 게이트를 안 봐서**
이 회귀를 통과시킨다.

- 프로덕션 `Flush`·`Acknowledge` 호출자 0, Notifier 생성점 하나, flock이 두 번째 엔진

- 기존 테스트 기준선은 전부 통과한다
  (`journal` 400s · `obs` · `engine` 90s · `execgw` 59s).
- **`openspec validate --strict`와 `check_analysis`는 위 결함을 하나도 못 잡는다.**

**BLOCK.** §3 RED에 들어가면 **잘못된 상태기를 테스트로 고정하게 된다.**

그리고 이 라운드가 드러낸 것은 개별 결함보다 **패턴**이다.

> 1라운드가 준 자리(D3·D4·spec)를 고쳤는데 **같은 값의 사본**이 D5·D6·tasks·a098·
> function-logic map에 살아남았다. 기억 「정정의 단위는 값이다」가 적은 실패를
> **연속으로 두 번** 했다.

**그래서 다음은 문서 패치가 아니다.** 두 보이스가 각각 같은 처방을 냈다 —
A-T1 *"API와 상태기를 먼저 확정하고 11개 map을 다시 작성하라"* ·
B-P5 *"하나의 typed API와 SQL을 설계 정본에 완전히 적고 모든 문서에서 동일하게 쓰라"*.

**상태기와 API를 하나로 확정하는 것이 먼저이고, 문서·map·tasks는 그것에서 유도한다.**

사용자 결정이 필요한 것 넷은 §3.8에 적는다.

### 3.8 사용자 결정 넷 (2026-08-11)

사용자가 `1-1, 2-1, 3-1, 4-1`로 답했다. 아래가 그 결정이고, **§4 이후 모든 문서는

| # | 결함 | 결정 | 무엇이 바뀌나 |
|---|---|---|---|
| 1 | **B-P2** — 만료 임차는 원격 publish를 fence하지 못한다 | **요구를 낮춘다** | spec Requirement 1을 *"유계 실행·유효 임차 아래에서 한 발송자"*로 한정하고, crash·시계 도약에서는 **at-least-once**임을 규범에 적는다 |
| 2 | **A-P1** — D10의 게이트 래치가 정상 경합에서 영구 잠긴다 | **게이트를 원장에서 유도한다** | 경합자가 추측해서 잠그지 않는다. **미전달 critical 행의 존재 자체가 barrier**이고 기동 시에도 복원된다 |
| 3 | **A-P10 = B-P6** — a099 단독 배포는 오늘보다 나쁘다 | **a099 + a098을 한 배포 단위로** | 4단계 → **3단계**. 배달 루프가 곧 재claim 주체다 |
| 4 | **A-P11 = B-P6** — 운영자 표면이 없다 | **`tossctl` CLI** | a098이 승인·목록 명령을 낸다. 콘솔 UI는 안 건드린다(2026-07-27 지시) |

#### 결정 1이 규범에 남기는 것

낮춘 요구가 **약한 요구**가 되면 안 된다. 세 문장으로 가른다.

| 조건 | 보장 |
|---|---|
| 두 발송자가 **유계 실행** 아래에서 경합한다 | **정확히 하나만** 보낸다 — 이것은 그대로 SHALL |
| 발송자가 **정지·GC·VM 일시정지**로 임차를 넘겨 잃는다 | 이미 나간 publish는 못 되돌린다. **정산은 반드시 거부된다** |
| 그 결과 | 알림이 **두 번 보일 수 있다**. 한 번도 안 보이는 것보다 낫다(불변식 4·6) |

**"보장한다"와 "거부한다"를 분리하는 것이 요점이다.** 원장은 이중 *정산*을 절대
허용하지 않고, 이중 *발송*은 유계 실행 밖에서 허용한다. 1판은 둘을 한 문장에 넣어
**거짓인 규범**을 만들었다.

#### 결정 2가 D10을 대체하는 것

| | 1판 (기각) | 결정 2 |
|---|---|---|
| 게이트를 잠그는 근거 | **경합을 관측했다** (추측) | **원장에 미전달 critical 행이 있다** (사실) |
| 푸는 주체 | 없다 — 운영자가 수동으로 | `Acknowledge`가 이미 하는 그것 (`notifier.go:506`) |
| 정상 경합에서 | **영구 래치** | 아무 일도 없다 |
| 기동 직후 | 메모리라 비어 있다 | **원장을 읽어 복원한다** |

`EntryGate.Block`은 reason별 메모리 래치이고 자동 해제가 없다(`execgw/retry.go:498-505`).
그 성질은 **원장이 진실을 들고 있을 때만** 안전하다.

#### 결정 3이 D9를 대체하는 것

`Flush`의 프로덕션 호출자가 0이므로 a099 단독으로는 **claim 뒤 죽은 행을 다시 집을
주체가 없다.** a098의 배달 루프가 그 주체다. 두 change는 **같은 배포에서 함께 나간다.**
각자 자기 gate를 통과하지만 **중간 상태로 배포하지 않는다.**

#### 결정 4가 a098에 남기는 것

`ReasonAlertUndelivered`는 자동으로 안 풀린다. 운영자 승인 경로가 없으면 복구 후에도
진입이 막히고 **재시작이 사실상 유일한 해제**가 된다. a098이 `tossctl` 하위 명령으로
목록·승인을 낸다. **타이핑 확인·추가 승인 마찰은 넣지 않는다.**

`EntryGate.Block`은 메모리 래치다(`execgw/retry.go:497-515`). tasks 4.3c는 재평가를
**경합·발송 실패·ACK** 경로에만 뒀다. **성공 경로에 없다.**

1. 아직 안 보낸 PENDING 행 때문에 C6이 게이트를 막는다
2. 원래 발송자가 **정상 정산한다** → count 0
3. **`Clear`를 부르는 자리가 없다** → 래치가 영구히 남는다

**2판 D10을 깼던 A-P1이 3판 C6에서 형태만 바꿔 되살아났다.** R23은 그래서 회귀 핀이
아니라 **실제 RED**다.

### 4.4 ⛔ A-P5 = B-R12 — 내 자체 발견이 절반만 맞았다

2라운드 뒤 내가 `claim_expires_at`을 없앴다. 근거는 *"쓰이기만 하고 읽히지 않는 열"*.
**진단은 맞았고 처방이 틀렸다** — 읽는 쪽을 그 열로 바꾸는 것이 답이었다.

C4는 `Options.AlertLease`를 **인스턴스마다 주입**한다. `journal.Options`는 인스턴스
단위다(`journal.go:34-68`). 그러면:

```text
A가 90초 lease 설정으로 claim → claimed_at = T
B가 같은 DB를 60초 설정으로 연다
T+60에 B의 판정: claimed_at <= now-60 → 만료로 보고 훔친다
A는 자기 90초 안에서 여전히 publish한다 → 이중 발송
```

**1라운드 B-P4가 깬 것과 같은 모양이다** — *"경합자가 들고 온 값으로 남의 임차를
판정하지 않는다."* 값이 인자에서 인스턴스 설정으로 옮겨갔을 뿐 권위는 여전히
**판정하는 쪽**에 있다.

### 4.5 A-P3 = B-P5 — CLI는 실행 중 엔진의 게이트에 못 닿는다

사용자 결정 4로 `tossctl`을 골랐다. `EntryGate`는 **실행 중 엔진 프로세스의 메모리
맵**이고(`retry.go:497-515`) 그 포인터는 엔진 `Context` 안에 있다(`engine.go:178`).
별도 프로세스가 원장을 ACK해도 **그 맵에 닿지 않는다.**

운영자가 마지막 행을 승인해도 **엔진의 래치는 남고, 재시작이 유일한 해제**가 된다 —
19라운드 B-P8이 잡은 바로 그 상태다. a098 4.6은 *"첫 tick"*만 적는다.

그리고 A-P3은 **원자성**도 짚는다. 오늘 승인 경로는 `n.mu` 아래에서 ACK·count·clear를
묶고, **그 이유가 코드에 적혀 있다**(`notifier.go:470-488`). a092 규범도
*"미전달 수를 읽고 게이트를 푸는 판단은 나눌 수 없는 하나"*를 요구한다. a098의 루프는
**의도적으로 `n.mu`를 안 쓴다** — 그 사이에 새 PENDING이 들어오면 게이트가 잘못 열린다.

### 4.6 A-P4 — 기동 복원을 「첫 tick」에 둔 것은 늦다

`Runtime.Run`에는 **모든 루프보다 먼저** 도는 `Recover` 단계가 있다
(`runtime.go:155-160`). 루프들은 그 뒤 goroutine으로 **동시에** 시작한다(`:261-283`).
전략 루프가 배달 루프의 첫 tick보다 먼저 스케줄되면 **신규 진입이 통과한 뒤에**
게이트가 잠긴다. a098 spec의 *"다시 차단된 상태로 올라온다"*를 어긴다.

### 4.9 A-P7 — C7과 spec의 경계가 다르다

C7은 예외를 *"정지·긴 GC·VM 일시정지"*로 한정한다. spec은 그것을 *"그 밖의 경우"*
전체로 넓히고 **at-least-once라고 부른다.** 거짓이다 — publisher가 죽어 있거나 실행자가
없으면 **한 번도 전달되지 않는다.** 시계 도약도 규범 표에서 빠졌다.

**규범이 「보장」을 쓰는 자리는 전송이 언젠가 성공한다는 전제가 필요한데 그 전제가 없다.**

### 4.12 결론

**BLOCK.** 그리고 이번 라운드가 드러낸 것은 2라운드와 **같은 패턴이 더 깊은 층에서**
반복됐다는 것이다.

> 2라운드: 자리를 고쳤는데 값의 사본이 살아남았다.
> 3라운드: **정본 절을 만들었는데 같은 문서의 요약표와 map이 안 따라왔다.**

정본을 만드는 것으로는 부족하다. **정본과 사본을 기계가 대조해야 한다** —
`check_analysis`도 `openspec validate`도 이것을 못 잡는다는 것이 세 라운드로 증명됐다.

그리고 더 무거운 것: **A-P1은 내가 사용자 결정 2를 확대 해석해 승인된 규범을 뒤집은
것이다.** 결정은 *"경합으로 래치하지 말고 원장에서 유도하라"*였지 *"해제를 자동화하라"*가
아니었다. 사용자 결정이 필요한 것 셋은 §4.13에 적는다.

### 4.13 사용자 결정이 필요한 것 셋

#### 결정 5 — 진입 게이트를 어디까지 바꾸는가 (A-P1 · A-P2 · A-P3)

내가 사용자 결정 2를 **확대 해석**했다. 결정은 *"경합으로 래치하지 말고 원장에서
유도하라"*였는데, 나는 **차단과 해제를 둘 다** 유도로 바꿨다. 해제 쪽은 오늘보다
**덜 보수적**이고 승인된 정본(`openspec/specs/engine-safety/spec.md:147-152`)을 어긴다.

| 안 | 차단 트리거 | 해제 트리거 | 대가 |
|---|---|---|---|
| **(a) 최소** | **오늘 그대로** — 발송 실패. **경합에는 안 잠근다** | **오늘 그대로** — 운영자 승인 + 0건. 단 **엔진 안에서 재평가**해 CLI 승인이 닿게 한다 | 규범 변경 0. `MODIFIED` 불필요. **R5를 버린다** |
| (b) 차단만 강화 | **미전달 critical 행이 있으면** 잠근다 | 오늘 그대로 | **critical 알림 하나마다 사람이 승인해야 진입이 열린다** — 제품 동작이 크게 바뀐다 |
| (c) 완전 유도 | 미전달 행이 있으면 | **0건이면 자동** | main spec을 `MODIFIED`로 명시해야 하고, count↔clear **원자성**을 새로 설계해야 한다 |

**(a)를 추천한다.** 사용자 결정 2가 실제로 요구한 것(경합 래치 제거)을 정확히 하고,
기동 복원 구멍도 닫으며, 승인된 규범을 안 건드린다. (b)·(c)는 결정 2의 범위 밖이다.

**(a)를 고르면 같이 닫히는 것**: A-P2(성공 뒤 영구 차단 — 애초에 안 잠그므로 없다) ·
A-P3의 원자성(오늘 `n.mu` 계약을 그대로 쓴다) · R23(다시 회귀 핀이 된다) ·
R5는 등록부에서 빠진다.

**(a)에서도 남는 것**: CLI 승인이 실행 중 엔진에 닿는 배선과, 기동 복원을
**`Recover` 단계**(첫 tick이 아니라)에 두는 것. 둘 다 a098이 진다.

#### 결정 6 — 임차 기간의 권위를 어디에 두는가 (A-P5 = B-R12)

**내 자체 발견이 절반만 맞았다.** `claim_expires_at`이 *"쓰이기만 하고 읽히지 않는
열"*이라는 진단은 맞았고, **없애는 처방이 틀렸다.**

| 안 | 어떻게 | 대가 |
|---|---|---|
| **(a) 만료를 저장한다** | 발급자가 `claimed_at + lease`를 계산해 `claim_expires_at`에 쓴다. **판정은 저장값으로만.** 역행 판정은 `claimed_at`으로. **열 넷** | 열이 하나 는다. 대신 **판정하는 쪽의 설정이 남의 임차를 재해석하지 못한다** — B-P4의 원래 논거를 그대로 만족 |
| (b) lease를 하나로 못 박는다 | 주입을 금지하고 패키지 상수 하나. **열 셋 유지** | C4의 「살아 있는 설정에서 계산」이 사라진다. 설정이 바뀌면 임차가 조용히 어긋나는 원래 문제로 돌아간다 |

**(a)를 추천한다.** 임차의 권위는 **발급 시점**에 있어야 하고, 그것을 표현하는 방법이
저장된 만료다. (b)는 「동일 DB의 모든 claimer가 동일·불변 lease를 쓴다」는 **배포 계약**을
사람이 지켜야 하는데, 그 계약을 기계가 검사할 방법이 없다.

#### 결정 7 — 공동 배포를 무엇이 강제하는가 (P-4, 두 보이스 공통)

`gate.sh`는 change ID 하나만 받고 그 change의 `tasks.md`만 검사한다
(`gate.sh:67`·`:83`·`:103`). **a099+a098을 묶은 것은 문장뿐이다.**

| 안 | 어떻게 | 대가 |
|---|---|---|
| **(a) 짝 gate** | `gate.sh`에 짝 change를 선언하는 자리를 만들고, 짝의 task가 전부 `[x]`가 아니면 실패시킨다 | 도구를 조금 고친다. 두 change의 리뷰 granularity는 유지 |
| (b) 한 change로 합친다 | a099와 a098을 하나로 | 기계가 자동 강제. 대신 스키마+engine+cmd가 한 High-risk change가 되고 번들·번호를 다시 잡아야 한다 |
| (c) 문서 선언만 | 오늘 상태 | **기계 강제 없음.** 사람이 잊으면 a099만 나간다 |

**(a)를 추천한다.** (c)는 두 보이스가 각각 결함으로 지목했다.

### 6.1 결정 9-2가 왜 `MODIFIED`를 없애 주는가 — 원문으로 확인했다

> **⛔ 이 절의 결론은 §8이 뒤집었다.** 아래는 4판 시점의 기록으로 남긴다 —
> 지우면 다음 라운드가 같은 논증을 다시 세운다. **무너진 자리는 첫 행 하나이고,
> 둘째 행(`stops`에 안 쓴다)은 지금도 참이다.**

승인된 `openspec/specs/engine-safety/spec.md:168`이 거는 것 둘의 **주어가 같다.**

| 조항 | 주어 | 보조 실행자에게 걸리는가 |
|---|---|---|
| *"루프 집합은 reconcile driver·exit observer·체결 감지다(SHALL)"* | 이름 셋 = `SupervisedLoop.Name` | **아니오** — `LoopNames()`(`runtime.go:236`)의 결과가 안 는다. **⛔ 다만 그 결과는 셋이 아니라 넷이다 — 5라운드 A-T1·A-P1** |
| *"**루프가** 취소 외의 사유로 반환하면 전체 런타임이 정지"* | `stops` 채널(`runtime.go:281`·`:297`) | **아니오** — 보조 실행자는 거기 안 쓴다 |

**판정이 아니라 배선이 그 성질을 준다.** 3판은 *"감독 루프로 등록한 뒤 이 이름이면 다르게
다룬다"*였고, 그것은 **판정이 틀리면 무너지고 정본도 바꿔야 했다.** 등록하지 않으면
**틀릴 판정이 없다.** 더 적은 편집으로 더 강한 성질이다.

> **⚠ 남는 읽기 하나를 숨기지 않는다.** *"루프 집합"*을 「런타임이 띄우는 goroutine 전부」로
> 읽으면 보조 실행자도 거기 들어가고 `MODIFIED`가 필요해진다. **좁은 읽기를 골랐고**
> 근거는 같은 문장이 셋을 **이름으로** 열거한다는 것이다. **넓은 읽기가 옳다면 델타가
> 부족하다** — 5라운드가 이 자리를 먼저 본다. a098 design D8.1에 같은 문장으로 적었다.

### 6.2 결정 8-1이 강제한 것 — 새 ReasonCode 하나 (그리고 Pre-Edit 확대)

**결정을 받자마자 3판 Pre-Edit이 거짓이 됐다.** 3판 D3은 *"`internal/execgw` 전부
안 건드린다"*였는데, 여섯 번째 트리거는 **자기 사유 코드를 가져야 한다.** 실측 근거:

| 사실 | 근거 |
|---|---|
| 오늘 다섯 자리가 전부 `ReasonAlertUndelivered` 하나를 쓴다 | `notifier.go:262`·`:379`·`:404`·`:482`·`:511` |
| `Acknowledge`는 미전달 0이면 **그 코드의 래치를 푼다** | `notifier.go:507-512` |

즉 같은 코드를 쓰면 **운영자가 밀린 행을 전부 승인하는 순간 「보낼 주체가 없다」는 차단도
함께 풀린다.** 보낼 주체는 여전히 없는데 진입만 열린다 — **a098의 전제가 그 자리에서

| 번들 | AST | 왜 필요했나 |
|---|---|---|
| `internal-app-engine--newruntime` (신설) | 분기 12 · 이탈 7 · 호출 13 | 9-2가 만든 **조립 시점 검증 자리** |

### 6.4 개정이 드러낸 새 위험 하나 — 결정 9-2의 유일한 대가

`Runtime.Run`의 doc(`runtime.go:258-260`)이 계약을 적는다:

> *"when this returns, every goroutine it started has returned too. That is what lets the
> caller close the journal immediately afterwards without racing a loop that is still writing."*

배달 실행자는 **원장에 쓴다**(claim·정산). 감독 집합 밖으로 빼면 `wg`가 그것을 안 담으므로
**기다리는 자리를 따로 안 만들면 이 계약이 깨진다.** 그것을 적어 두지 않으면
「감독 밖으로 뺐다」가 조용히 원장 손상 경로가 된다.

> **⛔ 이 자리의 첫 답이 틀렸고, 사용자 지적으로 고쳤다 (같은 날).**
> 처음에는 **`auxWG`를 새로 만들고 `:300` 옆에 `auxWG.Wait()`를 더한다**고 적었다.
> 그것은 **위험을 없애는 게 아니라 옮기는 것**이다 — 새 WaitGroup은 잊을 수 있는
> 자리를 **둘**(`Add`와 `Wait`) 만든다.
>
> **고친 답: 보조 goroutine을 기존 `wg`에 넣는다.** `wg.Add(1)`/`defer wg.Done()`는
> 감독 루프와 똑같이 쓰고 **`stops`에만 안 보낸다.** 그러면 `wg.Wait()`(`:300`)가
> **이미** 그들을 기다리고, `Runtime.Run`의 편집은 **range 하나로 끝난다** —
> 계약을 다시 구현하지 않고 **물려받는다.**
>
> 채널 산술도 확인했다: `stops` 버퍼가 `len(Loops)`(`:275`)이고 **송신자는 여전히
> 감독 루프뿐**이므로 `first := <-stops`(`:297`)에 보조 실행자가 안 나타나고
> `drain(stops)`(`:302`)도 안 막힌다.
>
> **「위험이 사라졌다」고는 안 적는다** — `wg.Add(1)`을 빼먹으면 여전히 깨진다.
> 줄어든 것은 **자리의 수**이고, **R14가 그 한 자리를 잰다.**

같은 결론에서 `recover`도 나왔다 — **패닉을 안 잡으면 배달 실행자의 패닉이 프로세스를
죽이고, 그것은 손절 루프까지 죽인다.** 즉 *"배달 실행자의 정지가 다른 루프를 내려서는
안 된다"*가 **패닉 경로에서 거짓**이 된다(R15).

## 7. 5라운드 (2026-08-11) — 보이스 A 판정 **BLOCK** (P4 · T5)

보이스 B는 이 절을 쓰는 시점에 **아직 실행 중**이다. 아래는 A만의 기록이고,
B가 끝나면 중복 제거 후 이 절을 갱신한다. **B의 결과를 미리 적지 않는다.**

### 7.1 A가 무너뜨린 것 — 9-2 방어의 전제가 거짓이었다

**측정은 옳았고 결론이 틀렸다.** 19판이 막으려던 것 —
*"미전달 critical 알림이 그대로인데 신규 진입이 다시 열린다"* — 는
a098의 **다른 요구가 이미 막는다**: 「재시작이 진입 차단을 푸는 우회로가 되어서는
안 된다」가 기동 시 **원장의 미전달 행**을 보고 잠근다(4.6).

**막아야 할 것은 원장이 막고, 막지 말아야 할 것만 메모리와 함께 사라진다.**

|---|---|---|---|
| 미전달 행이 남아 있다 | 막힌다 | **막힌다** (4.6) | 같다 |

인용하지 않는다 — 배선이 고쳐져도 결론이 그대로여야 하기 때문이다.

### 8.3 결정 12-2 — 「미배정」이 아니라 **「반대」**다. 값 단위로 다시 쓸었다

### 11.1 ⛔⛔ 제목의 주장이 자기 테스트로 증명되지 않았다

경합을 보지, 직렬화된 SQL 두 개가 배제되는지를 보지 않는다. 1491건 통과는 사실이고

| 자리 | 결함 | 출처 |

| `notifier.go` 반납 | 취소된 ctx 로 반납 → 종료 중 **항상** 실패 | 구현자 · security · api-contract · performance |
| `outbox.go` ack | 정산 4경로 중 유일하게 임차를 안 지움 → 토큰이 백업마다 복사됨 | security · api-contract · data-migration |
| `deliver` 실패경로 | `SettleNotFound`(원장이 "오류"라 못박은 값)를 평범한 경합으로 강등 | maintainability · api-contract |
| 반납 시점 상실 | 루프 안/반납 때가 정반대 결론 → 운영자 승인 직후 진입 재차단 | security · codex |
| `Flush` | `_, _ =` 로 정산·반납 결과 전부 폐기 | 구현자 · maintainability · api-contract · codex |
| lease vs 예산 | 독립 설정 넷, 비교하는 코드 없음 — 기본값에서만 참 | security · api-contract · codex |

전부 고쳤다. 근거와 고친 모양은 design **D14.2 / D14.3 / D14.5**.

### 11.3 `ClaimHeldElsewhere` — D10 은 옳고, 전제가 바뀌었다

D10 이 *"경합 ≠ 이미 전달됨"*으로 이 분기를 세운 것은 그대로 맞다. 4라운드가
더한 사실은 **오늘 이 분기에 닿는 원인이 하나뿐**이라는 것이다: 프로덕션 Notifier 는
`exitwiring.go:73` 하나이고 `Notifier.Flush` 는 프로덕션 호출자가 **0**이다
(`.Flush(` 55건 전부 bufio/csv/http). 그러므로 실제 원인은 "정상 경합"이 아니라
**"누가 죽었다"**이고, 그때 info 한 줄은 틀린 답이다.

codex 가 여기서 한 걸음 더 갔고 그 지적이 맞다: **만료는 수동이다** — 다음 claim 때만
평가된다. 조건이 한 번만 관측되고 회수 워커가 없으면 그 알림은 81초가 아니라
**무기한** 안 나간다.

**그 회수는 a099 가 지지 않는다.** a098 이 배달 루프 change 이고, 사용자 결정
(2026-08-10, 안 1)으로 *"배선 하나만"* 한다고 고정돼 있다. a099 안에 루프를 만들면
그 결정을 뒤집는다. a099 가 지는 것은 **그 상태를 만들지 않는 것**(D14.2 반납 고침)과
**보이게 하는 것**(Warn + `claim_expires_at`)까지다. 잔여는 D9 의 공동 배포가 닫는다.

### 11.4 반증한 것 — 교차 모델 합의

| 가설 | 기각 근거 |
|---|---|
| 두 프로세스의 read-then-UPDATE 가 SQLITE_BUSY 교착 | `journal.go:216` `_txlock=immediate` — 쓰기 락을 앞에서 잡는다. 업그레이드 교착이 없다 |
| RFC3339 를 TEXT 로 비교하는 것이 틀릴 수 있다 | `fills.go:1955` — 항상 UTC·고정폭 `Z`. 사전식 = 시간순 |
| PENDING 행 재무장이 임차를 지워 두 번 발송 | `outbox.go:379` `case AlertPending: return true, false` — PENDING 은 재무장 대상이 아니다 |
| 승인된 행의 유령 임차가 운영자 화면에 뜬다 | `PendingAlerts` 는 `WHERE state = PENDING`, `LookupAlert` 는 호출자 0. **노출 경로 없음** |

넷째는 내가 먼저 기각했고 security 리뷰가 **다른 각도**(토큰이 백업에 실려 나간다)로
되살렸다. 각도가 다르면 같은 코드가 다시 결함이 된다 — 기각도 각도째로 적어야 한다.

토큰 자체는 문제 없다: `crypto/rand` 256비트, 로그·발행·프로세스 경계 어디에도 안 나간다.
`=` 비교가 상수시간이 아니라는 지적은 리뷰어 스스로 5/10 "조치 불필요"로 달았다.

### 11.5 배포 제약 둘이 새로 붙었다

codex 단독 신규 — **이미 열려 있는 v30 프로세스는 임차를 통째로 우회한다.**
`ErrSchemaTooNew` 는 그 뒤에 여는 프로세스만 막는다. 그리고 스키마 31 은 저널 단위로
단방향이라 **바이너리만 되돌리는 것은 롤백이 아니라 장애다.**

둘 다 코드로 못 막는다. design **D14.6** 과 `deploy-pair.txt` 주석에 적었다.

### 11.6 남긴 것 (`not-applicable` 사유)

- **반납 시점 상실의 `markErr != nil` 경로**는 테스트로 도달할 수 없다. `Notifier.Journal`
  이 구체 타입(`*journal.Journal`)이라 원장 쓰기를 실패시킬 seam 이 없다. 고침은 넣었고
  (두 발견 시점이 같은 결론을 낸다) 그 분기만 핀이 없다. **침묵한 생략이 아니라 여기 적는다.**
- **`migrate` 루프에 상한이 없다**(data-migration, conf 8): 미래에 단계를 추가하며 상수를
  안 올리면 저널이 열 수 없게 된다. a099 는 `migrate` 를 안 건드렸다 — **a099 diff 밖**이라
  이 change 에서 안 고친다. 후속으로 넘긴다.
- **`claim_age_ms` 가 두 시계를 뺀다**(testing, conf 8): 테스트에서 Notifier 는
  `clock.System()`, 저널은 fake 다. 프로덕션은 둘 다 System 이라 살아 있는 결함은 아니고,
  고치려면 테스트 배선을 바꿔야 해서 이 라운드에 안 넣었다.

### 11.7 이 라운드가 **리뷰가 아니라 리뷰의 테스트**를 쓰다가 찾은 것

`lineFor` 헬퍼가 `engine.alert_claim_held` 줄을 못 찾아서 테스트가 실패했다.
고침이 안 들어간 줄 알고 로그를 덤프했더니 **줄은 있었다.** 못 찾은 것은 헬퍼였고,
못 찾은 이유가 결함이었다.

`Logger.emit` 은 이미 `event` 에 줄 자신의 이름을 쓴다. 호출부가 `FieldEvent` 로 한 번
더 넘기면 JSON 에 같은 키가 두 번 나오고, **모든 파서가 뒤엣것을 취한다.** 그래서
a099 가 더한 이벤트 셋은 자기 이름 대신 촉발 조건을 `event` 로 보고했고, 운영자가
`event == "engine.alert_claim_held"` 로 건 규칙은 **영원히 안 맞았다.**

> 이 change 의 `event.go` 가 이 셋을 따로 만든 이유가
> *"a line that means three things cannot be alerted on"* 이다.
> 그 줄들이 자기 이름조차 달고 있지 않았다는 것은 같은 병의 더 깊은 판이다.

**a099 안의 14곳을 `trigger_event` 로 옮겼다.** a099 밖 3곳
(`publishBestEffort` · `notifyCritical` · `escalate`)은 **되돌렸다** — 같은 결함이지만
그 함수들은 a099 diff 밖이라, 고치면 FLM 증거 범위가 그쪽으로 번진다.

> ⚠ **후속으로 남긴다: `EventAlertUndelivered` 줄도 같은 병을 앓는다.**
> 그것은 이 시스템에서 가장 중요한 운영자 줄이고, 지금 자기 이름 대신 촉발 조건을
> 보고한다. a099 가 만든 결함이 아니고 a099 가 고칠 자리도 아니지만,
> **찾았으므로 적는다.** 침묵한 생략은 금지다.

### 11.8 테스트를 통과했다고 증거가 되지 않는다 — 두 번 확인했다

- **새 경합 테스트**는 통과한 뒤에 **실패시켜 봤다**(D14.1 의 뮤테이션). 통과만 보고
  넘어갔으면 "핸들을 나눴다"는 사실이 곧 "새 경로를 짚는다"는 주장이 됐을 것이다.
- **전체 스위트의 종료 코드**는 뒤에 붙인 `echo` 의 것이었다. 알림이 `exit code 0` 이라고
  했지만 그것은 `echo` 가 성공한 값이다. 실제 출력을 읽어서 `8160 passed in 99 packages`
  를 확인했다. **같은 착각을 이 change 에서 이미 한 번 했다.**
