# 착지 지점 후보와 위조 가능성 (task 1.3)

2026-09-09 측정. base 는 다섯 change 가 전부 `448dfeb1` 로 같다.

## 먼저 나온 반증 — 이 다섯에는 **고칠 target 이 없다**

| 구간 | 바뀐 Go 파일 |
|---|---|
| `448dfeb1..840b3377` (a074~a079 재기준화 커밋) | **0** |
| `448dfeb1..7f8b1ae7` (a075·a076 아카이브 커밋) | 449 |
| `448dfeb1..1687baac` (HEAD) | 449 |
| `448dfeb1..워킹트리` (오늘의 동작) | 449 |

`448dfeb1..840b3377` 사이의 커밋은 **하나**이고(`git rev-list --count` = 1) 그것이
`840b3377` 자신, "chore(sdd): rebaseline a074-a079 after strategy merge" 다. 그 커밋이
고친 33개 파일은 `ast.json` 23 · `base-commit.txt` 6 · `function-logic-map.md` 2 ·
`branch-test-map.md` 2 이고 **Go 파일은 0** 이다. 즉 base 를 옮기면서 AST 를 다시
뽑고 분기를 재번호했다 — proposal 이 두 문단 앞에서 경계한 바로 그 절차다.

즉 **2026-08-04 재기준화가 base 를 이 다섯의 Go 작업보다 뒤로 옮겼다.** 확인:
a074 가 증거를 낸 `ExitObserver.record` 는 그 번들의 `ast.json` 이 말하는 대로
`internal/app/engine/exitloop.go:1018` 에 있고, 그 함수는 `448dfeb1` 에 **이미 있다**
(`git grep "func (o \*ExitObserver) record" 448dfeb1 -- internal/app/engine/exitloop.go`).

따라서 이 다섯에 대해 `changed_existing_functions(448dfeb1, T)` 는
- T 가 자기 작업의 착지 지점이면 **빈 집합**이고,
- T 가 그 뒤면 **남의 change 작업**이다.

"이 change 가 고친 함수" 를 되돌려 주는 T 는 **없다.** proposal 이 그렇게 적었고 그것은
틀렸다. 이 change 가 이 다섯에 주는 것은 *올바른 질문*이 아니라 *답할 수 있는 질문*이다 —
요구 집합이 비고, 번들은 `validate_target` 으로 계속 검사된다.

`sdd-workflow` 가 base 불변을 SHALL 로 요구하므로 base 쪽에서 고칠 수는 없다. 남은
레버는 target 쪽뿐이고, 그 레버로 얻는 것이 위 문단이다. 이것을 **조용히** 통과시키면
안 된다 — 요구 집합이 비었는데 번들이 있으면 도구가 그렇게 말해야 한다(task 3.3).

## 후보

### 후보 A — 파생: change 디렉터리를 마지막으로 만진 커밋

값을 적지 않으므로 위조할 값이 없다. 그러나 **측정에서 떨어진다.**

| change | 파생 착지 | base→착지 Go 파일 |
|---|---|---|
| a074 · a077 · a079 | `840b3377` | 0 |
| a075 · a076 (아카이브됨) | `1687baac` | 449 |

아카이브 커밋과 그 뒤 문서 커밋이 디렉터리를 만지므로, 아카이브된 change 에서는
파생값이 HEAD 로 끌려가 **오늘과 같은 실패**를 낸다. 회귀 픽스처가 바로 그 둘이다.
게다가 진행 중 change 는 워킹트리의 커밋 안 된 Go 편집이 요구에서 빠진다 — task 2.2
가 고정하려는 것과 반대다. **기각.**

### 후보 B — merge 커밋

base→merge 는 본선이 그 시점까지 받은 **모두**를 담는다. a112 병합 `62b35779` 를 쓰면
449 파일이 그대로 온다. 좁히려는 것을 안 좁힌다. **기각.**

### 후보 C — 아카이브 커밋

아카이브는 남의 작업이 착지한 뒤에 온다. 후보 A 의 아카이브 행이 정확히 이것이다
(`7f8b1ae7` → 449). **기각.**

### 후보 D — 선언: `landed-commit.txt` (채택)

change 의 작업이 착지한 커밋을 파일에 적는다. `base-commit.txt` 와 같은 모양이고,
작업이 착지한 **뒤** 커밋에서 쓴다(닭-달걀은 이 순서로 풀린다 — a075 는 `840b3377`
에 착지하고 `7f8b1ae7` 에서 아카이브됐다).

## 위조 방식과 그것을 막는 판정

값을 적을 수 있으면 그 값이 5단계를 통과시키는 유일한 손잡이가 된다. 먼저 위조 방식을
적는다.

| 위조 | 결과 | 막는 판정 |
|---|---|---|
| 존재하지 않는 커밋 | 도구가 던진다 | `rev-parse --verify <v>^{commit}` |
| base 보다 앞선 커밋 | `git diff` 가 역방향 — 지운 함수를 요구 | base 가 조상이어야 한다(같아도 된다). a077 이 실제로 여기 걸린다 |
| base 와 같은 커밋 | 요구 집합 = ∅ | ~~`!=` 로 막는다~~ — **철회**, 아래 §정정. 번들이 고정하므로 안전하고 a074·a079·a075 의 정답이다 |
| freeze 직후 커밋(구간의 바닥) | 요구 집합이 임의로 작아진다 | **번들이 고정한다** — 아래 §정정 |
| 착지한 적 없는 커밋(버려진 갈래) | 게이트가 존재하지 않는 이력을 판정 | 착지가 HEAD 의 조상이어야 한다 |
| 진짜 착지보다 **뒤**의 커밋 | 요구 집합이 커진다 | 막지 않는다 — 더 엄해질 뿐 안전하다 |

마지막 행이 이 설계의 비대칭이다. 느슨해지는 방향만 막고 엄해지는 방향은 둔다.

**존재 검사가 아니어야 한다.** `landed-commit.txt` 가 *있으면* 통과하는 판정은 위 표의
2·3·4·5 행을 전부 놓친다. task 2.4 의 변이가 그것이다.

## 정정 — 신원 검사를 증거 검사로 바꾼다 (2026-09-09, 1차 적대 리뷰)

처음 적은 판정 (4) 는 "착지 커밋의 트리에 이 change 의 `base-commit.txt` 가 같은
내용으로 있다" 였다. **그것은 존재 검사다.** `base-commit.txt` 는 proposal freeze 에
쓰이고 spec 이 **불변**을 SHALL 로 요구하므로, 그 판정은 "파일이 생긴 뒤"만 고른다 —
구간의 바닥이 착지가 아니라 freeze 다. 저자는 바닥을 고르면 된다.

재현했다. a112 base `aeeb209e`, 고른 착지 `5c5efec7`:

| 구간 | Go 파일 |
|---|---|
| base → 진짜 착지 `62b35779` | 135 |
| base → 고른 착지 `5c5efec7` | **12** |
| 숨는 비테스트 Go(`5c5efec7..HEAD`) | **48** |

숨는 48개에 `internal/journal/schema.go` · `strategy_lane_latch_v32.go` ·
`internal/app/engine/strategy_market_coordinator.go` · `internal/positioncampaign/*`
가 들어간다 — `.claude/CLAUDE.md` §5 의 High-risk 경로다.

**대신 이렇게 한다.** 착지 커밋에서 그 change 의 모든 `revision: current` 번들의
`source_sha256` 이 맞아야 한다. 저자는 자기 증거가 기술하는 리비전밖에 못 고른다.

| a112 후보 | 132개 번들 중 불일치 |
|---|---|
| `5c5efec7` (위조) | **43** — 거절 |
| `62b35779` (진짜) | **0** — 통과 |

그리고 이 판정은 유일한 답을 고른다. 후보 수십 개 중 전 번들이 맞는 커밋은 하나다:

| change | 번들 | 후보 | 전부 맞는 커밋 |
|---|---|---|---|
| a074 | 7 | 48 | 1 (`448dfeb1`) |
| a077 | 7 | 32 | 1 (`6b47be2f`) |
| a079 | 4 | 51 | 1 (`448dfeb1`) |
| a075 | 8 | 61 | 1 (`448dfeb1`) |

같은 이유로 `validate_target` 도 워킹트리가 아니라 착지 커밋에서 해싱해야 한다. 그
둘이 갈리면 하나는 착지를, 하나는 오늘을 기술하는 두 정본이 된다
([[two-judgements-cover-for-each-other]]).

착지가 base 와 **같아도** 안전해졌다 — 번들이 고정하므로 저자가 고를 수 없다. 위 표의
"base 와 같은 커밋" 행은 그래서 철회한다. a074·a079·a075 의 정답이 바로 그 경우다.

## 기록하지 않은 change

`landed-commit.txt` 가 없으면 오늘과 똑같이 워킹트리와 비교한다. 진행 중 change 의
판정이 이 change 때문에 바뀌면 안 된다(task 2.2).
