# a197 Design

## 0. a094 D−2.4 의 선행 조건 넷을 어떻게 갖는가

| 선행 조건(a094 design D−2.4) | 이 change 의 답 |
|---|---|
| ① 외부 주문의 귀속 규칙 — 무엇이 「이 포지션의 보호를 막는 주문」인가, 불완전·미지 주문은 거절 | D2·D3 |
| ② 다른 포지션·사람의 보호 매도는 취소하지 않는다 | D2(매수만) |
| ③ 공표된 OPEN 스냅숏 계약 — 신선도, 「비어 있음」과 「읽지 못함」의 구분, 실패 처리, 비차단 | D4·D5. 스냅숏을 공유·공표하지 않는다 — 거절 직후 그 자리에서 읽고 그 자리에서 쓰고 버린다(신선도 = 읽기 시작부터 취소 전송까지) |
| ④ 취소 사실의 감사 기록 | D6 |

## 1. 결정

| # | 결정 | 근거 |
|---|---|---|
| D1 | **여는 조건(전부)**: 토글 켜짐 ∧ 발의가 보호 손절(`isProtective(proposal)`) ∧ 그 제출이 `FAILED_CONFIRMED` 이고 사유가 `ReasonOppositePendingOrder`. 그 밖의 거절(호가 단위·장 시간·수량)과 익절에서는 열리지 않는다 | 브로커가 「반대 미체결이 있다」고 말한 뒤에만 읽는다 — 손절의 첫 제출 앞에 브로커 왕복을 더하지 않는다(정본 「손절 경로에 브로커 조회를 더하지 않는다」의 정신). 추측으로 사람 주문을 지우지 않는다 |
| D2 | **대상**: 같은 계좌·시장·종목의 미체결 주문 중 방향이 매수이고, 주문 번호가 있고, 엔진 원장에 그 주문 번호의 귀속(접수 확정 attempt)이 **없는** 것 전부. 매도는 대상이 아니다 | 브로커의 거절 사유는 「반대 방향 미체결의 존재」다(openapi 409 설명, 실물 3 건 — 조사 인용). 가격 교차·수량 조건은 저장소에 근거가 없으므로 매수 전부를 대상으로 한다. 엔진 귀속 매수는 기존 길 치우기가 이미 취소한다 |
| D3 | **하나라도 모르면 전부 안 한다**: 목록의 어느 행이든 방향·주문 번호·종목을 읽을 수 없으면, 또는 목록을 끝까지 읽지 못하면(오류·시한 초과·다음 쪽이 남음) 그 주기에는 아무것도 취소하지 않는다. 대상 0 건(매수가 없음)도 취소 0 이다 | 미지의 주문 위에서 일부만 치우면 무엇이 남았는지 모른다. 「비어 있음」(읽었고 매수 없음)과 「읽지 못함」을 다른 결과로 돌려준다 |
| D4 | **읽기는 시한을 가진다**: 미체결 목록 조회 전체에 시한 3 초(상수), 재시도 없음. 시한 안에 못 읽으면 「읽지 못함」 — 다음 거절 주기가 다시 시도한다 | 이 단계는 exit 관측 루프 안에서 돈다. 다른 포지션의 판정이 이 읽기 뒤에 서므로 상한이 있어야 한다(불변식 4). 3 초의 근거: 관측 주기 5 초보다 짧음. (AST/영수증 정정 2026-11-23: R7 은 OPEN 목록을 재지 않았다 — 단건 GET p99 는 accounts 569ms(max 4,171ms)·holdings 282ms·prices 252ms 이고 문서 결론은 「R7 p99 ≤ 0.6s」, OPEN 목록은 「cursor/limit 무시·전량 1요청」(M7) — `verify-execution-capability/analysis/retry-matrix-slo-2026-10-22.md:27,46,47`. 3 초는 그 p99 의 5 배이고 관측 max 보다 짧다.) tasks 3.8 에서 가짜 브로커로 상한을 잰다 |
| D5 | **비차단의 한계를 공시한다**: 읽기(≤ 3 초)와 취소 제출이 도는 동안 같은 루프의 다른 포지션 판정은 그만큼 늦는다. 기존 길 치우기의 엔진 주문 취소도 같은 성질이다. 별도 실행자로 떼지 않는다 | KISS. 이 단계가 열리는 것은 손절이 이미 거절된 포지션이 있을 때뿐이고, 그 주기에 한 번이다. 별도 goroutine 은 게이트웨이의 종목 단위 직렬화와 취소·제출 순서를 다시 설계해야 한다 |
| D6 | **감사**: 취소는 기존 취소 경로(`Issuer.IssueReduction` → 게이트웨이 취소)로 내어 원장에 결정·취소 attempt 가 남는다. 사유 문장은 「손절을 막는 외부 매수 주문 <주문 번호> 취소(포지션 <id>)」. 취소를 낸 주문마다 critical 알림 1(알림기의 critical 기록 단일 입구, key = 타입·포지션·주문 번호, 재알림 창 0) | 사람의 주문을 엔진이 지웠다는 사실은 운영자가 반드시 알아야 한다. 알림이 꺼진 엔진은 일반 등급 기록(기존 규칙) |
| D7 | **취소 뒤**: 매수 취소는 접수로 치운 것으로 본다(정본의 기존 규칙 — 초과 매도 방향이 아니다). 발의는 종전대로 해제되고 다음 주기가 손절을 다시 낸다. 취소가 거절·모호면 그 주문은 남고, 다음 거절 주기가 다시 연다 | 기존 흐름(`submit` default 갈래의 해제 → 재발의)을 바꾸지 않는다. 새 상태기계를 만들지 않는다 |
| D8 | **토글**: 설정 칸 하나(예: exit 정책 설정의 `cancel_external_opposite_buy`, 정확한 자리·이름은 tasks 1.4 에서 기존 토글 관례를 보고 정한다), 기본 false. false 면 브로커 조회 0·취소 0·기존 알림만. 변경은 기존 설정 audit 경로로 기록된다 | 안전 불변식 2·5·7. 운영 flip 은 사람이 한다 |
| D9 | **알림 문장(토글 무관)**: `alertProposalRefused` 가 사유가 `ReasonOppositePendingOrder` 이면 본문을 「이 종목에 매수 미체결 주문이 있어 브로커가 손절을 거절했다. 앱에서 그 주문을 취소해야 손절이 나간다」로, 브로커가 거절한 그 밖의 경우(`FAILED_CONFIRMED`)에는 「브로커가 거절했다」로 말한다. key·등급·재알림 창은 그대로 | 오늘 문장 「브로커에 닿기 전에 거부됐다」는 브로커 거절에 거짓이다(조사 인용). key 를 바꾸지 않으므로 알림 수는 그대로다 |
| D10 | **재제출 간격은 넣지 않는다** | a094 Q4-6 「새 간격 없음(즉시성)」 유지. 간격은 사람이 주문을 치운 뒤의 손절을 늦춘다 |

## 2. 순서 (한 주기)

```text
손절 제출 → 브로커 409/422 code=opposite-pending-order-exists → FAILED_CONFIRMED, Reason=opposite_pending_order_exists
  ├ (기존) alertProposalRefused — D9 문장
  ├ (신규, 토글 켜짐 ∧ 보호 손절일 때만) 외부 반대 매수 치우기
  │     미체결 목록 읽기(≤3s) ─ 읽지 못함/미지 행 → 취소 0, 결과 로그
  │                          └ 읽음 → 엔진 귀속 아닌 매수마다: 취소 제출 → 접수면 critical 알림 1
  └ (기존) 발의 해제(ProposalRefused) → 다음 관측 주기가 손절 재발의
```

치우기의 실패는 발의 해제를 막지 않는다(해제는 기존 규칙이 정한다). 치우기 안의 오류는 삼키지 않고 로그·기존 지연 경보 재료로 남긴다 — 구체 자리는 tasks 1.3 의 AST 를 보고 정한다.

## 3. 거절·침묵하는 정상 입력

- 토글 꺼짐: 전부 오늘과 같음.
- 익절·사다리 부분 청산이 같은 사유로 거절: 치우기 안 열림(알림 문장만 D9).
- 미체결 목록에 식별 불완전 행: 취소 0. 그 포지션의 손절은 사람이 치울 때까지 계속 거절된다 — 기존 동작과 같고 알림이 원인을 말한다.
- 목록에 매수가 없음(브로커가 거절했는데 매수가 안 보임 — 조건주문·타 채널 가능성): 취소 0, 결과 로그 한 줄. 이름 붙인 잔여.

## 4. 시험 전략 (RED 먼저)

새 시험 파일 `internal/app/engine/a197_external_opposite_buy_test.go`(실 원장 임시 경로 + 가짜 브로커 미체결 판독기·가짜 게이트웨이, 기존 `a094_exit_clear_test.go` 하네스 재사용):

1. 토글 켜짐, 보호 손절이 반대 미체결로 거절, 목록에 외부 매수 1 → 취소 제출 1(그 주문 번호), 원장에 취소 attempt, critical 알림 1, 발의 해제, 다음 주기 손절 제출 성공.
2. 토글 꺼짐 → 판독기 호출 0, 취소 0, 알림은 D9 문장 1, 재발의는 종전대로(places=2 — `a094_exit_clear_test.go:794` 의 기존 단언과 같은 모양).
3. 외부 매수 2 + 외부 매도 1 → 매수 둘만 취소, 매도 무접촉.
4. 엔진 귀속 매수가 목록에 있음 → 이 단계는 그것을 취소하지 않는다(귀속 판정), 외부 매수만.
5. 식별 불완전 행 1(주문 번호 없음 / 방향 미지) + 외부 매수 1 → 취소 0.
6. 판독 오류 · 시한 초과(가짜 시계/블로킹 판독기) · 다음 쪽 남음 → 취소 0, 그 주기의 루프가 시한 안에 끝남.
7. 목록에 매수 0 → 취소 0, 결과 로그.
8. 익절 발의가 같은 사유로 거절 → 판독기 호출 0.
9. 다른 거절 사유(호가 단위 등 `dispatch_rejected_by_broker`) → 판독기 호출 0.
10. 취소가 거절/모호 → 알림 없음(취소 접수 알림은 접수에만), 다음 거절 주기에 다시 시도.
11. 같은 주문에 대한 critical 은 주문 번호당 1(주기 반복에도).
12. 알림 제목·본문·필드에 계좌 정보 0. 주문 번호는 원장·로그에만 두고 시스템 밖 알림 본문에는 싣지 않는다(종목 표시와 건수만).
13. 한 주기의 브로커 요청 수 상한 계측(조회 쪽 수 + 취소 수) — design D4 의 실측.
14. `a087_submit_structure_test` 등 `submit` 구조 고정 시험 무편집 통과(깨지면 Manager 에게).

변이(전부 CAUGHT): 토글 검사 삭제 · 보호 손절 조건 삭제 · 사유 조건 삭제 · 매수 조건 삭제(매도도 취소) · 귀속 제외 삭제 · 미지 행 가드 삭제 · 「읽지 못함」을 「비어 있음」으로 · 시한 삭제 · 알림 key 에서 주문 번호 삭제.

선택 시험: `./internal/app/engine -run 'A197|A094|A087|ExitClear|ProposalRefused'`, `./internal/execgw -run 'Refusal|Cancel'`, 설정 패키지의 토글 시험. `-race` 는 `-run A197` 만.

## 5. 운영 (사람 승인)

1. 배포 뒤 토글은 꺼진 채다. 켜기 전에: 한 종목에 사람 매수 미체결을 두고 손절이 걸리는 상황을 만들 수는 없으므로(LIVE 주문 금지) 시험 증거와 design 을 사람이 읽고 flip 한다.
2. flip 뒤 첫 발생 때 원장의 취소 attempt·알림·손절 접수 시각을 `review.md` 에 시각·상태만 기록한다.

## 6. 잔여·후속

- 브로커가 거절했는데 미체결 목록에 매수가 없는 경우(§3 마지막).
- 미체결 조회의 실제 지연 분포는 운영에서 미측정이다(시한 3 초는 기존 조회 SLO 에서 유도).
- 장 마감 뒤 재제출, 거절 사유가 Reason 에서 사라지는 `order-hours-closed`(조사 인용 #11) — 별도 후보.
- 취소한 매수 주문을 사람이 다시 넣으면 같은 일이 반복된다 — 알림이 그것을 말한다.

## 7. 보류와 재개 조건 (Manager 결정 2026-11-23)

> a197 은 freeze 하지 않고 보류한다. 아래는 재개 때 설계에 반영할 결정이며, 본문 D1~D10 은 지금 고치지 않는다. 근거: `analysis/probe/probe-output.txt`, `analysis/cited-ast/README.md` (b), `analysis/review/proposal-freeze-r1-codex.md`.

- **선행 1**: a198 착지(취소 결정이 주문 경로를 통과하고 실제 게이트웨이를 거치는 시험이 생긴다). a197 의 외부 취소도 그 발행 경로를 쓴다.
- **선행 2(r1 #3)**: 이 단계가 낸 취소가 IN_DOUBT 로 남으면 다음 주기 길 치우기가 손절을 막고, CANCEL 은 세션 중 해소되지 않는다 — 사람이 매수를 치운 뒤에도 손절이 재시작까지 늦어질 수 있다. 재개 전에 「세션 중 CANCEL IN_DOUBT 해소」(a193 design §7-3 후속)를 선행으로 둘지, 이 단계의 취소가 모호해지면 그 포지션에서 이 단계를 다시 열지 않고 critical 로 올리는 것으로 닫을지 Manager 가 정한다.
- **재개 시 설계 변경(결정됨)**:
  - (r1 #2) 그 종목에 엔진의 미종결 또는 판정 불능 park 된 attempt 가 하나라도 있으면 이 단계를 열지 않는다 — 귀속 판정은 상태 무관 판독(`EngineBrokerOrderIDs` 계열)으로 넓게 잡는다.
  - (r1 #4) 시한은 조회만이 아니라 단계 전체(조회 + 취소 제출)에 걸고 한 주기 취소 건수에 상한을 둔다.
  - (r1 #5) 미체결 판독은 「다음 쪽 있음인데 커서 없음」을 읽지 못함으로 처리한다(`ScanOrders` 의 그 갈래를 그대로 쓰지 않는다).
  - (r1 #6) 목록 행 → 대상 → 취소 요청 사이에서 주문 번호는 바이트 그대로 보존하고 종목·방향을 행 값으로 다시 대조한다.
  - (r1 #7) 운영자 알림은 취소 접수 뒤가 아니라 **취소를 내기 전에** 「취소를 시도한다」로 기록한다(접수와 기록 사이의 충돌로 알림이 사라지지 않게).
  - (r1 #8) 정본은 ADDED 에 더해 「보호 청산의 길 치우기는 엔진 귀속 주문만 다룬다」의 MODIFIED 로 경계를 닫는다.
  - (r1 #9) 「토글 꺼짐 = 조회 0·취소 0」으로 고치고(알림 문장은 토글과 무관하게 바뀐다고 명시), 롤백은 「토글 끄고 엔진 재시작」으로 적는다.
  - (r1 #10) 토글·audit 자리는 census 고정 함수(`NewContext`)를 고치지 않는 쪽을 먼저 찾고, 없으면 census 갱신을 Manager 가 승인한다.
