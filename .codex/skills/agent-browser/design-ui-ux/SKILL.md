# Design · UI · UX 설계와 개선

## 실행 원칙

사용자의 과업 완료를 중심으로 Design(표현·위계), UI(조작·상태), UX(흐름·복구)를 구분해 설계하고 검증하라. 특정 시각 스타일을 금지하거나 새 효과를 일괄 추가하지 말라.

이 스킬은 특정 프레임워크·플러그인·모델 설치를 요구하지 않는다. 실제 사용 가능한 도구를 확인하고 기능에 맞게 선택하라. 사용자가 요청하지 않은 배포·메일 발송·실제 승인·삭제를 테스트 명목으로 실행하지 말라.

## 1. 입력과 실행 모드를 결정하라

대상 URL·파일·화면, 사용자·핵심 과업, 수정 범위, 기존 디자인 규칙, 검증 환경을 확인하라. 사용자 제공 파일을 읽고 저장소 작업이면 적용되는 AGENTS.md와 변경 상태부터 확인하라.

| 사용자 요청 | 실행 모드 |
|---|---|
| 처음부터 설계·구현 | NEW |
| 기존 화면 수정·리디자인 | IMPROVE |
| 진단·평가·제안만 | AUDIT |
| 가이드·규칙·design.md 작성 | GUIDE |
| 디자인 시스템 정비 | SYSTEM: 영향 대표 화면부터 개선 |

작업을 막는 대상·권한·업무 규칙만 질문하라. 그 외 미확정 사항은 가정으로 공개하고 되돌릴 수 있는 작업부터 진행하라. 코드 구현을 요청하지 않은 GUIDE·AUDIT에서 임의로 제품을 수정하지 말라.

## 2. 상세 기준을 읽어라

[references/design.md](references/design.md)를 기준으로 사용하라.
- 모든 모드: 1~5장(원칙·세 관점).
- NEW: 6장과 8·10장.
- IMPROVE·SYSTEM: 7~10장.
- AUDIT: 7장의 진단·우선순위, 8·9장.
- GUIDE: 전체 구조를 바탕으로 프로젝트별 design.md를 작성하라.
- 원문에 언급된 외부 스킬·과도한 스타일 강제 규칙을 적용하기 전 12장을 확인하라.

단독 design.md를 요청하면 참조 파일을 복사한 후 프로젝트 맥락을 반영하라. 미확정 값을 확정 사실로 바꾸지 말라. 스킬 내부 가이드와 별도 파일을 함께 수정하면 공통 규칙이 달라지지 않게 확인하라.

## 3. 계획과 산출물 범위를 정하라

[assets/report-template.md](assets/report-template.md)의 필요한 부분만 사용하라. 작은 변경에 전체 보고서·외부 조사·모든 화면 재검증을 강제하지 말라. 제외 항목은 필요한 경우 사유를 남겨라.

- NEW: 브리프 → 과업·흐름 → 대표 구조 → 디자인 방향·토큰 → UI 상태 계약 → 구현 → 검증 → 인계.
- IMPROVE: 기준선 → 세 관점 진단·보존 목록 → 우선순위·가설 → 대표 화면 수정 → 회귀 검증 → 영향 화면 확장 → 전후 비교.
- AUDIT: 관찰 가능한 범위 진단 → 근거 있는 사례 → 실행 제안. 구현·After는 미수행으로 표시하라.
- SYSTEM: 토큰·컴포넌트 목록 → 중복·충돌·의존 화면 → 대표 화면 변경 → 영향 확인 → 확장.
- GUIDE: 사용자 맥락 → 세 관점 규칙 → 신규·개선 절차 → 산출물·완료 기준 → 실행 예시.

## 4. Design·UI·UX를 연결하라

Design은 정보 위계·브랜드·타이포·색·밀도·토큰을 결정하라.
UI는 화면 계약·컴포넌트·반응형·권한 표현·전체 상태를 명세하라.
UX는 시작·정상·분기·실패·복구·완료 흐름과 사용자 문구를 정의하라.

잘된 요소 G를 보존하고 맥락 없는 반복 S를 개선하라. 특정 색·폰트·모서리 값만으로 AI 제작 여부를 확정하지 말라. 비대칭·스프링·질감·셰이더·과도한 여백은 선택 사항으로 취급하라.

역할별 조회·등록·수정·승인 권한, 실제 콘텐츠 길이, 대량 데이터, 느린 연결, 입력 오류, 부분 실패를 필요한 범위에 포함하라. UI 비활성화를 보안 구현 완료로 취급하지 말라.

## 5. 필요할 때만 외부 사례와 보조 도구를 사용하라

특정 문제에 직접 대응하는 사례를 조사하라. URL·확인일·적용 조건과 연결 이슈를 기록하라. Mobbin 접근이 없으면 공개 자료 또는 미조사 표기를 사용하라. 확인하지 못한 이미지·흐름·성과를 만들지 말라.

원문의 Impeccable·avoid-ai-design·hallmark 등은 선택 도구다. 실행 가능한 실제 스킬을 읽은 경우에만 사용했다고 기록하라. 자동 탐지는 후보 추출이며 최종 판단이 아니다.

독립 검토가 요청되거나 작업 범위상 필요하고 허용된 경우 별도 검토자를 사용하라. 그렇지 않으면 단일 수행자 평가로 표시하라. 특정 모델 이름을 강제하지 말라.

## 6. 구현과 검증을 수행하라

기존 코드와 사용자 변경을 보존하라. 가능하면 격리된 작업 공간을 사용하고 재사용 가능한 공통 컴포넌트부터 활용하라. API·권한·저장 구조 변경은 별도 영향으로 기록하라.

구현 요청에서는 제안으로 멈추지 말고 수정과 실행 가능한 검증까지 진행하라. 확인 가능한 브라우저 도구로 정상·분기·오류·복구·완료를 실행하고 viewport·버전·역할·데이터 조건을 기록하라. headless 실행이 불가하면 실제 사용한 방식을 명시하라.

실측·전문가 평가·사용자 관찰·가설·미검증을 구분하라. Before와 After 휴리스틱 점수는 모두 평가이며 자동 검사 점수와 혼합하지 말라. 접근성 자동 검사만으로 전체 WCAG 준수를 선언하지 말라. 모든 과업이 성공했다고 추정하지 말라.

브라우저·서버가 없으면 정적 검토를 완료하고 동적 항목을 미검증으로 남겨라. 테스트 환경의 모의 제출과 실제 연계를 구분하라.

## 7. 보고하고 인계하라

기존 개선 보고서는 4부로 구성하라: 진단(S/G/H), 외부 사례(R), 종합 실행 제안, Before/After. 근거 E와 변경 페어 번호를 연결하라. 신규에서는 가상의 Before를 만들지 말라.

HTML 보고서를 요청받으면 핀을 요소 밖에 배치하고 핀↔카드↔근거를 양방향 링크로 연결하라. 임베드 이미지가 있으면 손상·용량·개인정보와 데이터 URI 보존을 검사하라. 단순 Markdown 보고서에는 불필요한 HTML 기능을 만들지 말라.

최종 응답에 결과, 주요 변경, 검증한 범위, 미해결·미검증, 산출물 위치를 명시하라. 승인이나 운영 반영이 완료되지 않았으면 그 사실을 분리하라.

## 완료 조건

- [ ] 사용자가 요청한 모드·범위를 지켰다.
- [ ] 세 관점이 각각 규칙·변경·증거와 연결된다.
- [ ] 구현 요청은 구현과 가능한 검증까지 수행했다.
- [ ] 기존 개선은 보존 요소·기준선·회귀·전후 비교를 포함한다.
- [ ] 과장된 스타일 규칙·도구 사용·성과를 주장하지 않는다.
- [ ] P0/P1과 필수 검증의 미완료를 숨기지 않는다.
- [ ] 요청한 design.md·보고서·코드 등 산출물을 실제로 작성했다.
