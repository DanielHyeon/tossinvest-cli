## 0. 한 줄 결론

설계 문서의 **아키텍처 방향은 코드와 일치**하지만, **현재 상태 진단(§1, §2 사실표)은 HEAD보다 뒤처져 있다.**
진짜 갭은 "진입 엔진이 없다"가 아니라 **"진입 엔진이 다 만들어져 있고 네 곳에서 구조적으로 잠겨 있다"**이다.
그리고 문서가 요구하는 전략 논지(S1/S2/M1)와 코드에 구현된 레인 논지(continuation/reversal/weekly-value)는 **서로 다른 전략**이다.

## 3. 전략 논지 갭

문서 §6이 요구하는 레인과 코드에 있는 레인은 **다른 전략**이다.

| 문서 | 코드 | 일치도 |
| --- | --- | --- |
| **S1** Breakout Retest Confirmed (저항 돌파 → 리테스트 → 재탈환, 가격 구조) | — | **없음**. reversal 레인은 absorption/dislocation 반전으로 논지가 반대 |
| **S2** Momentum Pullback Reclaim (모멘텀 → 눌림 → 지지 재탈환) | `continuationlane` (KR flow / US participation 지속) | **부분**. 지속 논지는 같으나 근거가 가격 구조가 아니라 수급·참여 흐름 |
| **M1** Medium Trend Pullback Continuation (일봉 20/60 추세, 20EMA 눌림) | `weeklyvaluelane` (OpenDART/EDGAR 공시 가치 재평가) | **없음**. 시간축만 비슷하고 논지는 펀더멘털 공시 |
| Opening Fast Chase (초기 비활성) | 해당 없음 | 문서 의도와 일치(미구현이 곧 비활성) |

부수 갭:

- 문서 §5.3의 KR 기관·외국인 순매수 **랭킹 가산점(각 10점, 80점 기준 통과 가능)** 은 코드에 없다. `continuationlane`은 flow를 랭킹 가산점이 아니라 **레인 자체의 판단 근거**로 쓴다.
- 문서 §5.1의 L1/L2 2계층 수집(10~15초 L1 + 레인별 예약 L2 슬롯)은 `candidatesrc`/`ratebudget`에 대응 구조가 있으나 문서가 규정한 우선순위 5단계와 "보유·보호 조회 예산 우선"이 명시적으로 계약화돼 있지 않다.

> **결정됨(D1, §5): 코드 우선.** 설계 문서 §6을 코드 논지로 개정하고 S1은 후속 레인으로 미룬다.

## 5. 확정된 결정 (2026-08-11, 사용자)

### D1 — 전략 논지: **코드 우선**

설계 문서 §6을 코드의 논지(continuation / reversal / weekly-value)로 개정한다. S1(돌파 리테스트)은 후속 레인으로 미룬다.
→ 레인 신규 구현 없음. 문서 §5.3(수급 랭킹 가산점)·§6·§12도 코드 기준으로 개정한다.

### D2 — proposal 생성: **엔진 내부 라이브 평가로 전환**

외부 Ed25519 서명 manifest(`TOSSOS_STRATEGY_PROPOSAL_*`) 경로를 은퇴시키고, 엔진이 승인 후보를 라이브로 평가해 결정을 만든다.

**이 결정이 계획을 가장 크게 바꾼다.** 분석 중 확인된 사실:

> **`evidence.db`에는 프로덕션 writer가 없다.** `strategyevidence.Store.Append`, `Store.SealSnapshot`,
> `OfficialAdapter.CollectAndCommit` 모두 **테스트에서만** 호출된다
> (`continuationlane/production_proposal_test.go:96`, `reversallane/…:125`, `strategyproposal/…:129`, `weeklyvaluelane/…:99`).

즉 서명 manifest는 사람 승인 장치였을 뿐 아니라 **부재한 증거 파이프라인의 대역**이었다. 라이브 평가에 필요한 것:

1. **증거 파이프라인** — KR net flow, US participation, KR OpenDART, US EDGAR → `evidence.db` writer.
   수집 transport는 이미 Go로 존재한다(§6.1). 빠진 것은 sink·구동 루프·도메인 계층이다.
   공식 API 호출 추가이므로 **retry matrix/rate 예산에 계상**(안전 불변식 §0-4).
2. **사이클별 snapshot seal** — 평가 시점의 증거를 불변으로 고정.
3. **N건 평가** — `strategy_entry_supervisor.go:398`의 `len(proposal.entries) != 1` 제약 해제.
4. **레인 간 중복 제거** — 문서 §6.2대로 두 레인이 동시 신호를 내면 사전 정의 우선순위로 **하나의 `entry_decision_id`만** 만든다.

**사람 승인의 이동 (안전 불변식 §0-7 유지 방법)**: per-proposal 서명이 사라지므로, 승인은
① 레인 활성화 record(a105) ② 위험 envelope 값(a104) ③ kill switch — 세 지점으로 옮긴다.
셋 다 사람이 직접 승인하며 에이전트가 자동 flip하지 않는다. **a105(레인 활성화)는 a100(보호 배선) 없이는 착수하지 않는다.**

### D3 — canary 수치: **승인, 단 주문상한은 전략 레인값 참조**

| 항목 | 확정값 |
| --- | --- |
| 거래당 위험 | `min(계좌 순자산 0.10%, 5,000원 상당)` |
| 일일 손실 한도 | `min(계좌 순자산 0.25%, 12,000원 상당)` |
| 일일 신규진입 | KR 2, US 2, 전 시장 합계 3 |
| 동시 신규 포지션 | 레인당 1, 전 시장 합계 3 |
| 레버리지·신용·공매도 | 금지 |
| **주문금액 상한** | **고정 190,000원을 쓰지 않는다.** 전략 레인이 구조적 손절에서 역산한 값을 참조한다 |

주문상한 결정의 코드 함의 — **레인은 현재 수량을 역산하지 않는다.**
`continuationlane/risk.go:73-110`의 `CalculateActualRisk`는 `quantity × (entry − stop) + fees`를 FX 환산해 `RiskBudgetMinor`와 **대조(검증)** 만 한다. 수량은 `allocation.go:56` `PlannedQuantity`로 **입력받는다**.
즉 문서 §7.1의 `quantity = floor(min(risk_budget/risk_per_share, notional_cap/entry))` 중 **검증 절반만 구현**돼 있고 역산 절반이 없다. 이 역산 경로가 a104의 본체다.

### 6.1 StockOS DART/SEC 이식 검토 (사용자 요청)

#### 정정 — TossOS의 수집기는 "없다"가 아니라 "구동되지 않는다"

`internal/strategyevidence/official_source.go`(13.5K)는 **완성된 Go 수집기**다:
`collectSEC`(EDGAR submissions) + `collectDART`(OpenDART), 페이징, 응답 byte 상한,
공유 rate budget(`SharedRateBudget`), credential provider, batch digest, `Complete` 플래그,
`CollectAndCommit` + `OfficialBatchSink` 인터페이스까지 있다.

빠진 것은 세 가지다 — ① `OfficialBatchSink` 구현체(= `evidence.db` writer) ② 어댑터를 만들어
주기적으로 호출하는 프로덕션 루프 ③ **도메인 계층**(정정 체인 판정·재무 수치 추출·point-in-time).
앞 절에서 "수집기를 만들어야 한다"고 쓴 것은 부정확했다. 만들 것은 **③과 ①②**이지 HTTP 수집기가 아니다.

#### 계층별 이식 판정

| 계층 | TossOS 현재 | StockOS (Python) | 판정 |
| --- | --- | --- | --- |
| HTTP transport·페이징·rate budget·credential | `official_source.go` **완성(Go)** | `dart/client.py` 231줄, `collector.py` 475줄 | **이식 불필요** — TossOS 쪽이 seal·digest·byte bound 계약이 더 엄격 |
| KR 정정 체인·point-in-time | 필드만 존재(`revision_identity`, `correction_notation`), **판정 로직 없음** | `dart/point_in_time.py` 284줄 — 실측 확인 계약 3건 | **계약 이식(Go 재구현) — 최고 가치** |
| KR 재무 수치 추출 | `DisclosureEvidence.FinancialInputs`(`types.go:104`) **정의만 있고 생산자 없음** | `dart/report_facts.py` 413줄 + `financials.py` 181줄 | **계약 이식** |
| 희석주식수 | `DilutedShares`·`DilutionStatus`·`DilutionFactsDigest` 필드 정의만 | `report_facts.py` 부분 | 이식 + 보완 |
| major events · red flags | 없음 | `events.py` 400줄 + `red_flags.py` 582줄 | **선택 — 관측 전용으로만.** StockOS 자신이 "판정 결과는 후보·진입·청산·사이징에 도달하지 않는다"고 못박았다 |
| backfill·진행상태 | 없음 | `backfill.py` 355줄 + `status.py` 87줄 | 이식 가치 낮음 — canary 규모에 불필요 |
| **US EDGAR 재무** | `collectSEC`는 submissions 목록만 | **없음** — `news_research.py:694`의 키워드 문자열 하나뿐 | StockOS에서 가져올 것은 없으나 **공식 taxonomy 출처가 있다**(§6.2) |
| **KR net flow (단기 레인)** | 생산자 없음 | `external_intelligence_collector.py:65` — 출처가 **WTS**(`wts.trading_flows`) | **그대로 이식 불가** — authority 불일치(아래) |

#### 그대로 가져올 수 없는 이유 둘

1. **언어** — StockOS `dart/` 3,723줄은 Python, TossOS는 Go다. 파일 복사가 성립하지 않는다.
   `docs/WORKFLOW.md`와 `docs/ROADMAP.md`도 "StockOS에서는 **검증된 거래 불변조건·순수 로직만 선별 이식**"으로
   규정한다. 실제로 가져오는 것은 코드가 아니라 **실측으로 확인된 도메인 계약**이다.
2. **authority 제약** — `continuationlane/production_proposal.go:86`은 KR flow 증거로
   `AuthorityKRX` 또는 `AuthorityTossOpenAPI`만 수용하고, US participation은 `AuthorityTossOpenAPI`만 수용한다
   (`:117`). StockOS의 flow는 **WTS 출처**다. TossOS 불변 규칙("WTS는 조회 전용")과 충돌하지는 않지만
   **레인이 그 출처의 증거를 받지 않는다.** 출처를 KRX/Toss Open API로 바꿔 재구현해야 한다.

#### 이식 가치가 가장 높은 것 — `point_in_time.py`의 실측 계약 3건

StockOS Phase 2 **실측**으로 확인된 계약이며, 재발견하려면 같은 실측을 반복해야 한다.

1. **정정 표시는 `report_nm` 접두이지 `rm`이 아니다.** `rm`은 시장·공시 구분 코드(유/코/공/정/연)이며
   정정과 무관함이 실측으로 확인됐다. 또한 `정정신고서제출요구`는 감독당국의 정정 *요구*이지 정정 공시가
   아니므로 별도 분류한다 — 요구를 정정으로 세면 정정 이력이 부풀려져 as-of 조회가 정상 구간을 잘못 막는다.
2. **귀속 접수번호를 확정할 수 없으면 저장하지 않는다(fail-closed).** `rcept_no`가 없거나 타임라인에
   없으면 값을 추측해 넣지 않는다.
3. **결측과 명시 0을 구분한다.** `dict.get` 기본값이 둘을 붕괴시키는 함정을 타입으로 막는다 —
   TossOS의 `not_measured` 규율(문서 §10.1)과 정확히 같은 원칙이다.

`red_flags.py`의 등급 배치 근거도 함께 인용할 가치가 있다: BLOCK에는 **되돌릴 수 없는 종류의 위험만**
넣고, ROE 미달·부채비율·상승여력 같은 **품질 지표는 BLOCK에 넣지 않는다** — 단기 수급·추세 레인에서는
저평가가 아니어도 상승할 수 있고, 이를 공통 하드 게이트로 만들면 단기 레인이 근거 없이 굶는다.

### 6.2 US EDGAR 재무 계층 — 출처와 재평가 (사용자 지시)

#### 선행 확인: 토스 Open API에는 재무 데이터가 없다

`internal/official/`의 read 표면은 account · asset · calendar · candle · commissions · conditional ·
market · orders · price_limits · protection이며 **재무제표·공시 엔드포인트가 없다**(grep 0건).
더구나 US weekly value 레인은 `weeklyvaluelane/production_proposal.go:123`에서 authority를
`strategyevidence.AuthoritySEC`로 고정하고 `:150`에서 `header.Authority != authority`면 거부한다.
즉 **토스가 재무 데이터를 제공하더라도 이 레인은 그 증거를 받지 않는다.** SEC/EDGAR가 유일한 경로다.

#### 재평가: "전량 신규 설계"는 틀렸다

`collectSEC`는 이미 **`https://data.sec.gov/submissions/CIK##########.json`** 을 소비한다
(`source.go:152`에 endpoint identity가 하드 핀). 페이징·byte bound·digest·`Complete` 판정이
모두 Go로 돌아간다. 재무 수치는 **같은 호스트의 XBRL companyfacts 리소스**를 같은 어댑터로 치면 된다.

`SourcePolicy.validateOfficial()`이 `ContractID`·`EndpointIdentity`·`SchemaVersion`을 하드 핀하므로,
필요한 작업은 **새 계약 1건 추가**다(예: `sec-companyfacts-v1`). 어댑터·rate budget·credential 프로필
(SEC는 `CredentialRequired: false`)은 그대로 재사용한다. KR도 같은 구조다 — 현재 OpenDART 계약은
`api/list.json`(공시 목록)만 핀돼 있으므로 재무제표 엔드포인트 계약을 별도로 추가한다.

#### 매핑 지점은 단 한 곳

`weeklyvaluelane.FinancialInput`은 `{Name, ValueMinor, Unit}` 세 필드뿐이다(`types.go:73-77`).
**XBRL 표준 element name을 `Name`에 그대로 싣는 것으로 매핑이 성립한다.** 따라서 필요한 것은
파서가 아니라 **어떤 element를 어떤 계층에서 고를지에 대한 표준 근거**다.

#### 근거 출처 (권위 순)

| 출처 | 쓰임 |
| --- | --- |
| **SEC 공식 XBRL Taxonomies** (연도별·분기별 아카이브) | SEC가 승인한 US GAAP 표준 계정과목의 계층 구조와 아키텍처 가이드. **정본** |
| **FASB Taxonomy Viewers** | 자산·부채·자본·매출 전체를 부모-자식 트리로 열람. depth와 표준 element name 확인 |
| **FASB Taxonomy Online Search** | 특정 계정과목(예: `CashAndCashEquivalents`)의 상위 계층·하위 구조 검색. 최초 이용 시 무료 계정 등록 필요할 수 있음 |
| **EdgarTools — XBRL Standardization Concepts** | 대형 금융정보사가 매핑하는 **핵심 80~150개 표준 재무 라인 아이템** 계층. 실무 매핑 범위 산정용 |

**EdgarTools는 Python OSS다.** StockOS와 동일한 규칙을 적용한다 — **매핑표와 표준화 개념만 참조하고
코드는 이식하지 않는다.** 인용 시 라이선스를 확인하고 출처를 spec delta에 남긴다.

미국 상장기업은 재무제표를 XBRL 구조로 계정 과목의 상하 관계를 설정해 제출하므로, 위 taxonomy가
**계층의 권위**다. 임의로 고른 element 집합을 재무 입력으로 삼지 않는다.

#### 남는 미지수 (출처가 해결하지 못하는 것)

1. **point-in-time 정합** — companyfacts는 최신 사실을 반환한다. TossOS `DisclosureEvidence`는
   `as_of`·`cutoff_at`·`superseded_revision_id`·`revision_sequence`를 요구한다. 정정(10-K/A 등)이
   과거 값을 덮을 때 as-of 재구성이 되는지는 **실측으로 확인**해야 한다. KR 쪽은 StockOS
   `point_in_time.py`의 실측 계약이 있으나 US는 없다.
2. **`ValueMinor` 스케일** — `MonetaryScale`·`MonetaryUnit`과 XBRL `decimals`/`unitRef`의 대응.
3. **희석주식수** — `DilutedShares`·`DilutionStatus`·`DilutionFactsDigest`에 대응하는 element 선택.

이 셋은 a109의 design 단계에서 fixture로 확정한다.

#### 이식 계획 반영

- **a102를 KR/US로 분리한다.** KR은 StockOS 계약 이식으로 위험이 낮고, US는 선례가 없어 성격이 다르다.
- **첫 활성화 레인 후보는 KR weekly value다.** 증거 조달 가능성 기준으로 가장 짧은 경로이기 때문이다 —
  KR disclosure는 TossOS 수집 transport(있음) + StockOS 도메인 계약(있음)으로 닿지만,
  단기 레인의 KR net flow는 **수집기도 승인된 출처도 없다**. (문서 §15는 단기 레인 우선을 권했으나,
  그 판단은 증거 조달 가능성을 고려하지 않은 것이다.)

## 7. 규모 추정과 위험

- **P0는 change 7건**이고 그 범위는 **KR weekly value 레인 하나**까지다. D2(라이브 평가)가 a102·a103·a104 세 건을 추가시켰다. 서명 manifest를 유지했다면 P0는 4건이었다.
- **a102와 a109 모두 초기 추정보다 위험이 낮다.** HTTP 수집기는 이미 Go로 있고(§6.1), KR 도메인 계층은
  StockOS의 실측 계약을, US 재무 계층은 SEC/FASB 공식 taxonomy를(§6.2) 근거로 삼을 수 있다.
  양쪽 다 **새 `SourcePolicy` 계약 추가 + 매핑 계층**으로 좁혀진다.
- **남은 최대 미지수는 US point-in-time 정정 재구성이다**(§6.2). KR은 StockOS 실측 계약이 있으나
  US는 없고, taxonomy도 이 문제를 풀어주지 않는다. a109 design에서 fixture로 확정해야 한다.
- **여섯 레인 중 다섯은 P0 이후다.** KR net flow는 승인된 출처가 없고(StockOS는 WTS 출처라 재사용 불가),
  US participation·US EDGAR도 선례가 없다. 문서 §15가 권한 "S1·S2 먼저"는 증거 조달 가능성을 고려하지
  않은 순서다.
- **a103은 되돌리기 어려운 결정**을 포함한다: `strategydispatch`/`strategyruntime`(약 60K)과 `strategy_dispatch_cycle.go` 중 하나를 삭제한다. 어느 쪽이 정본인지는 a103 design 단계에서 두 구현의 계약을 대조해 정한다.
- a100·a101·a102를 병행하면 3건을 동시에 진행하게 되는데, `docs/WORKFLOW.md`는 **change당 활성 Teammate 1명**을 요구한다. 파일 표면이 겹치지 않으므로 병행은 가능하나, `make sdd-sync` fingerprint 경합에 주의한다(기억: 병행 세션 게이트 간섭).
