## Context

Guardian 주입이 완료된 엔진이 startup account 조회에는 성공했지만, restart
reconciliation의 첫 open-order 조회에서 계좌 목록을 다시 요청해 429를 받고
루프 시작 전에 종료했다.

## Observation

`Client.Accounts`가 반환한 첫 account sequence를 같은 클라이언트에 보존하지 않아
`ensureAccountSeq`가 즉시 중복 discovery를 수행했다. 또한 engine accountRef
해석은 첫 레코드의 번호가 비면 뒤 레코드로 건너뛴 반면 lazy sequence는 항상 첫
레코드를 택해 journal identity와 request header가 갈라질 수 있었다. 명시적
sequence도 첫 레코드와 다르면 같은 문제가 재발한다.

## Evidence

public/lazy unresolved discovery를 기존 mutex와 lock-assuming helper로
직렬화하고, 완전히 성공한 양수 첫 sequence만 zero cache에 반영했다. 선택 완료
후에는 atomic fast path를 사용해 느린 public 계좌 목록 I/O가 손절·취소를 포함한
account-scoped 요청을 막지 않는다. 이후 public 목록이 암묵적 선택과 달라지거나
비면 identity drift 오류로 거부하고 기존 선택을 조용히 바꾸지 않는다. 엔진은 첫
레코드의 비어 있지 않은 accountNo·양수 sequence·실제 선택값의 정확한 일치를
journal open 전에 검증한다. 실제 CLI `NewContext → Context.Recovery → Recovery.Run`
회귀에서 `/accounts` 1회, 두 스냅샷의 orders·holdings·buying-power 동일 header를
확인했다. genuine orders 429는 여전히 빈 partial snapshot과
`ErrRecoveryIncomplete`로 fail-closed다. 집중 race, 전체 Go test, strict
OpenSpec, Function Logic Map, SDD check를 통과했다.

## What to reuse

계좌 scope를 가진 클라이언트는 “표시용 accountRef 조회”와 “header용 sequence
해석”을 독립 절차로 만들지 않는다. unresolved discovery는 한 mutex/cache에서
공유하되, 선택된 값은 lock-free로 읽어 위험 축소 주문의 지연 경로를 늘리지 않는다.
상위 runtime이 durable identity를 만들기 전에 실제 header 선택과 같은지 검증하고,
후속 목록 drift는 fail-closed한다. 중복 429는 이미 얻은 식별자를 재사용해 제거하며
recovery의 partial-read 거부를 완화하지 않는다.

## What not to infer

이 수정은 계좌 API 또는 snapshot endpoint의 일반 429 retry 정책이 아니다.
여러 계좌 중 자동 선택, Guardian 승인 확대, gate flip, 주문 mutation retry,
부분 snapshot 수용, 현재 바이너리 교체나 엔진 재시작도 승인하지 않는다.
