## Context

headerless TLS+Host fallback을 추가한 뒤에도 실제 Chrome의 `/restart` 폼은 origin
gate에서 거부됐다. 브라우저 캡처 결과 응답의 `Referrer-Policy: no-referrer` 때문에
same-origin POST가 `Origin: null`과 Referer 부재로 직렬화됐다.

## Observation

`Origin: null`은 헤더 부재가 아니라 sandbox 등에서도 생길 수 있는 명시적 opaque
origin이므로 TLS+Host fallback으로 구제하면 안 된다. 또한 remote security wrapper
한 곳만 고치면 `Console.render`의 후행 응답 헤더와 shared/restart HTML meta가 다시
`no-referrer`를 적용한다. 브라우저의 실효 정책을 결정하는 네 표면을 모두
`same-origin`으로 맞춰야 한다.

## Evidence

원격 wrapper와 renderer의 두 응답 헤더, shared head와 restart interstitial의 두 meta
값만 변경했다. explicit `Origin: null`에 canonical TLS·Host와 유효 CSRF를 함께 줘도
실제 mutation gate가 origin 오류로 거부하고 handler 호출은 0회임을 테스트했다.
focused/console/race/전체 Go test, vet, strict OpenSpec, Function Logic Map, PM 1:1,
독립 보안 리뷰와 8단계 gate가 통과했다. 배포된 Chrome에서 실제 `/restart` 폼의
CSRF만 고의로 무효화해 제출하자 canonical Origin/Referer가 전송되고 origin 오류가
아닌 CSRF 403에 도달했다.

## What to reuse

브라우저 생성 보안 헤더 문제는 서버의 판정 로직만 보지 말고 response header,
renderer override, HTML meta를 함께 검색한다. operational form의 브라우저 검증은
실제 폼을 쓰되 CSRF 값을 고의로 무효화하면 origin gate 통과를 증명하면서 대상
handler 실행을 구조적으로 막을 수 있다.

## What not to infer

`same-origin` 정책은 explicit opaque/cross-origin 허용, CSP 완화, forwarded header
신뢰, 인증 완화 또는 인터넷 공개를 뜻하지 않는다. Chrome DevTools의
`/.well-known/appspecific/` CSP 경고는 앱 폼과 무관하며 허용할 필요가 없다.
