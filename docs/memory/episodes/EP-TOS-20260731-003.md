## Context

canonical HTTPS 콘솔에서 설정·재시작 폼을 제출해도 공통 origin gate가 모든 POST를
거부했다. 응답은 `Referrer-Policy: no-referrer`를 보내고 일부 브라우저는 same-origin
폼 POST에 Origin도 보내지 않아, 서버가 요구하는 두 증거를 서버 자신이 없앨 수 있었다.

## Observation

URL path는 origin identity가 아니며 scheme·host·port만 비교해야 한다. 그러나 헤더
부재를 단순히 TLS+Host로 보완하면 CSRF가 없는 compatibility login까지 약화된다.
따라서 strict Origin→Referer 판정은 login에 유지하고, CSRF가 바로 뒤따르는 mutation
gate에만 direct TLS+exact Host fallback을 둬야 한다. 명시적 빈 값·공백·중복 헤더는
부재가 아니라 잘못된 증거이며 더 낮은 우선순위로 fall through하면 안 된다.

## Evidence

명시적/빈 값/중복/상충 Origin·Referer, 하위 path, headerless login, non-TLS,
wrong Host/port, `X-Forwarded-Host`/`X-Forwarded-Proto`, CSRF 순서를 RED/GREEN
회귀 테스트로 검증했다. 콘솔 전체 race, 저장소 전체 test/vet/strict validate,
Function Logic Map, PM 1:1, 독립 security review와 `make gate`가 통과했다.
배포 후 headerless `/restart`에 일부러 잘못된 CSRF를 보내 origin 오류가 아니라
CSRF 403에 도달함을 확인했으며 restart handler는 호출하지 않았다.

## What to reuse

브라우저 privacy header와 origin gate를 함께 설계한다. header key의 존재 여부를
`Header.Get` 결과와 혼동하지 말고, 우선순위가 높은 명시적 증거는 유효/무효 모두
최종으로 취급한다. request-derived fallback은 그 뒤에 독립 anti-CSRF gate가 있는
mutation 경로로만 제한하고 login 같은 credential bootstrap에는 재사용하지 않는다.

## What not to infer

TLS+Host fallback은 reverse proxy, forwarded header 신뢰, wildcard origin, 인터넷
공개 또는 인증 완화를 승인하지 않는다. 또한 설정 저장 가능성이 LIVE 주문, 엔진
기동, 운영 토글 변경 또는 재시작 실행을 자동 승인한다는 뜻이 아니다.
