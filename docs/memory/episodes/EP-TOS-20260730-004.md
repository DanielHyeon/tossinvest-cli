## Context

Codex와 Claude가 TossOS 저장소에서 동시에 시작되며 각각 같은
`.sdd/gbrain-home`으로 `gbrain serve`를 띄웠다. 두 프로세스는 모두 살아 있었지만
PGLite lock heartbeat의 소유자는 하나뿐이었고, 후발 서버와 직접 CLI는 응답하지
않다가 timeout했다.

## Observation

프로젝트별 `GBRAIN_HOME` 분리는 다른 저장소와의 충돌만 막는다. 같은 저장소의
process-per-client stdio MCP는 PGLite의 단일 프로세스 계약과 충돌한다.
heartbeat lock 파일을 삭제하는 것은 살아 있는 소유자의 데이터 디렉터리를 동시에
여는 위험한 복구이며, PID 파일만 추가하면 crash 뒤 stale cleanup과 PID 재사용 문제가
남는다.

## Evidence

두 `gbrain serve`의 command, cwd, `GBRAIN_HOME`, open PGLite files와
`.gbrain-lock/lock` PID를 교차검증했다. project wrapper가 별도 POSIX flock을
nonblocking으로 획득하고 file descriptor를 `execve` 뒤에도 상속하게 했다. 따라서
실제 GBrain 프로세스가 종료되면 커널이 자동으로 소유권을 회수한다. 변경 전부터 살아
있던 PGLite owner는 lock JSON의 PID 생존과 upstream steal grace 안의 heartbeat를 함께
확인해 exit 75 busy로 즉시 반환하고 그 lock은 삭제하지 않는다. PID가 살아 있어도
heartbeat가 stale이면 PID 재사용/holder wedge일 수 있으므로 실제 GBrain의 token-checked
stale recovery에 판정을 넘긴다.

실제 subprocess 회귀는 두 번째 `serve`가 실제 GBrain을 시작하지 않는 것, holder
종료 뒤 별도 파일 삭제 없이 다음 명령이 실행되는 것, fresh legacy live owner가 보존되고
stale heartbeat는 upstream recovery에 위임되는 것, lock metadata가 command 인자를
저장하지 않는 것을 검증한다. SDD sync는 source probe
전후 어느 시점에 contention이 생겨도 GBrain freshness를 갱신하지 않고 CodeGraph
성공만 기록한다. 일반 nonzero source probe와 source registration 실패는 후속 성공으로
덮지 않고 즉시 incomplete로 끝내며, legacy owner 진단은 안전한 subcommand만 출력한다.
현재 환경의 wrapper probe는 종전 약 10초 timeout 대신 약 0.02초에
busy로 끝났고, lock owner가 아닌 동일 홈의 중복 GBrain 자식만 SIGTERM으로 종료했다.

## What to reuse

단일 프로세스 embedded store를 여러 에이전트가 공유할 때는 DB 내부 lock timeout에
의존하지 말고 모든 실행 입구를 하나의 kernel-lifetime lock으로 감싼다. lock 파일
내용은 진단용일 뿐 권위로 삼지 않으며, crash release는 kernel flock에 맡긴다. 배포 전
프로세스가 존재할 수 있는 전환기에는 기존 store lock의 live owner를 별도로 감지한다.
advisory 계층의 검증된 busy만 hard-evidence 경로에서 비차단 처리하고, 다른 오류까지
일괄적으로 삼키지 않는다.

## What not to infer

이 패턴은 PGLite가 여러 프로세스의 동시 접근을 지원한다는 뜻이 아니다. 두 번째
에이전트에 동시 GBrain MCP를 제공하지도 않으며, 그 요구는 HTTP broker 또는 local
PostgreSQL backend를 다루는 별도 change가 필요하다. 살아 있는 lock owner, 에이전트
부모 프로세스, `.gbrain-lock` 디렉터리를 자동 종료·삭제해도 된다는 승인도 아니다.
